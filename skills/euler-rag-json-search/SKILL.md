# euler-rag-json-search

This skill is for completing JSON knowledge-base search tasks end to end, not
just for running a script. Use it to inspect the target KB, build the correct
`/json/search` request, execute it, and verify that the result is usable.

## Agent Contract

When this skill is selected, the agent must perform a real JSON KB search task
or produce an exact runnable command for one. Do not answer from memory and do
not switch to chunk search.

Mandatory behavior:

1. Use `POST /json/search`.
2. Put the natural-language fault description in `query`.
3. Add `logical_expression` only for explicit structured field constraints.
4. Prefer the bundled CLI to construct requests. Do not hand-write payload JSON
   when `scripts/search_json.py` is available.
5. Execute the request when tools are available; otherwise output a paste-ready
   curl command generated by `scripts/search_json.py --print-curl`.
6. Validate the response by reporting `code`, hit count, and the top result
   names/titles.

Execution honesty rule:

- Never fabricate `code`, hit count, result names, titles, or summaries.
- If no command was actually executed, say `not executed` and output only the
  command that should be run.
- Only report `code`, `hits`, or `top result` after reading real stdout from
  `scripts/search_json.py`, `curl`, or another actual tool call.
- Do not simulate, estimate, or infer API results from the query text.
- If a tool is unavailable, stop at command generation and ask the user or
  calling framework to run the command.

Never invent structured filters from ordinary keywords. For example, terms such
as `skb_gso_segment`, `RAID`, `SCSI`, `SMART`, `磁盘故障`, or `性能下降` are query
terms. They are not filters unless the user says a named field must equal,
contain, or compare to a value.

For strict structured-search verification, run a structured-only request first:
set `query` to an empty string and include only the explicit
`logical_expression`. Mixed semantic+structured requests may be useful for
ranking, but service implementations can blend semantic candidates with
filtered candidates depending on `ratio`, so they are not the cleanest proof
that the structured filter itself works.

## Hard Payload Rules

The `/json/search` payload schema is fixed. Do not rename fields, flatten nested
arrays, or invent mode flags.

Required root shape:

```json
{
  "need_trace": false,
  "search_json_configs": [
    {
      "kb_id": "<KB_ID>",
      "query": "<QUERY>",
      "top_k": 5
    }
  ]
}
```

Strict rules:

- The root object must contain `search_json_configs`, whose value is an array.
- Each search config must be inside `search_json_configs`.
- Use `top_k`; never use `topn`, `topK`, or `limit`.
- Do not add `mode`, `search_mode`, or `type` fields.
- `semantic_keys` must be an array of key paths, for example
  `[["title"], ["phenomenon"], ["root_cause"], ["solution"], ["content"]]`.
  Do not use a flat array such as `["title", "phenomenon"]`.
- `logical_expression` must use `{ "operator": "...", "expressions": [...] }`.
  Do not use shortcut forms such as `{ "eq": { "kernel_version": "3.0.18" } }`.
- A condition inside `expressions` must contain `field`, `type`, `operator`,
  and `value`.

Incorrect examples that must not be generated:

```json
{"kb_id":"<KB_ID>","query":"","topn":5}
```

```json
{"logical_expression":{"eq":{"kernel_version":"3.0.18"}}}
```

```json
{"semantic_keys":["title","phenomenon"],"mode":"semantic-only"}
```

If uncertain, run the bundled CLI with `--print-payload` or `--print-curl`
instead of constructing JSON manually.

Use this decision table:

| User input | Request shape |
| --- | --- |
| General troubleshooting text only | Semantic-only: `query` + `semantic_keys`; omit `logical_expression`. |
| Explicit field constraint, such as `kernel_version=3.0.18` | Structured or mixed: include `logical_expression`. |
| General text plus explicit field constraint | Mixed: keep text in `query` and put only the field constraint in `logical_expression`. |
| User asks to verify structured search | Use a known existing field/value from inspected records, then run a structured test. |
| API returns 422 for a filter | Fix the filter schema or remove the unsupported filter; do not silently claim success. |
| API returns 200 with empty hits | The request succeeded but did not retrieve matching records. Report empty results. |

## Workflow

1. **Collect runtime inputs**
   - `base_url`, for example `http://localhost:9988` or a deployed service URL.
   - `kb_id`.
   - `access_key`. Do not print real secrets in handoff docs; use
     `<ACCESS_KEY>` placeholders unless the user explicitly asks for a private
     runnable command.

2. **Inspect the target KB before choosing fields**
   - Use `/kb/list` to confirm the KB exists when needed.
   - Use `/json/list/{kb_id}` to inspect one or more records.
   - Do not assume the JSON schema. Choose `semantic_keys` and filters from the
     actual record fields.

3. **Choose search mode**
   - Default to semantic search: provide `query`, `top_k`, and
     `semantic_keys`.
   - Treat free-text keywords as query terms, not filters. For example,
     `SMART`, `RAID`, `SCSI`, `磁盘故障`, and `硬盘坏道` should stay in
     `query` unless the user explicitly asks to filter a named field.
   - Structured filtering is opt-in. Use `logical_expression` only when the
     user provides explicit field constraints such as `kernel_version=3.0.18`,
     `category=storage`, or `enabled=true`, and only when those fields are
     present in the JSON content.
   - Do not assume wrapper metadata such as uploaded filename is filterable
     unless the API/schema confirms it.
   - Mixed search: combine semantic `query` with structured filters when both
     are needed.
   - Use `/json/search` for JSON KB tasks. Do not switch to `/chunk/search`
     unless the user specifically asks for chunk search.

4. **Generate the request**
   - For CLI usage, run `scripts/search_json.py --print-payload` to inspect the
     generated body before executing a new or risky request.
   - For handoff, generate a curl command that can be pasted into a terminal.
   - Keep environment-specific paths out of the skill instructions. Refer to
     the bundled script by relative path: `scripts/search_json.py`.

5. **Execute and validate**
   - A successful API call should return `code=200`.
   - A useful search sample should return a non-empty `result.jsons`.
   - Report at least the returned count and the top result name/title.
   - Prefer `--summary` when using the bundled CLI so the model sees the
     validation fields directly.
   - If no explicit field filters were requested, report the search as
     semantic-only. Do not say "structured filters fell back" for a normal
     semantic-only query.

6. **Troubleshoot**
   - `401/403`: check auth header style and access key.
   - `404`: check `base_url` and route path.
   - `422`: inspect the payload shape, especially `logical_expression`. If the
     filter was inferred from free text rather than requested as a field
     constraint, remove `logical_expression` and rerun semantic-only.
   - `code=200` but empty `jsons`: inspect record fields, adjust
    `semantic_keys`, increase `top_k`, or simplify filters.

## Request Templates

Semantic-only request:

```json
{
  "need_trace": false,
  "search_json_configs": [
    {
      "kb_id": "<KB_ID>",
      "query": "skb_gso_segment 内核 WARNING 性能下降",
      "top_k": 5,
      "semantic_keys": [
        ["title"],
        ["phenomenon"],
        ["root_cause"],
        ["solution"],
        ["content"]
      ],
      "ratio": 0.3
    }
  ]
}
```

Structured-only request for a known content field:

```json
{
  "need_trace": false,
  "search_json_configs": [
    {
      "kb_id": "<KB_ID>",
      "query": "",
      "top_k": 5,
      "logical_expression": {
        "operator": "and",
        "expressions": [
          {
            "field": "kernel_version",
            "type": "string",
            "operator": "eq",
            "value": "3.0.18"
          }
        ]
      }
    }
  ]
}
```

Mixed semantic plus structured request:

```json
{
  "need_trace": false,
  "search_json_configs": [
    {
      "kb_id": "<KB_ID>",
      "query": "skb_gso_segment 内核 WARNING 性能下降",
      "top_k": 5,
      "semantic_keys": [
        ["title"],
        ["phenomenon"],
        ["root_cause"],
        ["solution"],
        ["content"]
      ],
      "logical_expression": {
        "operator": "and",
        "expressions": [
          {
            "field": "kernel_version",
            "type": "string",
            "operator": "eq",
            "value": "3.0.18"
          }
        ]
      },
      "ratio": 0.3
    }
  ]
}
```

When generating a curl command, always keep this route and header shape:

```bash
curl -sS -X POST "<BASE_URL>/json/search" \
  -H "access_key: <ACCESS_KEY>" \
  -H "Content-Type: application/json" \
  -d '<PAYLOAD_JSON>'
```

## Required Agent Output

After running the search with an actual tool call, return a compact result:

```text
mode: semantic-only | structured-only | mixed
code: 200
hits: <number>
top_results:
  1. <name or title>
  2. <name or title>
notes: <empty/no-hit/error explanation if needed>
```

If execution is not possible, output the exact curl command and state that it
has not been run.

Use this exact shape when execution is not possible:

```text
status: not executed
reason: no bash/curl/CLI execution result is available
command:
  <paste-ready command>
notes: Do not report code, hits, or top result until this command is actually run.
```

## Bundled CLI

The bundled CLI is a convenience wrapper around `POST /json/search`.

```bash
python3 scripts/search_json.py \
  --base-url http://localhost:9988 \
  --kb-id <KB_ID> \
  --access-key <ACCESS_KEY> \
  --query "用户问题或检索词" \
  --top-k 5 \
  --semantic-keys title,phenomenon,root_cause,solution,content \
  --semantic-only \
  --summary
```

Print the payload without sending it:

```bash
python3 scripts/search_json.py \
  --kb-id <KB_ID> \
  --access-key <ACCESS_KEY> \
  --query "用户问题或检索词" \
  --semantic-keys title,phenomenon,root_cause,solution,content \
  --print-payload
```

Print a curl command for handoff:

```bash
python3 scripts/search_json.py \
  --base-url http://localhost:9988 \
  --kb-id <KB_ID> \
  --access-key '<ACCESS_KEY>' \
  --query "用户问题或检索词" \
  --semantic-keys title,phenomenon,root_cause,solution,content \
  --print-curl
```

## Field Selection

For openEuler kernel-case JSON records, common semantic fields are:

```text
title,phenomenon,root_cause,solution,content
```

If the inspected records use another schema, replace these with the actual
fields. Nested keys use dot notation in the CLI, for example:

```text
metadata.title,content.summary
```

## Structured Filters

Use `--filter` for generic content-field filters:

```bash
python3 scripts/search_json.py \
  --kb-id <KB_ID> \
  --access-key <ACCESS_KEY> \
  --query "磁盘无法识别" \
  --semantic-keys title,phenomenon,root_cause,solution,content \
  --filter kernel_version:eq=3.0.18 \
  --summary
```

Supported filter format:

```text
field[:operator[:type]]=value
```

Examples:

```text
kernel_version:eq=3.0.18
title:like=megaraid_sas
priority:gte:number=3
enabled:eq:boolean=true
```

Multiple filters are combined with `--operator` (`and` by default).

Legacy flags `--name` and `--kernel-version` are still supported for schemas
that actually contain those fields. Prefer `--filter` when the target schema is
not fixed.
