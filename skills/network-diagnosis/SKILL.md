# 网络故障诊断 Skill

本技能为运维/工程师提供一套 **网络故障诊断步骤与报告模板**，适用于以下典型场景：

- 业务反馈某台服务器网络不通或时延显著升高（你已能登录到目标服务器并执行排查命令）。
- 某个端口或服务偶发/持续不可用。
- 仅部分网段（如某机房、某业务网段）访问异常。

## Skill 目录结构

本技能包含以下文件，请勿自行创建或重写这些文件：

```text
network-diagnosis/
├── SKILL.md                 # 主指令文档（本文件）
└── scripts/
    ├── collect_snapshot.sh  # 阶段一快照采集脚本（核心脚本，请直接调用）
    └── README.md            # 脚本使用说明
```

> **重要**：`scripts/collect_snapshot.sh` 是本技能提供的核心采集脚本，位于本 Skill 目录下。
> 使用时请通过相对路径调用：`bash scripts/collect_snapshot.sh ...`
> **请勿自行编写或重写采集脚本**，直接使用现有脚本即可。

> **使用范围与定位原则**
> - 若用户明确指出 **某个 IP / 某个网口（或网卡）** 出现不通、丢包、延时、抖动等问题：  
>   - 以该 IP/接口为主线进行 **精准定位**（优先围绕该接口的链路状态、邻居表、路由、端口可达性与相关日志展开），避免无关信息干扰。
> - 若用户描述的是 **某台服务器整体** 网络不通/延时等（未指定具体 IP/接口，或影响范围不清）：  
>   - 需要对该服务器的 **所有网卡/子接口** 进行覆盖分析，并结合路由与流量路径逐一排查，避免遗漏“某一块网卡异常”或“策略路由导致部分路径异常”的情况。

## 整体诊断框架

本技能采用 **「三阶段 + 分支 + 早停」** 的诊断框架：

1. **阶段一：快速信息收集（T0 快照 / Network & System Snapshot）**  
   - 明确本次故障对应的目标接口（用户指定则聚焦，未指定则覆盖所有接口/子接口）。  
   - 一次性采集接口状态、路由、DNS、系统资源与关键日志，构建高信息量快照。  
   - 同步执行一次全局 MAC 去重检查（检查本机是否存在两个或更多接口使用同一 MAC），作为必查项之一。  
   - 如发现显性致命问题（物理链路中断、黑洞路由、邻居表/conntrack 满、DNS 完全失效等），可直接给出结论与建议，必要时早停。

2. **阶段二：按层级分支收敛（L1/L2/L3/L4/L7 粗定位）**  
   - 基于阶段一标签，把问题归类到若干网络层级与故障类型：  
     - L1-L2：物理链路 / MAC / ARP / VLAN  
     - L3：路由 / 策略路由 / 多出口 / 不对称路径  
     - L3.5：DNS / 解析  
     - L4：端口 / 防火墙 / conntrack  
     - L4-L7：端到端性能 / 应用监听与配置  
   - 每个分支只执行少量高价值检查，避免“全网体检”。

3. **阶段三：深入诊断与根因分析（Deep Dive & Root Cause Analysis）**  
   - 针对已识别的层级与故障类型，执行更精细的路径探测、多点对比和时序分析。  
   - 最终生成一份根因分析报告，包含：  
     - 故障现象、故障组件、故障时间、故障根因、故障传播链、故障时间链、关键证据、影响评估和修复建议。

## 一、阶段一：快速信息收集（T0 快照）

**目标**：用少量命令在数秒内获得全局“网络与系统健康画像”，优先发现显性致命问题。

> **推荐方式（脚本化采集）**：为避免人工漏项，建议优先使用 `scripts/collect_snapshot.sh` 一键生成 T0 快照，并将输出目录作为后续阶段的输入材料。  
> - 示例：`bash scripts/collect_snapshot.sh --out /tmp/net_diag --iface <iface> --dest <关键目标IP>`  
> - 产物：`/tmp/net_diag/snapshot_YYYYmmdd_HHMMSS/` 下的多份 `.txt` 文件（接口、路由、DNS、连接状态、系统日志等）。

### 1.1 脚本化采集（唯一方式）

直接运行阶段一快照采集脚本，生成 T0 快照目录（后续所有判断均以该目录内文件为依据）：

```bash
bash scripts/collect_snapshot.sh \
  --out /tmp/net_diag \
  --iface <可选_重点接口> \
  --dest <可选_关键目标IP>
```

参数建议：

- **用户已明确指定异常接口**：传 `--iface <iface>`，脚本会额外采集该接口的 `ethtool/ethtool -S` 等细节。
- **用户已明确指定关键目标（网关/核心服务 IP）**：传 `--dest <dest_ip>`，脚本会采集 `ip route get` 与 `ping` 快速探测结果。
- **用户未指定接口/目标（整机异常）**：可不传 `--iface/--dest`，先做一次全量快照；如需收敛，再补采一次带 `--iface/--dest` 的快照。

> 产物目录：`/tmp/net_diag/snapshot_YYYYmmdd_HHMMSS/`，包含接口、路由、DNS、连接状态、防火墙/conntrack、内核日志等多份 `.txt`。  
> 其中 `mac_duplicate_check.txt` 用于记录“本机接口是否存在重复 MAC”（`DUP_MAC` / `NO_DUP_MAC`），`mac_duplicate.txt` 仅保留重复项明细（为空表示未检出重复 MAC）。
> `ip_conflict_check.txt` 用于记录基于 `arping -D` 的本机 IP 冲突探测结果（若环境缺少 `arping`，文件内会给出 `SKIP` 提示）。

### 1.2 从快照中确定 `target_ifaces[]`（聚焦或全量）

根据快照文件进行选择：

- **聚焦接口**：若传了 `--iface`，以 `iface_<iface>_details.txt` 与 `ip_link_stats.txt` 为主线，记录为 `target_ifaces[]`。
- **全量覆盖**：若未指定接口，以 `ip_link_stats.txt` 与 `ip_addr.txt` 中所有 UP 的物理口/bond/vlan 子接口组成 `target_ifaces[]`。
- **路径确认**：若传了 `--dest`，以 `route_get_<dest>.txt` 为准确认实际出接口与下一跳，并用于校验 `target_ifaces[]` 是否覆盖真实路径。

### 1.3 阶段一的快速判断（基于快照文件）

优先回答以下问题（对应文件见括号）：

- **接口是否异常**：目标接口是否 `DOWN/NO-CARRIER`、丢包/错误计数是否异常增长（`ip_link_stats.txt`，以及可选的 `iface_<iface>_details.txt`）。  
- **路由是否异常**：是否缺少默认路由/关键网段路由，是否存在黑洞路由或错误掩码（`ip_route_main.txt`、`ip_route_all.txt`、`ip_rule.txt`，可选 `route_get_<dest>.txt`）。  
- **邻居/ARP 是否异常**：是否存在邻居表异常、网关 MAC 抖动迹象（`ip_neigh.txt`）。  
- **本机是否存在重复 MAC**：查看 `mac_duplicate_check.txt` 是否出现 `DUP_MAC <mac> <iface...>`（该项为必查，但不强制作为最高优先级）。  
- **本机 IP 是否冲突**：查看 `ip_conflict_check.txt`，重点关注 `POTENTIAL_CONFLICT_OR_CHECK_FAILED` 与 `arping` 输出中的 `reply received` 提示。  
- **conntrack/防火墙是否异常**：是否出现 `nf_conntrack` 相关异常，规则是否大量命中（`conntrack_count.txt`、`firewall_iptables.txt`、`firewall_nft.txt`）。  
- **DNS 是否明显错误**：`/etc/resolv.conf` 是否异常、解析链路配置是否可疑（`dns_resolv_conf.txt`、`dns_nsswitch.txt`）。  
- **内核日志是否有关键告警**：是否出现网卡/驱动/邻居表/conntrack 等关键报错（`dmesg_tail_300.txt`、`journal_k_tail_300.txt`）。  

若阶段一已能得到高置信度结论（例如：链路断、路由缺失/黑洞、neighbor/conntrack 打满、明显 DNS 配置错误），可直接给出初步结论与修复建议并早停；否则进入阶段二分支诊断。

## 二、阶段二：按层级分支诊断

在阶段一未得到明确根因时，根据现象与初步发现，选择以下分支（可多选）继续：

### 2.1 L1-L2 分支：物理链路 / MAC / ARP / VLAN

**适用场景：**

- 目标接口错误/丢包计数异常增加；  
- 近期存在 `NIC Up/Down` 日志；  
- 无法 ARP 到网关或同网段主机。

**建议检查：**

- `ethtool <app_iface>`：查看速率、双工、链路是否稳定。  
- `ip neigh show` / `ip neigh get <gw>`：观察网关 ARP 是否存在抖动或解析失败。  
- 全局检查本机重复 MAC：查看 `mac_duplicate_check.txt`（或现场执行 `ip -o link` 聚合），确认是否存在两个接口使用同一 MAC。  
- VLAN 场景：  
  - `cat /proc/net/vlan/config`  
  - `ip -d link show <vlan_iface>`：确认 VLAN ID 与计划一致。

**潜在结论：**

- 物理链路故障或抖动；  
- MAC/IP 冲突；  
- ARP/邻居表溢出；  
- VLAN ID/Trunk/Access 端口配置错误。

### 2.2 L3 分支：路由 / 多出口 / 策略路由

**适用场景：**

- 只影响部分网段或外部网络；  
- 存在策略路由、多路由表或多出口。

**建议检查：**

- `ip rule show`：是否存在策略路由规则。  
- `ip route show table all`：检查是否配置错误/黑洞路由。  
- 对关键目标执行 `ip route get <dest_ip>`：确认实际出接口和下一跳是否合理。

### 2.3 DNS 分支：解析故障或延迟

**适用场景：**

- “域名访问慢/失败，但 IP 访问相对正常”。

**建议检查：**

- 使用 `dig` 或 `nslookup`：
  - 比较 `dig <domain>` 与 `dig @<nameserver> <domain>` 的解析时延和结果；  
  - 分别对多个 nameserver 进行测试。

### 2.4 L4 分支：端口 / 防火墙 / conntrack

**适用场景：**

- `ping` 正常但端口连接不通或不稳定；  
- 连接状态中，`SYN-RECV` 异常偏多。

**建议检查：**

- `nc -zv <target_ip> <port>`：本机对端口的连通性。  
- `ss -lntp`：确认服务是否监听在业务 IP 上。  
- `iptables -L -n -v` / `nft list ruleset`：检查是否有规则大量命中。  
- `conntrack -L | wc -l` 或日志：判断连接跟踪是否达到上限。

### 2.5 MTU / 性能分支：大包问题与时延

**适用场景：**

- 小包通信正常，文件传输/HTTPS 等大包或长连接不稳定。

**建议检查：**

- `ping -M do -s <size> <dest_ip>`：递增数据包大小，查找最大无分片包。  
- 检查 `ip link show <app_iface>` 和上游设备的 MTU 设置。

## 三、阶段三：深入诊断与根因分析（RCA）

当问题层级和大类清晰后，进入第三阶段，重点是：

1. **验证当前假设**：通过更多证据支持或推翻已形成的判断。  
2. **重建因果与时间链**：弄清楚“为什么出问题、如何演变、影响到哪里”。  
3. **形成标准化故障报告**，便于复盘和经验沉淀。

### 3.1 深入分析动作

可根据情况选择部分操作，例如：

- 使用 `mtr --report <target>` 或 `traceroute` 分析哪一跳开始丢包/时延激增。  
- 使用 `curl -Iv <URL>` 分解 DNS/TCP/TLS/应用耗时。  
- 在其他同网段/同机房机器上做相同测试，判断是否为“单机问题”。  
- 拉取更长时间窗口日志，分析是否存在“预兆”或渐进式恶化。

### 3.2 故障报告模板（建议结构）

在完成分析后，故障报告请统一按以下最终格式输出：

## 1. 总结

| 项目 | 内容 |
| ---- | ---- |
| 故障时间 | <开始时间-结束时间，持续时长> |
| 影响范围 | <受影响服务/功能/用户范围> |
| 根因 | <一句话根因结论> |
| 等级 | <严重/高/中/低> |

## 2. 故障路径分析

使用单行路径链路描述：

```text
<节点A> -> <中间故障节点> -> <上游影响> -> <用户侧影响>
```

并补充三项说明：

- **触发点**：最初触发故障的关键事件/配置/资源瓶颈。  
- **核心节点**：造成故障放大的中间节点（例如连接池耗尽、路由黑洞、接口 flap）。  
- **最终影响**：用户或业务最终可见的异常。  


## 3. 故障排查过程

按时间顺序列出排查步骤，建议 3~6 步，每步包含：

1. 执行了什么检查（命令/脚本/日志来源）  
2. 看到了什么关键现象  
3. 由此得出的阶段性判断

示例结构：

1. 收集用户反馈与系统日志，确认故障时间段。  
2. 检查连接状态与路由，发现关键异常信号。  
3. 结合阶段二/阶段三证据，定位核心故障节点。  
4. 回溯配置/容量/时序，确认根因。  

## 4. 修复建议

分三层给出建议：

1. **立即修复**：用于快速止血与恢复服务。  
2. **根本解决**：针对根因的配置/架构/容量优化。  
3. **预防措施**：监控告警、巡检、压测、变更流程优化等防复发措施。

## 附录：常用深入诊断命令

> 本附录列出在阶段三中常用的深入排查命令，按层级分类，供需要“多走一步”时快速查阅。实际使用时，可结合现场环境和权限选择执行。

### A.1 L1-L2 深入：链路 / MAC / ARP / VLAN

- **更长时间窗口日志**  
  - `dmesg` / `journalctl -k`  
    - 链路 Up/Down 是否与报障时间吻合？
- **多点对比**  
  - 在同 VLAN 其他主机上执行 `ping` / `arp` / `mtr`，对比“单机 vs 整段 VLAN 问题”。  
- **针对性验证**  
  - `arping -D -I <app_iface> <ip>`：检测 IP 冲突；  
  - 反复执行 `ip neigh get <gw>`：观察 MAC 是否抖动；  
  - VLAN ID 与交换机配置对齐（需要配合网络侧信息确认）。

### A.2 L3 深入：路由 / 策略路由 / 回程路径

- **可达性矩阵**  
  - 选取若干关键目标（如数据库、外网、跨机房 IP），分别执行：  
    - `ip route get <dest>`  
    - `ping <dest>`  
- **策略路由模拟**  
  - 若存在 `ip rule`，使用不同源 IP/mark 多次执行 `ip route get <dest>` 验证策略行为。  
- **路径对称性检查**  
  - 若用户提供对端信息，让对端执行相反方向的 `ip route get <src>` / `ping <src>`，判断回程路径是否不对称。

### A.3 L3.5 / L4-L7 深入：路径质量 / MTU / 应用分层

- **路由与路径质量**  
  - `mtr --report <target>`：找出从哪一跳开始丢包/RTT 抖动。  
- **MTU / 分片探测**  
  - 系统性使用 `ping -M do -s <size>` 逐步探测最大无分片包。  
- **TCP/TLS/HTTP 分解**  
  - `curl -Iv <url>`：拆解 DNS、TCP 建连、TLS 握手、首字节时间（TTFB），区分“网络慢”还是“应用慢”。  
- **服务端深入**  
  - `ss -lntp`：监听 IP/端口是否正确；  
  - 结合应用/Nginx/中间件日志，看 4xx/5xx/超时/限流等模式是否与网络现象对应。

---

通过以上三阶段流程以及附录中的深入命令，本技能能帮助工程师系统化地排查网络故障，从“能否连通”一路深入到“具体哪一层、哪个组件、什么配置/事件导致问题”，并沉淀成标准化的根因分析报告，支持后续复盘与经验积累。
