# 离线网络硬件故障诊断

本技能通过分析从服务器收集的标准日志文件，帮助诊断 EulerOS 网络硬件故障。

## ⚠️ 强制执行流程

**必须严格按以下顺序执行，禁止跳过或乱序：**

```
Step 0 (故障日志采集) → Step 1 (场景分类) → Step 2 (深入分析) → Step 3 (根因校验) → Step 4 (生成报告)
```

**执行规则：**
1. **顺序强制**：必须完成当前步骤并验证通过后，才能进入下一步
2. **场景分支**：Step 1 输出场景标签后，Step 2 必须执行对应的专项分析脚本
3. **数据校验**：Step 3 必须通过证据矩阵校验后才能生成最终报告
4. **文件适配**：日志文件不全时自动降级分析策略，但必须至少有一个日志文件

**每步完成标志：**
- Step 0：输出日志文件时间范围、文件统计、错误关键词概览
- Step 1：确定故障场景（如 NIC_HARDWARE_FAILURE 等）
- Step 2：输出物理级精准定位、传导链及初步根因
- Step 3：输出根因证据校验表、原生日志证据及置信度定性
- Step 4：生成完整的诊断报告文件（.md）

**执行命令**：

**目标**：根据全量扫描结果和用户提供的过滤条件，使用 `grep` / `less` 等文件操作命令查看具体的原始日志上下文获取更细粒度的故障信息。

## Step 1：场景分类

根据 Step 0 采集的日志概览，分析故障现象并确定故障场景类型。

### 场景分类概述

网络硬件故障主要分为以下六种场景类型：

| 场景标签 | 中文描述 | 主要特征 |
|---------|---------|----------|
| `NIC_HARDWARE_FAILURE` | 网卡硬件故障 | iBMC SEL报告硬件错误、PCIe 致命错误、网卡热插拔、温度异常 |
| `DRIVER_ISSUE` | 驱动/固件问题 | 内核日志出现网卡驱动 Panic、固件加载失败、驱动版本不匹配 |
| `LINK_DOWN` | 物理链路故障 | 网口 Link Down、载波丢失、Bond 网卡发生主备切换 |
| `PERFORMANCE_DEGRADATION` | 性能下降/丢包 | 网络丢包/错包/乱序、延时大/抖动、网络拥塞/广播风暴 |
| `INTERRUPT_ERROR` | 中断/调度错误 | 网卡中断负载极化、MSI/MSI-X 配置失败、中断风暴 |
| `CONFIG_ERROR` | 配置/协议错误 | IP冲突、路由错误、VLAN不当、MTU不一致、网卡乱序 |

### 场景 → 根因假设矩阵

确定场景标签后，**必须从以下矩阵中选取 2~3 个候选根因假设**，并在 Step 2 中逐一验证：

| 场景标签 | 候选根因假设（需在 Step 2 中验证） |
|---------|----------------------------------|
| `NIC_HARDWARE_FAILURE` | ① 网卡芯片物理损坏 ② PCIe 插槽接触不良 ③ 网卡热插拔事件引发的设备重枚举 |
| `DRIVER_ISSUE` | ① 驱动版本与内核不兼容 ② 固件(Firmware)文件缺失或损坏 ③ 驱动代码 Bug 导致的 Panic |
| `LINK_DOWN` | ① 网线/光模块物理损坏 ② 对端交换机端口故障 ③ Bond 主从网卡切换（MII/ARP 探测失效） |
| `PERFORMANCE_DEGRADATION` | ① 物理链路干扰(CRC/FCS错包) ② 网络环路(STP失效)诱发广播风暴 ③ 转发节点拥塞 |
| `INTERRUPT_ERROR` | ① 中断亲和性配置不当(极化负载) ② MSI-X 初始化失败回退 ③ 驱动中断风暴 |
| `CONFIG_ERROR` | ① MTU 设置不一致导致大包丢弃 ② udev 规则缺失导致网卡名乱序 ③ 网络地址冲突 |

> ⚠️ **强制要求**：Step 2 分析结束后，必须对上述候选根因逐一标注：✅ 已证实 / ❌ 已排除 / ❓ 证据不足

**Step 1 完成标志：**
1. ✅ 确定主要故障场景标签（从上述类型中选择）
2. ✅ 记录故障现象与关键证据
3. ✅ 为Step 2深入分析提供明确的故障场景方向

## Step 2：深入分析

根据 Step 1 的场景分类结果，必须**首先完成时序关联与故障传导链重建**，然后再通过通用或专项脚本收集对应证据，最终给出精确的物理坐标定位。

### 2.1 时序关联与传导链重建 (核心理论框架)

**目标**：通过多源日志的时间戳对齐，重建故障发生的完整时间轴，厘清事件的先后顺序与因果链，为根因定位提供时序证据。

#### 2.1.1 确定 网络故障 零点 (T0)

故障零点（T0）是时序分析的基准锚点，定义为**最早可观测到异常的时间戳**。确定优先级（由高到低）：

| 优先级 | 来源 | 说明 |
|----|----|----|
| **P1** | 硬件错误日志（iBMC / SEL） | 最底层的致命报错（如 PCIe Fatal, NIC failure, Temp Critical），时间点最准确。 |
| **P2** | 内核感知层（`dmesg`） | 最早出现的 PCIe AER 错误、驱动挂死 (TX hang) 或接口初始化失败。 |
| **P3** | 系统调度层（`syslog` / `messages`） | `Link is Down`, `carrier lost`, 或 `IP conflict` 等系统级异常事件。 |
| **P4** | 应用感知层 | 业务心跳丢失、响应时间突增或算力同步失败，通常滞后最大。 |

> ⚠️ **时钟偏差处理**：多节点或异构日志源场景下，需留意 iBMC 时间与 OS 时间（NTP）是否存在时钟偏移。多源对齐时需留意并修正该偏差量。

#### 2.1.2 多维日志对齐与时间轴矩阵

以 T0 为基准，将 iBMC 传感器读数、dmesg 报错、配置状态和 OS 日志统一映射到绝对时间轴上，构建**事件序列矩阵**。
*示例：因 PCIe 错误导致的网卡重置时间轴*
```text
T0-10m  ├─ [InfoCollect] 监测到网卡纠错计数 (CRC error) 缓慢上升。
T0-1m   ├─ [iBMC SEL]    检测到 PCIe 链路修正错误告警。
T0      ├─ [OS dmesg]    `pcieport 0000:00:01.0: AER: Uncorrected (Fatal) error` → 标定为故障发生零点 T0。
T0+1s   ├─ [OS dmesg]    `ixgbe 0000:01:00.0: Reset adapter` (驱动开始重置)。
T0+2s   ├─ [OS messages] `eth0: link down` (业务网络连接中断)。
```

#### 2.1.3 网络故障传导链推断

结合对齐的时间轴矩阵，运用以下规则推导故障传导链方向：
- **规则一：底层向上传导（硬件/驱动主导）**
  - *特征*：底层的 PCIe 链路错误早于 Link Down 记录。
  - *传导链*：插槽接触不良 → 触发 PCIe AER 错误（根因） → 驱动侦测到硬件状态异常 (表象1) → 操作系统执行 Reset 适配器 (表象2) → 链路临时中断 (结果)。
- **规则二：环境向硬件传导（热管理主导）**
  - *特征*：iBMC 温度告警先行，伴随性能波动，最后驱动报错。
  - *传导链*：机柜散热失效（根因） → 网卡高负载积热 → 触发温度阈值 (T0) → 硬件降频/报错 → 业务丢包 (结果)。
- **规则三：对端向本地传导（外部因素主导）**
  - *特征*：本端仅记录载波丢失 (Carrier Lost)，而 iBMC 和物理硬件极度干净。
  - *传导链*：对端交换机端口变动/网线物理损坏（根因） → 物理电气信号消失 (T0) → OS 感知到 Link Down → 业务超时。

> ⚠️ **精确定位强制要求**：在网络诊断中，**严禁仅使用“网卡故障”这类含糊结论。**
> 必须通过证据追踪到细粒度的物理/逻辑坐标定位，例如：
> - ✅ 正确结论：`PCIe 0000:03:00.0 (eth0) 因 CRC 错误过高触发 CRC 风暴` 或是 `SFP 模块波长不匹配导致 Rx 功率过低`。
> - ❌ 错误结论：`发生网络错误` 或仅仅说是 `eth0 坏了`。

### 2.2 日志脚本分析执行 (执行工具动作)

#### 2.2.1 通用分析流程

通用分析流程适用于所有网络硬件故障场景，提供基础的日志提取与数据分析能力：

```bash
# iBMC 日志分析（硬件层）
python3 scripts/diagnose_ibmc.py <log_dir> [选项]

# InfoCollect 日志分析（系统信息层）
python3 scripts/diagnose_infocollect.py <log_dir> [选项]

# OS Messages 日志分析（操作系统层）
python3 scripts/diagnose_messages.py <log_dir> [选项]
```

**通用分析执行策略**：
1. **顺序执行**：建议按硬件层→系统信息层→操作系统层的顺序执行分析
2. **参数调整**：根据Step 0的输出结果，调整时间范围、关键词等参数
3. **结果整合**：将不同来源的分析结果整合，形成完整的故障视图

#### 2.2.2 按场景专项分析

当Step 1确定故障场景后，优先使用对应的专项分析流程。详细的专项分析指南请参考：

- [网络故障场景专项分析指南](references/network_scenario_analysis.md)

**专项分析包含以下六种场景**：
1. **网卡硬件故障分析** (NIC_HARDWARE_FAILURE)
2. **驱动/固件问题分析** (DRIVER_ISSUE)
3. **物理链路故障分析** (LINK_DOWN)
4. **性能下降/丢包分析** (PERFORMANCE_DEGRADATION)
5. **中断/调度错误分析** (INTERRUPT_ERROR)
6. **配置/协议错误分析** (CONFIG_ERROR)

**专项分析执行策略**：
1. **场景匹配**：根据Step 1确定的场景标签，选择对应的专项分析流程
2. **参考指南**：按照专项分析指南中的步骤执行
3. **专用参数**：使用场景专用的分析命令和参数
4. **根因验证**：使用根因假设矩阵进行根因验证

#### 2.2.3 分析执行原则

1. **场景优先原则**：当故障现象明确匹配某个场景时，优先使用专项分析
2. **通用备用原则**：当故障现象不明确或不符合任何专项场景时，使用通用分析
3. **组合使用原则**：可以同时使用专项分析和通用分析，相互验证结果
4. **逐步深入原则**：从概览分析开始，逐步深入具体问题

**Step 2 完成标志**：
1. ✅ 输出故障零点 T0 的精确时间戳及其所依托的具体日志行。
2. ✅ 梳理出以 T0 为基准的结构化事件序列矩阵与至少 3 步的确定故障传导链。
3. ✅ 给出精确到物理部件/逻辑端口的细粒度定位结果。

## Step 3：根因反思与证据双向校验

**目标**：对 Step 2 输出的“初步传导链与定位结果”进行“交叉质询”，确保得出的最终结论 100% 由底层日志支撑，防范分析过程中脱离实际日志记录的发散性推断。本阶段是确立最终诊断结论的“防御门槛”。

### 3.1 交叉质询铁律 (Cross-Examination Rules)

规定分析输出最终结论前，必须遵循以下三条铁律对 Step 2 的结果进行自我质询：
1. **孤证不立原则**：任何一个最终的物理级故障结论（如 网卡损坏、对端交换机故障），绝对不能仅凭系统层的一条报错（如 Link Down 或 丢包严重）就下断言。**必须**同时找到硬件基板（如 iBMC / SEL）或内核底层（如 PCIe 寄存器记录、ethtool 状态）的第二独立证据源支撑。若无底层证据支撑，只能定性为“疑似故障”或“环境波动”。
2. **逻辑闭环原则**：从 T0（故障零点）到最终业务故障结果，中间的传导链不允许出现跳跃性结论。例如：`发现网卡温度略高`不能直接跳跃推断导致`协议栈丢包`。如果两端现象同时出现但无法建立合乎科学原理的因果桥梁，则说明这可能是彼此独立的异常，或者根源推断方向发生错误。
3. **互斥排异原则**：如果判定故障是 A 原因主导，那么必须主动去查证与之互斥的 B 模块日志是否“干净”。例如，若推断结论是纯粹的“网线物理故障”，则必须反向验证本地网卡自诊断正常，绝不能在日志中出现“PCIe Fatal Error”；若有违背，则“单纯网线故障”假设被推翻。

### 3.2 强制：根因证据校验表 (Evidence Validation Matrix)

在确认最终结论并进入撰写报告环节前，强制要求进行独立对照梳理，且**每一项检查都必须强制附带对应的真实原生日志片段截取**，否则视作校验不通过：

| 校验维度 | 校验标准要求 | 强制证据格式（分析打样要求） |
| :--- | :--- | :--- |
| **E1: 时序连续性** | 从结果向故障零点(T0)回溯，序列是否存在无法解释的空白期？ | `[✅/❌ 结果]` + `时序计算说明` + `相邻事件的原生日志片段关联` |
| **E2: 物理同一性** | 各级日志（如 OS层报 eth0，和 iBMC 层报 NIC1）指控的设备坐标（PCIe BDF / MAC / Name），映射后是否确实是真实的、同一个物理部件单元？ | `[✅/❌ 结果]` + `系统层接口名与物理层物理 ID 的对应关系梳理日志` |
| **E3: 现象排他性** | 导致该报错的最终层级链路中，是否存在其他未被完全排除的平行底层因素（如对端配置更改）？ | `[✅/❌ 结果]` + `主动寻找并排除相关平行干扰因素的说明` |

### 3.3 结论防发散拦截机制 (Anti-Hallucination Mechanism)

针对上述证据审查过程发现不通过的情况，制定硬性拦截退回与评级降级规范：

*   **断链阻断**：如果在前置证据校验表中存在 `[❌ 冲突]` ，或是无法从日志堆中**找到任何能证明因果传导的日志片段**，则视为假想传导链无效，**强制触发流程拦截，需回溯重新收集或判定**。
*   **降级处分**：大模型或人员不得依托已有知识强行缝合残缺证据。如果在客观上确实缺乏某一层（比如缺失了 iBMC 的底层支持）的关键日志，导致核心环节断裂，在此种情况下，必须将最终呈现给用户的异常归归因为**“存在多重并行可能性”**或**“高度疑似 (Suspected)”**状态。在此，必须在最终诊断处高亮警示：“由于缺乏 XXX 维度的日志，故障判定传导链在 XXX 处断裂，暂时无法得出唯一明确性判定。”
*   **严禁用词限制**：在证据链未能满足完全逻辑校验闭环的标准前，诊断文书及对质交互中**绝对严禁**出现诸如“肯定”、“必然”、“绝对是 XXX 的直接毁坏”等发散式、决定性断言词汇。

**Step 3 完成标志（防发散质询门槛）**：
1. ✅ 高度结构化地产出《根因证据校验表》中包含的每一个三维质询的自查结论。
2. ✅ 每个标记为通过（✅）的自查项，均强制提取并附带截取了原生日志记录中的 Timestamp 和 原文 Text 以便二次佐证。
3. ✅ 基于自查的客观事实依据，对当前的证据链有效性进行状态声明定性（分为：完全闭环 / 确实存在断层）。
4. ✅ 基于实际掌握的强关联证据链集合，输出与之匹配等位置信度（已明确证实 / 单一疑似判定 / 多重交织未知原因）的严谨最终诊断研判方向。

## Step 4：生成报告

汇总 Step 0～3 的所有分析结果，生成结构化诊断报告：

```bash
bash scripts/generate_report.sh \
    --analysis /tmp/network_analysis_results.json \
    --output ./network_diagnosis_report.md
```

**报告结构：**

1. **Executive Summary（故障摘要）** — 故障场景、根本原因、修复建议概述
2. **Technical Analysis（技术分析）** — 日志文件概览、故障现象、故障机理、证据链（E1/E2/E3...）
3. **Root Cause（根本原因）** — 直接原因 + 根本原因 + 5 Whys 分析
4. **Recommendations（修复建议）** — 立即 / 短期 / 中期 / 长期修复措施
5. **风险评估** — 业务中断、数据丢包、复发风险评估
6. **最终验证清单** — 确认分析足够深入的检查清单
7. **附录** — 关键日志片段与相关命令参考

**根因具体性要求（笼统描述视为分析不足）：**

| ❌ 笼统 | ✅ 具体 |
|--------|--------|
| "网卡坏了" | "Intel X710 网卡 (PCIe 03:00.0) 内部控制器触发 Fatal Error 导致 PCIe 链路 Down" |
| "链路异常" | "由于 SFP 模块与交换机端口波长不匹配 (850nm vs 1310nm)，导致 Rx 功率过低触发 Link Down" |
| "丢包严重" | "网卡 receive_errors 指标持续增长，伴随大量 CRC 错误，指向网线/光口物理链路干扰" |

**根因推理完成性检查（调用 `generate_report.sh` 前必须通过）：**

在调用 `./scripts/generate_report.sh` 生成报告框架之前，必须能够回答以下所有问题：

- [ ] 根因是否具体到：**网卡标识**（接口名/BDF号）+ **错误类型**（硬件损坏/驱动异常/配置错误/物理链路）+ **触发条件**（负载/时间/环境）？
- [ ] Step 2 矩阵中所有候选根因是否已完成 ✅/❌/❓ 标注？
- [ ] 是否能描述从"根因"到"最终症状"的完整因果链条（至少 3 层，例：光模块老老化 → Rx 功率下降 → CRC 错误率激增 → 触发重传丢包 → 业务性能下降）？
- [ ] 是否排除了至少一个"相似但非真正根因"的情况（即做过鉴别诊断，如通过排除本端硬件报错来证实驱动 BUG）？

> ⚠️ **若有任何未通过项，必须返回 Step 2 继续分析（追加关键词或缩小时间范围），而非直接填写报告模板。**

## 分析原则

0. **根因优先**：诊断的最终目标是**定位根因（Root Cause）**，而非仅描述症状。每个分析步骤都应推进"为什么会发生"的答案，而非停留在"发生了什么"。症状描述（如"载波丢失"）只是中间过程，根因（如"对端交换机端口异常"）才是终点。
1. **硬件优先**：优先排查物理层和硬件报错，确认非外部环境或对端设备引起
2. **证据驱动**：每个结论必须有日志数据支撑，无数据则标注"待验证假设"
3. **配置核对**：特别是网络互通性问题，必须核对比对端配置、驱动版本、MTU 等
4. **风险评估**：评估修复操作对系统的影响，优先选择保守方案
5. **反思验证**：通过假设驱动分析和跨层反思，确保根因结论的严谨性
6. **离线分析**：本 Skill 仅基于日志文件进行分析，不执行任何在线系统命令
