# 离线内存故障诊断

本技能通过分析从服务器收集的标准日志文件，帮助诊断 EulerOS 内存相关故障。

## 输入日志目录结构与对应诊断脚本

以 `/path/to/logs/xxxx` 为例，标准的服务器日志收集包通常具有以下层级结构。本技能提供了针对性的脚本来分析不同层级的日志。

> **注意**：在实际场景中，用户提供的日志包可能不完整，可能仅包含以下三种目录中的一种或多种。请根据实际存在的日志类型灵活选择对应的分析脚本。

```text

```

## ⚠️ 强制执行流程

**必须严格按以下顺序执行，禁止跳过或乱序：**

```
Step 0 (故障日志采集) → Step 1 (场景分类) → Step 2 (深入分析) → Step 3 (根因校验) → Step 4 (生成报告)
```

**执行规则：**
1. **顺序强制**：必须完成当前步骤并验证通过后，才能进入下一步
2. **场景分支**：Step 1 输出场景标签后，Step 2 必须执行对应的专项分析脚本
3. **数据校验**：Step 3 必须通过证据矩阵校验后才能生成最终报告
4. **文件适配**：日志文件不全时自动降级分析策略，但必须至少有一个日志文件

**每步完成标志：**
- Step 0：输出日志文件时间范围、文件统计、错误关键词概览
- Step 1：确定故障场景（如 MEMORY_ECC_ERROR 等）
- Step 2：输出物理级精准定位（如 DIMM 插槽）、传导链及初步根因
- Step 3：输出根因证据校验表、原生日志证据及置信度定性
- Step 4：生成完整的诊断报告文件（.md）

**目标**：快速扫描所有日志文件，识别异常模块和关键报错，建立故障全景视图。

**执行命令**：
```bash
python3 scripts/diagnose_summary.py <log_dir> -o
```

**目标**：根据全量扫描结果和用户提供的过滤条件，使用 `grep` / `less` 等文件操作命令查看具体的原始日志上下文获取更细粒度的故障信息。

## Step 1：场景分类

根据 Step 0 采集的日志概览，分析故障现象并确定故障场景类型。

### 场景分类概述

内存故障主要分为以下七种场景类型：

| 场景标签 | 中文描述 | 主要特征 |
|---------|---------|----------|
| `MEMORY_ECC_ERROR` | 内存ECC错误 | iBMC SEL报告ECC错误、Correctable/Uncorrectable、MCE记录 |
| `MEMORY_OOM_KILLER` | 内存不足(OOM) | 系统日志出现 Out of memory、OOM killer 被调用、进程被杀 |
| `MEMORY_LEAK` | 内存泄漏 | 内存使用持续增长、Slab/Cache 异常增大且无法回收 |
| `MEMORY_CORRUPTION` | 内存损坏 | 内核报告 memory corruption、segfault、page fault |
| `MEMORY_PERFORMANCE` | 内存性能问题 | swap使用率高、NUMA访问延迟大、内存带宽受限 |
| `MEMORY_HARDWARE_FAILURE` | 内存硬件故障 | DIMM 在位丢失、SPD读取错误、内存初始化失败 |
| `MEMORY_CONFIG_ISSUE` | 内存配置不当 | 频率不匹配、双通道配置错误、NUMA配置偏差 |

### 场景 → 根因假设矩阵

确定场景标签后，**必须从以下矩阵中选取 2~3 个候选根因假设**，并在 Step 2 中逐一验证：

| 场景标签 | 候选根因假设（需在 Step 2 中验证） |
|---------|----------------------------------|
| `MEMORY_ECC_ERROR` | ① 内存颗粒物理老化 (GPIO CE/UCE) ② BIOS 隔离机制触发 (GPIO FATAL) ③ 内核 hwpoison 页面下线 (Idle UCE) ④ 进程受损被杀 (Used UCE SIGBUS) |
| `MEMORY_OOM_KILLER` | ① 业务负载突增超过预留内存 ② 应用程序/驱动存在内存泄漏 ③ 内存分配碎片化严重 |
| `MEMORY_LEAK` | ① 指定进程（如Java/Nginx）存在泄露 ② 内核 Slab 泄露（kmemleak） ③ 巨页/缓存未回收 |
| `MEMORY_CORRUPTION` | ① 硬件 UCE 导致的位反转 ② 内核/驱动 Bug 导致的指针越界 ③ 超频/电压不稳定 |
| `MEMORY_PERFORMANCE` | ① NUMA 配置偏差导致频繁跨 Node 访问 ② Swap 交换过于频繁（thrashing） ③ 内存总线负载过高 |
| `MEMORY_HARDWARE_FAILURE` | ① 内存条物理损坏/烧毁 ② 主板内存插槽电路故障 ③ 硬件兼容性问题 |
| `MEMORY_CONFIG_ISSUE` | ① BIOS/UEFI 配置错误 ② 内存条混插/位置不匹配 ③ 电源管理策略干扰 |

> ⚠️ **强制要求**：Step 2 分析结束后，必须对上述候选根因逐一标注：✅ 已证实 / ❌ 已排除 / ❓ 证据不足

**Step 1 完成标志：**
1. ✅ 确定主要故障场景标签（从上述类型中选择）
2. ✅ 记录故障现象与关键证据
3. ✅ 为Step 2深入分析提供明确的故障场景方向

## Step 2：深入分析

根据 Step 1 的场景分类结果，必须**首先完成时序关联与故障传导链重建**，然后再通过核心脚本收集对应证据，最终给出精确的维度定位。

### 2.1 时序关联与传导链重建 (核心理论框架)

**目标**：通过多源日志的时间戳对齐，重建故障发生的完整时间轴，厘清事件的先后顺序与因果链，为根因定位提供时序证据。

#### 2.1.1 确定内存故障零点 (T0)

故障零点（T0）是时序分析的基准锚点，定义为**最早可观测到异常的时间戳**。确定优先级（由高到低）：

| 优先级 | 来源 | 说明 |
|----|----|----|
| **P1** | 硬件错误日志（iBMC / SEL） | 最底层的 ECC、DIMM 状态报错，时间点最准确（精确到秒或毫秒）。 |
| **P2** | 内核感知层（`dmesg` / `mcelog`） | 最早出现的 MCE（机器检查异常）、EDAC 报错或内存分配失败计数开始升高的时间点。 |
| **P3** | 系统调度层（`syslog` / `messages`） | `Out of Memory (OOM)` 触发、Swap 激增开始或大量进程段错误 (Segfault) 系统记录。 |
| **P4** | 应用感知层 | 业务响应延迟上升、GC 频繁（针对 Java）、或是应用层捕获的内存分配异常。 |

#### 2.1.2 多维日志对齐与时间轴矩阵

以 T0 为基准，将 iBMC 传感器读数、dmesg 报错、进程内存快照和 OS 日志统一映射到绝对时间轴上，构建**事件序列矩阵**。
*示例：因内存记录 UCE 导致的系统宕机时间轴*
```text
T0-2h   ├─ [OS dmesg]    `EDAC MC0: 1 CE on DIMM_A1` (监测到零星的可纠错错误)。
T0-10m  ├─ [iBMC SEL]    检测到内存 CE 严重告警 (Correctable error, logging limit reached)。
T0-1s   ├─ [OS dmesg]    `Uncorrected error detected at 0x12345678` -> `Machine Check Exception`。
T0      ├─ [iBMC SEL]    记录 `Memory UCE error` 硬件日志或 `CATERR` → 标定为故障发生零点 T0。
```

#### 2.1.3 内存专属故障传导链推断

结合对齐的时间轴矩阵，运用以下规则推导故障传导链方向：
- **规则一：层级自下而上（硬件损坏主导）**
  - *特征*：物理 ECC 错误早于操作系统 Panic 或段错误。
  - *传导链*：DIMM 物理颗粒失效 (T0) → 触发 ECC 中断举报 → OS 层尝试纠错失败 (UCE) → 最终引发关键系统服务挂起或系统重启。
- **规则二：环境向资源传导（泄漏/负载主导）**
  - *特征*：业务量升高或运行时间增长，内存可用率线性下降，伴随 Swap 活跃和最终的 OOM。
  - *传导链*：业务负载/漏洞 (根因) → 内存逐级耗竭 → OS 触发 Swap 换入换出 (T0) → IO 等待升高引起性能瘫痪 → 触发 OOM Killer 排空关键进程 (结果)。
- **规则三：软硬件死锁（配置/微码主导）**
  - *特征*：底层硬件检测正常，但特定工作负载下发生内存访问冲突或总线锁定。
  - *传导链*：NUMA 不均衡配置/硬件预取 Bug → 跨区域内存访问冲突 → 触发 CPU 调度死锁或内存访问违例。

> ⚠️ **精确定位强制要求**：在内存诊断中，**严禁仅使用“内存故障”这类含糊结论。**
> 必须追踪到细粒度的坐标定位，例如：
> - ✅ 正确结论：`DIMM 010 (Socket 0, Channel A) 第 3 颗粒出现单比特翻转 CE 累积` 或 `PID 4567 (java) 进程因 JVM Heap 泄漏导致系统 OOM`。
> - ❌ 错误结论：`发生内存报错` 或仅仅说是 `内存坏了`。

## Step 3：根因反思与证据双向校验

**目标**：对 Step 2 输出的“初步传导链与定位结果”进行“交叉质询”，确保得出的最终结论 100% 由底层日志支撑，防范分析过程中脱离实际日志记录的发散性推断。

### 3.1 交叉质询铁律 (Cross-Examination Rules)

1. **孤证不立原则**：物理级故障结论（如 DIMM 损坏），绝对不能仅凭系统层的一条报错（如 Segfault）就下断言。**必须**同时找到硬件基板（iBMC / SEL）或内核底层（MCE / EDAC）的第二独立证据源支撑。
2. **逻辑闭环原则**：从 T0 到最终业务故障，中间传导链不允许出现跳跃性结论。例如：`发现内存在负载高时有换入换出`不能直接跳跃推断导致`内存颗粒物理损坏`。
3. **互斥排异原则**：如果判定故障是内存泄漏引起，必须主动排除如“巨页配置不当”、“系统启动即存在的大规模非法内存占用”等互斥因素。

### 3.2 强制：根因证据校验表 (Evidence Validation Matrix)

在确认最终结论并进入撰写报告环节前，强制要求进行独立对照梳理：

| 校验维度 | 校验标准要求 | 强制证据格式（分析打样要求） |
| :--- | :--- | :--- |
| **E1: 时序连续性** | 从结果向故障零点(T0)回溯，序列是否存在无法解释的空白期？ | `[✅/❌ 结果]` + `时序计算说明` + `原生日志片段` |
| **E2: 物理/逻辑同一性**| 不同层级指控的设备坐标（如 OS 坐标 vs 硬件插槽），映射后是否確實是一个单元？ | `[✅/❌ 结果]` + `DIMM ID 与 物理 Socket/Channel 的映射关系梳理` |
| **E3: 现象排他性** | 导致该报错的最终层级链路中，是否存在其他未被完全排除的平行底层因素？ | `[✅/❌ 结果]` + `主动寻找并排除相关平行干扰因素的说明` |

### 3.3 结论防发散拦截机制 (Anti-Hallucination Mechanism)

针对上述证据审查过程发现不通过的情况，制定硬性拦截退回与评级降级规范：

*   **断链阻断**：如果在前置证据校验表中存在 `[❌ 冲突]` ，或是无法从日志堆中**找到任何能证明因果传导的日志片段**，则视为假想传导链无效，**强制触发流程拦截，需回溯重新收集或判定**。
*   **降级处分**：大模型或人员不得依托已有知识强行缝合残缺证据。如果在客观上确实缺乏某一层（比如缺失了 iBMC 的底层支持）的关键日志，导致核心环节断裂，在此种情况下，必须将最终呈现给用户的异常归归因为**“存在多重并行可能性”**或**“高度疑似 (Suspected)”**状态。在此，必须在最终诊断处高亮警示：“由于缺乏 XXX 维度的日志，故障判定传导链在 XXX 处断裂，暂时无法得出唯一明确性判定。”
*   **严禁用词限制**：在证据链未能满足完全逻辑校验闭环的标准前，诊断文书及对质交互中**绝对严禁**出现诸如“肯定”、“必然”、“绝对是 XXX 的直接毁坏”等发散式、决定性断言词汇。

**Step 3 完成标志（防发散质询门槛）**：
1. ✅ 高度结构化地产出《根因证据校验表》中包含的每一个三维质询的自查结论。
2. ✅ 每个标记为通过（✅）的自查项，均强制提取并附带截取了原生日志记录中的 Timestamp 和 原文 Text 以便二次佐证。
3. ✅ 基于自查的客观事实依据，对当前的证据链有效性进行状态声明定性（分为：完全闭环 / 确实存在断层）。
4. ✅ 基于实际掌握的强关联证据链集合，输出与之匹配等位置信度（已明确证实 / 单一疑似判定 / 多重交织未知原因）的严谨最终诊断研判方向。

## Step 4：生成报告

汇总 Step 0～3 的所有分析结果，生成结构化诊断报告：

```bash
bash scripts/generate_report.sh \
    --analysis /tmp/memory_analysis_results.json \
    --output ./memory_diagnosis_report.md
```

**报告结构：**

1. **Executive Summary（故障摘要）** — 故障场景、根本原因、修复建议概述
2. **Technical Analysis（技术分析）** — 日志文件概览、故障现象、故障机理、证据链（E1/E2/E3...）
3. **Root Cause（根本原因）** — 直接原因 + 根本原因 + 5 Whys 分析
4. **Recommendations（修复建议）** — 立即 / 短期 / 中期 / 长期修复措施
5. **风险评估** — 数据丢失、业务中断、复发风险评估
6. **最终验证清单** — 确认分析足够深入的检查清单
7. **附录** — 关键日志片段与相关命令参考

**根因具体性要求（笼统描述视为分析不足）：**

| ❌ 笼统 | ✅ 具体 |
|--------|--------|
| "内存坏了" | "DIMM 010 (Socket 0, Channel A) 第 3 颗粒出现不可纠错 UCE 错误导致系统重启" |
| "内存不足" | "PID 4567 (java) 进程因 JVM Heap 频繁 GC 导致系统各 CPU 核心负载升高并触发 OOM" |
| "内存配置不当" | "内存频率设置为 3200MHz 但混合使用了 2666MHz 的内存条，导致主板无法成功训练内存" |

**根因推理完成性检查（调用 `generate_report.sh` 前必须通过）：**

在调用 `./scripts/generate_report.sh` 生成报告框架之前，必须能够回答以下所有问题：

- [ ] 根因是否具体到：**DIMM/进程/Slab标识** + **错误类型**（CE/UCE/OOM/Leak） + **触发条件**（时间/负载/位置）？
- [ ] Step 2 矩阵中所有候选根因是否已完成 ✅/❌/❓ 标注？
- [ ] 是否能描述从"根因"到"最终症状"的完整因果链条（至少 3 层，例：内存泄漏 → 可用物理内存耗尽 → 触发 OOM Killer 排空进程）？
- [ ] 是否排除了至少一个"相似但非真正根因"的情况（即做过鉴别诊断）？

> ⚠️ **若有任何未通过项，必须返回 Step 2 继续分析（追加关键词或缩小时间范围），而非直接填写报告模板。**

## 分析原则

0. **根因优先**：诊断的最终目标是**定位根因（Root Cause）**，而非仅描述症状。每个分析步骤都应推进"为什么会发生"的答案，而非停留在"发生了什么"。症状描述（如"内存泄露"）只是中间过程，根因（如"java 进程堆配置不当"）才是终点。
1. **硬件优先**：优先排查 DIMM 物理状态，确认非硬件引发的 CE/UCE 风暴
2. **证据驱动**：每个结论必须由 100% 同源或交叉对齐的日志数据支撑，无数据则标注"待验证假设"
3. **时序敏感**：严格对齐 NTP 及硬件时钟偏移，防止时序错乱导致的误判
4. **风险评估**：评估修复操作对系统的影响，优先选择保守方案
5. **反思验证**：通过假设驱动分析和跨层反思，确保根因结论的严谨性
6. **离线分析**：本 Skill 仅基于日志文件进行分析，不执行任何在线系统操作
