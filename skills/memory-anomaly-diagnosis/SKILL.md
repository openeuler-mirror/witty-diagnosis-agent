# 内存异常诊断 (Memory Anomaly Diagnosis)

## 何时使用
> 当用户遇到以下场景时，应使用此技能：
- 当C/C++服务或代码出现内存故障类问题时
- 当需要使用strace和gdb查询内存变化根因时

## 核心指令 (Core Instructions)
> 加载skill后必须严格按照此skill的流程执行;- **当使用skill时，如果skill的流程里指定里使用工具或者脚本来完成操作，严格执行；涉及到执行skill里的脚本时，需要执行ansible将 **本地脚本** 远程执行到服务器上，参考指令: ansible all -i 7.53.28.15, -u root -m script -a '/scripts/start_monitor.sh' ，你需要在skill所在的本地路径下执行。你要把参考指令中的服务器ip、用户名和脚本路径替换成真实的。
> 诊断流程遵循 **顺序工作流 (Sequential Workflow)**，步骤间存在强依赖关系。分析阶段则涉及 **条件分支 (Conditional Branches)**，根据 GDB 输出内容决定分析路径。
> 故障注入：如果用户问题里明确自动触发故障，则你可以主动去触发故障；否则，必须等人为触发。

### 步骤 1：启动内存操作监控
**目标**：获取进程 PID，启动监控工具。
运行pidstat和strace监控内存变化，需要运行脚本 start_monitor.sh，必须要传入的参数有：服务名或进程，持续时间(如果用户没有指定则默认60秒)。参考示例：
```bash
# Usage: ./start_monitor.sh <target> <duration_seconds>
# Example: ./start_monitor.sh app_name 60
```
**操作**：
1.  执行上述命令。
2.  脚本会启动监控并告知用户。
3.  等待脚本运行结束（持续60秒）。

### 步骤 2：分析日志，获取内存关键信息
**目标**：分析日志，定位内存异常关键信息。在这个步骤中，函数名和内存变化趋势（或者固定增长的内存值）是必须找到的关键信息！！！这俩个信息将传给下一步分析。
**操作**：
1.  告知用户监控服务已启动。接着等待上一步的监控服务结束（取决于上一步指定的持续时间），然后开始分析。
2.  监控时间结束后，先读取pidstat的日志，一般位于/tmp/agent_rss.log（取决于上一步的脚本里指定的位置）。分析内存变化的趋势，给出分析结果。分析过程如下：
pidstat的输出类似于：
16:20:00      PID  minflt/s  majflt/s     VSZ    RSS   %MEM  Command
16:20:01    12345      0.00      0.00  204800  16384   0.40  app_name
这一步要做的分析：观察pidstat记录的内存每次变化的趋势，比如是否有一个固定增长的值（如果用户的问题里提到了内存会增长某个值，那么判断是否与用户的问题相匹配？）。如果出现稳定增长固定值的情况，那么可能出现了内存泄漏。要记录下来这个固定的值，接下来通过strace日志来查询是哪个函数申请这个值的内存。举个例子，你可能从pidstat的输出看到：
	1. 在23:30:07，RSS从12440增长到12660 (+220KB)
	2. 在23:30:10，RSS从12660增长到23800 (+11140KB) - 这是一次明显的增长
	3. 在23:30:33，RSS从22356增长到38720 (+16364KB) - 又一次明显的增长16mb左右
	4. 在23:31:07，RSS从38996增长到56996 (+16000KB) - 又一次明显的增长16mb左右

3. 进行这一步之前，确保已经分析了pidstat的日志，拿到了内存变化的趋势。然后读取strace的日志，一般位于/tmp/agent_strace.log（取决于上一步的脚本里指定的位置）。
根据pidstat观察到的变化趋势，在日志中锁定申请内存的函数。如果用户的问题里明确提到了内存增长某个值，那么优先去检索申请这个值的内存的函数；如果用户没有提到，那么根据上一步pidstat的分析结果来判断。
执行脚本 strace_analyze.sh 来分析strace日志，必须传入的参数有日志的位置、目标内存大小（从用户的问题或者pidstat的分析结果中得到）：
```bash
# usage: ./strace_analyze.sh <log_file> <target_size_mb>
# Example: ./strace_analyze.sh /tmp/agent_strace.log 10
```
4.拿到strace的结果后，分析日志里的信息，推断出最有可能导致故障的系统调用操作。

### 步骤3. 使用GDB定位故障代码
**目标**：首先，确保已拿到上一步的分析结果！如果没有分析结果，先回到上一步去做分析。步骤2的分析结果应该包含：pidstat记录的RSS增长趋势，从strace里定位到具体申请内存的函数。然后此步骤使用GDB做具体的捕获操作。

**操作**：
需要运行脚本 start_gdb_trap.sh，必须要传入的参数有：服务名或进程，持续时间(如果用户没有指定则默认30秒)，上一步分析出来的函数名，要查询的内存阈值（根据上一步strace查询到的内存大小判断，要稍微比这个值小一点。比如上一步查询到的内存是10MB，那么阈值设置为10000000字节）。参考示例：
```bash
# Usage: ./start_gdb_trap.sh <target> <duration> <syscall> <threshold>
# Example: ./start_gdb_trap.sh app_name 30 xxxxxx 10000000
```

### 步骤4. 分析GDB结果
**目标**：从堆栈回溯和内存映射信息中定位到故障的源代码文件和行号。

**操作**：
1. 告知用户监控服务已启动。接着等待上一步的监控服务结束（取决于上一步指定的持续时间）
2. 开始分析 GDB 的输出，日志通常保存在/tmp/agent_gdb.log（取决于上一步的脚本里指定的位置）
GDB脚本预期输出:
- **Backtrace**: Shows call stack
- **Mappings**: Memory map information

**工作流模式：条件分支 (Conditional Branches)**

**分支逻辑判定：**

*   **场景 A: 堆栈回溯中包含清晰的源代码信息**
    - [ ] **检查 Backtrace 部分**：查找堆栈帧，其中应包含源代码文件和行号。
    - [ ] **提取关键信息**：记录函数名、源文件路径、行号 以及相关参数。
    - [ ] **分析 Mappings 部分**：查看内存映射列表，了解进程的虚拟内存布局。重点关注 `[heap]` 和匿名映射的变化。
        ```unknown
        Start Addr           End Addr       Size     Offset objfile
        0x400000           0x40d000     0xd000        0x0 /usr/bin/hkidsd
        0x11b08000         0x11b38000    0x30000        0x0 [heap]
        ```
    - [ ] **阅读代码**：根据定位到的具体文件、代码位置，查询对应的目录和代码文件是否存在。如果存在，阅读文件、代码故障的位置，具体分析代码的错误。
	- [ ] **得出结论**：直接告知用户定位到的具体文件、代码位置以及涉及的函数。

*   **场景 B: 堆栈回溯仅停留在 libc 内部，无明确源代码信息**
    - [ ] **检查 Backtrace 部分**：如果堆栈类似以下情况，停在 `calloc`、`mprotect` 等 libc 函数内。
        ```c
        #0  0x00007f971717b67b in mprotect () from /usr/lib64/libc.so.6
        #1  0x00007f971710df27 in ?? () from /usr/lib64/libc.so.6
        #2  0x00007f971710f070 in ?? () from /usr/lib64/libc.so.6
        #3  0x00007f97171103b8 in calloc () from /usr/lib64/libc.so.6
        ```
    - [ ] **结合 Mappings 与操作参数**：查看 系统操作的内存地址和大小。
    - [ ] **计算代码偏移（如需）**：如果堆栈最顶层是可执行文件本身的地址，可能需要通过内存映射计算代码偏移，以推测大致的函数位置。**注意**：如果 backtrace 已包含足够源码信息，则跳过此步。
    - [ ] **得出结论**：告知用户问题与 libc 内存分配/保护机制相关，并指出可能触发该操作的调用模式。

*   **⚠️ 异常处理 (Fallback)**
    - 若 GDB 日志为空或未捕获到目标调用：
        - 检查进程 PID 是否正确，进程是否在运行。
        - 确认触发问题的操作是否在 GDB 陷阱生效期间执行。
        - 考虑延长陷阱时长或监控其他系统调用（如 `mmap`、`brk`）。

### 步骤 5：总结诊断报告并提供建议

根据步骤4的分析结果，形成结构化报告。
**目标**：清晰传达根因、位置和解决方案。

1.  **诊断报告**
	- 总结你做了哪些操作
2.  **指明故障原因和位置**：
    - 根因：指明故障的原因，例如，“glibc 在释放大块内存（约16MB）后未及时归还给操作系统，因其‘贪婪’缓存机制。”
    - 定位：提供具体的文件路径和代码行号。
3.  **提供优化建议**（供用户参考执行）：
    - **显式内存管理**：将 `calloc`/`free` 替换为 `mmap`/`munmap`，避免 glibc 缓存。
        ```c
        // 替代 calloc(1, LOG_BUF_SIZE);
        void* log_buf = mmap(NULL, LOG_BUF_SIZE, PROT_READ | PROT_WRITE,
                             MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
        // 使用后...
        munmap(log_buf, LOG_BUF_SIZE);
        ```
    - **内存复用**：重用缓冲区，而非反复分配释放。实现对象池。
    - **内存修剪**：在释放大缓冲区后调用 `malloc_trim(0)`，鼓励 glibc 归还内存给 OS。
	
## 参考文件说明
> 此技能包含以下参考文件，概述了诊断流程的核心内容和脚本工具。

- **`scripts/start_monitor.sh`**：进程内存监控脚本。用于在指定时间内监控目标进程的 RSS 等内存指标，帮助确认内存异常的现象。

- **`scripts/strace_analyze.sh`**：strace日志分析脚本。核心诊断工具，用于分析strace日志里的信息。

- **`scripts/start_gdb_trap.sh`**：GDB 陷阱脚本。核心诊断工具，用于附加到运行中的进程，拦截特定的系统调用，并输出详细的调用堆栈和进程内存映射信息到日志文件。
