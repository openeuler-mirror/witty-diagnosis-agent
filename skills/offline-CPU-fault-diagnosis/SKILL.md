# 离线CPU故障诊断

本技能通过分析从服务器收集的标准日志文件，帮助诊断 EulerOS CPU 故障。

## 输入日志目录结构与对应诊断脚本

以 `/path/to/logs/xxxx` 为例，标准的服务器日志收集包通常具有以下层级结构。本技能提供了针对性的脚本来分析不同层级的日志。

> **注意**：在实际场景中，用户提供的日志包可能不完整，可能仅包含以下三种目录中的一种或多种。请根据实际存在的日志类型灵活选择对应的分析脚本。

```text

```

## ⚠️ 强制执行流程

**必须严格按以下顺序执行，禁止跳过或乱序：**

```
Step 0 (故障日志采集) → Step 1 (场景分类) → Step 2 (深入分析) → Step 3 (根因校验) → Step 4 (生成报告)
```

**执行规则：**
1. **顺序强制**：必须完成当前步骤并验证通过后，才能进入下一步
2. **场景分支**：Step 1 输出场景标签后，Step 2 必须执行对应的专项分析脚本
3. **数据校验**：Step 3 必须通过证据矩阵校验后才能生成最终报告
4. **文件适配**：日志文件不全时自动降级分析策略，但必须至少有一个日志文件

**每步完成标志：**
- Step 0：输出日志文件时间范围、文件统计、错误关键词概览
- Step 1：确定故障场景（如 CPU_HARDWARE_FAILURE 等）
- Step 2：输出物理级精准定位、传导链及初步根因
- Step 3：输出根因证据校验表、原生日志证据及置信度定性
- Step 4：生成完整的诊断报告文件（.md）

**目标**：快速扫描所有日志文件，识别异常模块和关键报错，建立故障全景视图。

**执行命令**：
```bash
python3 scripts/diagnose_summary.py <log_dir> -o
```

### 精细定位（微观分析）

**目标**：根据全量扫描结果和用户提供的过滤条件，使用 `grep` / `less` 等文件操作命令查看具体的原始日志上下文获取更细粒度的故障信息。

> **注意：使用```diagnose_summary.py```脚本时，必须优先执行 `--help` 参数，了解脚本用法**

## Step 1：场景分类

根据 Step 0 采集的日志概览，分析故障现象并确定故障场景类型。

### 场景分类概述

CPU故障主要分为以下七种场景类型：

| 场景标签 | 中文描述 | 主要特征 |
|---------|---------|----------|
| `CPU_HARDWARE_FAILURE` | CPU硬件故障 | iBMC SEL报告CPU硬件错误、MCE（机器检查异常） |
| `CPU_OVERHEATING` | CPU过热 | CPU温度持续超过安全阈值、风扇故障、散热不良 |
| `CPU_MICROCODE_ERROR` | CPU微码错误 | 微码更新失败、微码版本不匹配、CPU微码错误 |
| `CPU_CACHE_ERROR` | CPU缓存错误 | L1/L2/L3缓存ECC错误、缓存一致性错误 |
| `CPU_FREQUENCY_THROTTLING` | CPU频率调节 | CPU频率被限制、电源管理问题、性能下降 |
| `CPU_INTERCONNECT_ERROR` | CPU互连错误 | QPI/UPI总线错误、CPU间通信故障 |
| `CPU_VOLTAGE_REGULATION` | CPU电压调节 | VRM（电压调节模块）故障、CPU供电异常 |

### 场景 → 根因假设矩阵

确定场景标签后，**必须从以下矩阵中选取 2~3 个候选根因假设**，并在 Step 2 中逐一验证：

| 场景标签 | 候选根因假设（需在 Step 2 中验证） |
|---------|----------------------------------|
| `CPU_HARDWARE_FAILURE` | ① CPU物理损/UCE 引发 MCE #18 导致 Panic 宕机 ② CPU插座接触不良 ③ 主板供电故障 |
| `CPU_OVERHEATING` | ① 散热器安装不当/硅脂干涸 ② 风扇故障/转速不足 ③ 机箱风道设计不良/积尘 |
| `CPU_MICROCODE_ERROR` | ① 微码版本与CPU型号不兼容 ② 微码更新过程中断电 ③ BIOS/UEFI固件bug |
| `CPU_CACHE_ERROR` | ① 高频 CE 错误导致 CE 风暴触发降频保护 ② CPU缓存物理损坏 ③ 内存控制器故障 |
| `CPU_FREQUENCY_THROTTLING` | ① 电源策略配置不当 ② 温度过高触发降频 ③ 主板供电不足 |
| `CPU_INTERCONNECT_ERROR` | ① QPI/UPI总线物理损坏 ② CPU插座针脚弯曲 ③ 主板布线问题 |
| `CPU_VOLTAGE_REGULATION` | ① VRM模块过热/损坏 ② 主板电容老化 ③ 电源供应不稳定 |

> ⚠️ **强制要求**：Step 2 分析结束后，必须对上述候选根因逐一标注：✅ 已证实 / ❌ 已排除 / ❓ 证据不足

**Step 1 完成标志：**
1. ✅ 确定主要故障场景标签（从上述类型中选择）
2. ✅ 记录故障现象与关键证据
3. ✅ 为Step 2深入分析提供明确的故障场景方向

## Step 2：深入分析

根据 Step 1 的场景分类结果，必须**首先完成时序关联与故障传导链重建**，然后再通过通用或专项脚本收集对应证据，最终给出精确的物理坐标定位。

### 2.1 时序关联与传导链重建 (核心理论框架)

**目标**：通过多源日志的时间戳对齐，重建故障发生的完整时间轴，厘清事件的先后顺序与因果链，为根因定位提供时序证据。

#### 2.1.1 确定 CPU 故障零点 (T0)

故障零点（T0）是时序分析的基准锚点，定义为**最早可观测到异常的时间戳**。确定优先级（由高到低）：

| 优先级 | 来源 | 说明 |
|----|----|----|
| **P1** | 硬件错误日志（iBMC / SEL） | 最底层的致命报错（如 CATERR, IERR, MSMI, Thermal Trip），时间点最准确。 |
| **P2** | 内核感知层（`dmesg` / `mcelog`） | 最早出现的 MCE（机器检查异常）、PCIe AER 错误或温度阈值告警。 |
| **P3** | 系统调度层（`syslog` / `messages`） | `Soft Lockup`、`RCU Stall` 或 CPU 降频 (throttling) 等系统级异常事件。 |
| **P4** | 应用感知层 | 进程段错误（Segfault）、算力骤降或业务响应超时，通常滞后最大。 |

> ⚠️ **时钟偏差处理**：多节点或异构日志源场景下，需留意 iBMC 时间与 OS 时间（NTP）是否存在时钟偏移。多源对齐时需留意并修正该偏差量。

#### 2.1.2 多维日志对齐与时间轴矩阵

以 T0 为基准，将 iBMC 传感器读数、dmesg 报错、微码状态和 OS 日志统一映射到绝对时间轴上，构建**事件序列矩阵**。
*示例：因风扇失效导致的 CPU 热宕机时间轴*
```text
T0-30m  ├─ [InfoCollect] 环境温度与 CPU 温度传感器记录开始持续升高。
T0-5m   ├─ [iBMC SEL]    检测到 CPU 风扇转速过低或转子锁定告警。
T0-1m   ├─ [OS dmesg]    `Core temperature above threshold, cpu clock throttled` (CPU开始降频自保)。
T0      ├─ [iBMC SEL]    记录 `Thermal Trip` 硬件断电保护 → 标定为故障发生零点 T0。
```

#### 2.1.3 CPU 专属故障传导链推断

结合对齐的时间轴矩阵，运用以下规则推导故障传导链方向：
- **规则一：层级自下而上（硬件损坏主导）**
  - *特征*：底层的 UPI 链路错误或 iBMC 掉电日志早于（或同发生于）内核 Panic。
  - *传导链*：主板供电/CPU插槽实体异常 → 触发硬件报错中断 (SMI/NMI) → 操作系统无法处理 → 系统复位宕机。
- **规则二：环境向硬件传导（热灾难/外围设备主导）**
  - *特征*：风扇/电源模块预警先行，伴随持续的温度上升和大量降频记录，最后宕机。
  - *传导链*：散热失效（根因） → CPU 限制功耗（表象1） → 算力不足引发业务性能告警（表象2） → 最终宕机保护（结果）。
- **规则三：软硬件死锁（微码/缺陷主导）**
  - *特征*：iBMC 等底层完全无硬件异常记录，但系统频发特定指令集崩溃或进程无响应。
  - *传导链*：触发微码 Bug/内核调度死锁 → 内部锁或寄存器状态异常 → 触发 OS 层面的 Soft Lockup → 业务层产生超时报错。

> ⚠️ **精确定位强制要求**：在 CPU 诊断中，**严禁仅使用“CPU故障”这类含糊结论。**
> 必须通过证据追踪到细粒度的三维物理坐标定位，例如：
> - ✅ 正确结论：`Socket 1 -> Core 8 -> L2 Cache 读取校验失败` 或是 `Node 0 与 Node 1 之间的 UPI Link 0 端口互通异常`。
> - ❌ 错误结论：`发生 MCE 错误` 或仅仅说是 `CPU 1 损坏`。

### 2.2 日志脚本分析执行 (执行工具动作)

#### 2.2.1 通用分析流程

通用分析流程适用于所有CPU故障场景，提供基础的日志提取与数据分析能力：

```bash
# iBMC 日志分析（硬件层）
python3 scripts/diagnose_ibmc.py <log_dir> [选项]

# InfoCollect 日志分析（系统信息层）
python3 scripts/diagnose_infocollect.py <log_dir> [选项]

# OS Messages 日志分析（操作系统层）
python3 scripts/diagnose_messages.py <log_dir> [选项]

# CPU专项分析（综合层，推荐根据场景使用）
python3 scripts/diagnose_cpu.py <log_dir> --hardware    # 硬件/缓存/互连/电压故障
python3 scripts/diagnose_cpu.py <log_dir> --temperature # 过热/热管理故障
python3 scripts/diagnose_cpu.py <log_dir> --frequency   # 降频/频率故障
```

**通用分析执行策略**：
1. **顺序执行**：建议按硬件层→系统信息层→操作系统层的顺序执行分析
2. **参数调整**：根据Step 0的输出结果，调整时间范围、关键词等参数
3. **结果整合**：将不同来源的分析结果整合，形成完整的故障视图

#### 2.2.2 按场景专项分析

当Step 1确定故障场景后，优先使用对应的专项分析流程。详细的专项分析指南请参考：

- [CPU故障场景专项分析指南](references/CPU_scenario_analysis.md)

**专项分析包含以下七种场景**：
1. **CPU硬件故障分析** (CPU_HARDWARE_FAILURE)
2. **CPU过热分析** (CPU_OVERHEATING)
3. **CPU微码错误分析** (CPU_MICROCODE_ERROR)
4. **CPU缓存错误分析** (CPU_CACHE_ERROR)
5. **CPU频率调节分析** (CPU_FREQUENCY_THROTTLING)
6. **CPU互连错误分析** (CPU_INTERCONNECT_ERROR)
7. **CPU电压调节分析** (CPU_VOLTAGE_REGULATION)

**专项分析执行策略**：
1. **场景匹配**：根据Step 1确定的场景标签，选择对应的专项分析流程
2. **参考指南**：按照专项分析指南中的步骤执行
3. **专用参数**：使用场景专用的分析命令和参数
4. **根因验证**：使用根因假设矩阵进行根因验证

#### 2.2.3 分析执行原则

1. **场景优先原则**：当故障现象明确匹配某个场景时，优先使用专项分析
2. **通用备用原则**：当故障现象不明确或不符合任何专项场景时，使用通用分析
3. **组合使用原则**：可以同时使用专项分析和通用分析，相互验证结果
4. **逐步深入原则**：从概览分析开始，逐步深入具体问题

**Step 2 完成标志**：
1. ✅ 输出故障零点 T0 的精确时间戳及其所依托的具体日志行。
2. ✅ 梳理出以 T0 为基准的结构化事件序列矩阵与至少 3 步的确定故障传导链。
3. ✅ 给出精确到物理部件（例如 Socket / Core / 通道端口）的细粒度定位结果。
4. ✅ 收集脚本产出的相关原生日志片段作为强有力的支撑证据。

## Step 3：根因反思与证据双向校验

**目标**：对 Step 2 输出的“初步传导链与定位结果”进行“交叉质询”，确保得出的最终结论 100% 由底层日志支撑，防范分析过程中脱离实际日志记录的发散性推断。本阶段是确立最终诊断结论的“防御门槛”。

### 3.1 交叉质询铁律 (Cross-Examination Rules)

规定分析输出最终结论前，必须遵循以下三条铁律对 Step 2 的结果进行自我质询：
1. **孤证不立原则**：任何一个最终的物理级故障结论（如 CPU 损坏、主板供电异常），绝对不能仅凭系统层的一条报错（如 OS Panic 或业务超时）就下断言。**必须**同时找到硬件基板（如 iBMC / SEL）或内核底层（如 MCE 寄存器记录）的第二独立证据源支撑。若无底层证据支撑，只能定性为“疑似故障”或“软件死锁状态”。
2. **逻辑闭环原则**：从 T0（故障零点）到最终业务故障结果，中间的传导链不允许出现跳跃性结论。例如：`发现温度异常超高`不能直接跳跃推断导致`UPI互连通信错误`。如果两端现象同时出现但无法建立合乎科学原理的因果桥梁，则说明这可能是彼此独立的异常，或者根源推断方向发生错误。
3. **互斥排异原则**：如果判定故障是 A 原因主导，那么必须主动去查证与之互斥的 B 模块日志是否“干净”。例如，若推断结论是纯粹的“机房环境高温导致服务器积热”，则必须反向验证风扇转速正常，绝不能在日志中出现“风扇转子锁定告警”；若有违背，则“单纯环境高温”假设被推翻。

### 3.2 强制：根因证据校验表 (Evidence Validation Matrix)

在确认最终结论并进入撰写报告环节前，强制要求进行独立对照梳理，且**每一项检查都必须强制附带对应的真实原生日志片段截取**，否则视作校验不通过：

| 校验维度 | 校验标准要求 | 强制证据格式（分析打样要求） |
| :--- | :--- | :--- |
| **E1: 时序连续性** | 从结果向故障零点(T0)回溯，序列是否存在无法解释的空白期？ | `[✅/❌ 结果]` + `时序计算说明` + `相邻事件的原生日志片段关联` |
| **E2: 物理同一性** | 各级日志（如 OS层报 CPU 0，和 iBMC 层报 CPU 1）指控的设备坐标，映射后是否确实是真实的、同一个物理部件单元？ | `[✅/❌ 结果]` + `系统层 CPU ID 与 物理层 Socket ID 的对应关系梳理日志` |
| **E3: 现象排他性** | 导致该报错的最终层级链路中，是否存在其他未被完全排除的平行底层因素？ | `[✅/❌ 结果]` + `主动寻找并排除相关平行干扰因素的说明` |

### 3.3 结论防发散拦截机制 (Anti-Hallucination Mechanism)

针对上述证据审查过程发现不通过的情况，制定硬性拦截退回与评级降级规范：

*   **断链阻断**：如果在前置证据校验表中存在 `[❌ 冲突]` ，或是无法从日志堆中**找到任何能证明因果传导的日志片段**，则视为假想传导链无效，**强制触发流程拦截，需回溯重新收集或判定**。
*   **降级处分**：大模型或人员不得依托已有知识强行缝合残缺证据。如果在客观上确实缺乏某一层（比如缺失了 iBMC 的底层支持）的关键日志，导致核心环节断裂，在此种情况下，必须将最终呈现给用户的异常归因为**“存在多重并行可能性”**或**“高度疑似 (Suspected)”**状态。在此，必须在最终诊断处高亮警示：“由于缺乏 XXX 维度的日志，故障判定传导链在 XXX 处断裂，暂时无法得出唯一明确性判定。”
*   **严禁用词限制**：在证据链未能满足完全逻辑校验闭环的标准前，诊断文书及对质交互中**绝对严禁**出现诸如“肯定”、“必然”、“绝对是 XXX 的直接毁坏”等发散式、决定性断言词汇。

**Step 3 完成标志（防发散质询门槛）**：
1. ✅ 高度结构化地产出《根因证据校验表》中包含的每一个三维质询的自查结论。
2. ✅ 每个标记为通过（✅）的自查项，均强制提取并附带截取了原生日志记录中的 Timestamp 和 原文 Text 以便二次佐证。
3. ✅ 基于自查的客观事实依据，对当前的证据链有效性进行状态声明定性（分为：完全闭环 / 确实存在断层）。
4. ✅ 基于实际掌握的强关联证据链集合，输出与之匹配等位置信度（已明确证实 / 单一疑似判定 / 多重交织未知原因）的严谨最终诊断研判方向。

## Step 4：生成报告

汇总 Step 0～3 的所有分析结果，生成结构化诊断报告：

```bash
bash scripts/generate_report.sh \
    --analysis /tmp/cpu_analysis_results.json \
    --output ./cpu_diagnosis_report.md
```

**报告结构：**

1. **Executive Summary（故障摘要）** — 故障场景、根本原因、修复建议概述
2. **Technical Analysis（技术分析）** — 日志文件概览、故障现象、故障机理、证据链（E1/E2/E3...）
3. **Root Cause（根本原因）** — 直接原因 + 根本原因 + 5 Whys 分析
4. **Recommendations（修复建议）** — 立即 / 短期 / 中期 / 长期修复措施
5. **风险评估** — 数据丢失、服务中断、复发风险评估
6. **最终验证清单** — 确认分析足够深入的检查清单
7. **附录** — 关键日志片段与相关命令参考

**根因具体性要求（笼统描述视为分析不足）：**

| ❌ 笼统 | ✅ 具体 |
|--------|--------|
| "CPU坏了" | "CPU 1 (物理位置 Socket 0) 因温度持续超过95°C导致硅片热损伤" |
| "CPU过热" | "CPU散热器硅脂干涸，导致CPU温度在负载下从60°C升至105°C触发热保护" |
| "微码错误" | "CPU微码版本0x42与当前CPU型号不兼容，导致L3缓存ECC错误频发" |

**根因推理完成性检查（调用 `generate_report.sh` 前必须通过）：**

在调用 `./scripts/generate_report.sh` 生成报告框架之前，必须能够回答以下所有问题：

- [ ] 根因是否具体到：**CPU标识**（CPU编号/物理位置）+ **错误类型**（硬件损坏/过热/微码错误）+ **触发条件**（温度/负载/时间）？
- [ ] Step 2 矩阵中所有候选根因是否已完成 ✅/❌/❓ 标注？
- [ ] 是否能描述从"根因"到"最终症状"的完整因果链条（至少 3 层，例：硅脂干涸 → 散热不良 → CPU温度升高 → 触发热保护降频 → 性能下降）？
- [ ] 是否排除了至少一个"相似但非真正根因"的情况（即做过鉴别诊断）？

> ⚠️ **若有任何未通过项，必须返回 Step 2 继续分析（追加关键词或缩小时间范围），而非直接填写报告模板。**

## 分析原则

0. **根因优先**：诊断的最终目标是**定位根因（Root Cause）**，而非仅描述症状。每个分析步骤都应推进"为什么会发生"的答案，而非停留在"发生了什么"。症状描述（如"CPU过热"）只是中间过程，根因（如"散热器硅脂干涸"）才是终点。
1. **硬件优先**：CPU问题优先排查硬件层面，确认非软件配置引起
2. **证据驱动**：每个结论必须有日志数据支撑，无数据则标注"待验证假设"
3. **温度监控**：CPU故障多与温度相关，必须仔细分析温度数据
4. **风险评估**：评估修复操作对系统的影响，优先选择保守方案
5. **反思验证**：通过假设驱动分析和跨层反思，确保根因结论的严谨性
6. **离线分析**：本 Skill 仅基于日志文件进行分析，不执行任何在线系统命令
