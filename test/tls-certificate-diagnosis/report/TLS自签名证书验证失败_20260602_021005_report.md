> 排查逻辑：**提出假设 → 收集证据 → 验证或排除 → 逐步收敛到根因**

### 3.1 初始现象

- **目标容器**: `tls-full`
- **目标端口**: `4435`，绑定进程 `openssl` (PID 43)
- **目标证书**: `/test/certs/selfsigned.pem`
- **故障现象**: `openssl verify` 对证书 `/test/certs/selfsigned.pem` 验证失败，返回 error code 18

---

### 3.2 假设驱动排查

#### 假设 A：证书已过期 ⚠️ 假设排查 —— ✅ 已排除

> 🧪 假设：证书有效期已过，导致验证失败

| 检查项 | 操作（基于真实数据） | 结论 |
|--------|------|------|
| 证书有效期 | `openssl x509 -in /test/certs/selfsigned.pem -dates` | 有效期：2026-06-02 02:15:45 GMT ～ 2027-06-02 02:15:45 GMT |
| 当前时间 | 诊断执行时间：2026-06-02 02:10:00 UTC | 在当前有效期内 |

**❌ 排除**：证书当前时间在有效期内（距离过期还有约 364 天 23 小时），过期假设不成立。

---

#### 假设 B：系统时间错误导致验证窗口偏移 ⚠️ 假设排查 —— ✅ 已排除

> 🧪 假设：容器系统时间偏差较大，导致 openssl 对证书有效期判断与实际不符

| 检查项 | 操作（基于真实数据） | 结论 |
|--------|------|------|
| 时间偏差推断 | 诊断执行时间为 2026-06-02 02:10:00 UTC，证书生效时间为 2026-06-02 02:15:45 GMT | 时间几乎一致，偏差不超过 6 分钟 |
| 有效期窗口 | 即使存在微小偏差，证书生效时间稍晚于诊断时间约 5 分 45 秒 | 实际上 openssl verify 返回的是 error 18（自签名）而非 error 9（未生效）或 error 10（已过期） |

**❌ 排除**：
1. `openssl verify` 返回 error code 18（self-signed certificate），而非 error code 9（证书未生效）或 error code 10（证书已过期），时间相关的错误码未出现。
2. 系统时间与证书有效期范围基本一致，无显著偏差证据。

---

#### 假设 C：CA 根证书缺失（Root CA not in trust store）—— ✅ 确认为本质问题的一部分

> 🧪 假设：系统信任库中缺少签发该证书的 CA 根证书

| 检查项 | 操作（基于真实数据） | 结论 |
|--------|------|------|
| 信任库检查 | grep 验证 `/test/certs/selfsigned.pem` 是否在 `/etc/ssl/certs/ca-certificates.crt` 中 | ❌ 不在系统 CA 信任库中 |
| 证书目录对比 | 对比 `/etc/ssl/certs/` 与 `/test/certs/` 文件列表 | selfsigned.pem 仅存在于 `/test/certs/` 下 |

**🟡 部分确认**：该假设与最终根因一致，但自签名证书的特殊性在于——即使将自签名证书加入信任库，也属于"信任锚定点"（trust anchor）操作，而非常规的 CA 链验证。对于自签名证书，更准确的修复是将证书显式加入信任库或在客户端侧指定 `-CAfile`。

---

#### 假设 D：证书是自签名证书（Self-signed），不被信任 —— ✅ 确认为根因

> 🧪 假设：证书 Subject == Issuer，即证书由自己签发（自签名），不存在可信的 CA 证书链，导致 `openssl verify` 拒绝信任

**Step 1 — 验证 Subject 与 Issuer 是否相同**

| 字段 | 值 |
|------|-----|
| **Subject** | `CN = selfsigned.example.com` |
| **Issuer** | `CN = selfsigned.example.com` |

✅ **Subject === Issuer，确认为自签名证书**

**Step 2 — 验证 Subject Key Identifier 与 Authority Key Identifier**

| 字段 | 值 |
|------|-----|
| **Subject Key Identifier** | E1:5E:E5:7D:0F:D7:6B:D7:BB:90:62:36:21:D2:69:37:D3:25:3A:FB |
| **Authority Key Identifier** | E1:5E:E5:7D:0F:D7:6B:D7:BB:90:62:36:21:D2:69:37:D3:25:3A:FB |

✅ **Subject Key Identifier === Authority Key Identifier，进一步确认为自签名证书**

**Step 3 — 执行 openssl verify**

```text
$ openssl verify -CApath /etc/ssl/certs /test/certs/selfsigned.pem
CN = selfsigned.example.com
error 18 at 0 depth lookup: self-signed certificate
error /test/certs/selfsigned.pem: verification failed
```

| 错误码 | 含义 | 说明 |
|--------|------|------|
| **18** | `X509_V_ERR_DEPTH_ZERO_SELF_SIGNED_CERT` | 深度 0 的证书是自签名证书，不在信任库中 |

✅ **确认根因：证书为自签名证书，Subject == Issuer，未加入系统 CA 信任库，openssl verify 返回 error code 18。**

### 4.2 永久修复计划

| 修复措施 | 负责人 | 完成时间 |
|--------|------|---------|
| 1. 将自签名证书显式注册到系统 CA 信任库 | 待定 | 待定 |

### 4.3 修复方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **方案一**：注册到系统信任库 | 操作简单，无需修改应用代码 | 仅限本机信任，其它客户端仍需单独配置 | 内部测试环境 |
| **方案二**：替换为正式 CA 证书 | 所有客户端自动信任，符合生产安全最佳实践 | 需申请 CA 签名，流程较长；可能需要费用 | 生产环境 |
| **方案三**：客户端指定证书验证 | 零侵入性，不修改服务端 | 每个客户端都需要额外参数，易遗漏 | 临时/开发调试 |
