三、排查过程

排查逻辑：提出假设 → 收集证据 → 验证或排除 → 逐步收敛到根因

3.1 初始现象

  • 故障描述：容器 tls-test 中服务 expired.example.com 在端口 4433 提供 TLS 服务，客户端 openssl verify 返回 code 10（certificate has expired）。
  • 关键日志/输出：
    • openssl s_client -connect 127.0.0.1:4433 显示证书 notBefore=notAfter=May 29 15:50:32 2026 GMT
    • openssl verify 返回码：10 (certificate has expired)
    • 证书链深度：1（仅叶证书，无中间 CA 或根 CA）
    • 验证输出还包含 unable to get local issuer certificate (code 20/21)
  • 用户侧表现：客户端 TLS 验证失败，依赖该证书的服务调用被拒绝。

3.2 假设驱动排查

自检说明：以下所有假设排查均基于 Kuafu Agent 在执行阶段实际采集的真实数据，无虚构操作。

假设 A1：服务器证书已过期（核心理赔）✅ 确认根因

🧪 假设：证书的 notAfter 时间已早于当前系统时间，导致证书被判定为过期。

检查项 操作（基于 Kuafu 诊断输出） 结论
证书有效期 通过 openssl s_client 获取证书，解析 notBefore/notAfter notBefore = May 29 15:50:32 2026 GMT，notAfter = May 29 15:50:32 2026 GMT
过期判定 两个字段完全相同，意味着有效期为 0 秒 证书在签发的那一刻即已过期
OpenSSL 验证 openssl verify 执行结果 返回 code 10（certificate has expired）
系统时间对比 date 命令输出 Fri May 29 15:54:01 UTC 2026 ✅ 系统时间与证书时间戳在同一分钟范围内，时间正确

✅ 结论：证书的 notBefore 与 notAfter 完全相同（零有效期），导致证书签发即过期。唯一的根本原因。

假设 A2：证书即将过期（接近过期但尚未过期）❌ 排除

🧪 假设：证书有效期较短，但尚未真正过期，可能是客户端本地时间偏差导致的误判。

❌ 排除理由：

  • openssl verify 在服务器本地执行，返回 code 10 表明服务器自身的 OpenSSL 库判定证书已过期。
  • notAfter 时间戳（15:50:32）早于诊断时的系统时间（15:54:01），差值约 3 分 29 秒。
  • 更关键的是，notBefore == notAfter，这使得该证书在任何时间点都不可能通过有效期验证——即便是刚签发的那一秒。
  • 这并非"即将过期"，而是"从未有效"。

假设 A3：系统时间错误（时间漂移）❌ 排除

🧪 假设：容器内系统时间不正确，导致证书有效期验证判断失误。

检查项 操作 结论
系统时间获取 date 命令 Fri May 29 15:54:01 UTC 2026
与证书时间对比 证书 notAfter 为 May 29 15:50:32 2026 GMT 系统时间晚于 notAfter 约 3.5 分钟，但即便将系统时间回拨到 15:50:32 之前，该证书仍然无效（notBefore==notAfter）
NTP 配置 查找 ntp.conf / chrony.conf / timedatectl ❌ 容器内未配置 NTP，但当前时间准确

❌ 排除理由：

  • 系统时间准确（与 UTC 一致），不是时间漂移问题。
  • 即使系统时间存在偏差，由于 notBefore == notAfter，任何时间点都无法通过验证——该证书不存在任何有效时间窗口。
  • 因此，系统时间错误可以彻底排除。

假设 A4：中间证书或根 CA 证书过期 ❌ 排除

🧪 假设：证书链中存在过期的中间 CA 或根 CA 证书，导致验证失败。

检查项 操作 结论
证书链深度 openssl s_client 输出 深度 = 1（仅叶证书）
中间/根证书 链中未提供任何中间 CA 或根 CA 证书 ✅ Issuer 为 CN = TestCA（非公开受信 CA）
本地 CA 包 /etc/ssl/certs/ 检查 标准 Mozilla CA 包存在，但 TestCA 不在其中

❌ 排除理由：

  • 虽然存在 unable to get local issuer certificate (code 20/21) 的问题，但 openssl verify 返回的首要错误码是 code 10，即有效期验证失败。
  • 即使补全了 TestCA 到受信任存储中，证书零有效期的问题仍然存在，验证仍会失败。
  • 中间证书问题是一个次要的、独立的问题，不是导致 code 10 的根本原因。

假设 A5：主机名（Hostname）验证失败导致的误告 ❌ 排除

🧪 假设：客户端连接时使用的主机名与证书 CN 不匹配，导致验证错误。

检查项 操作 结论
证书 Subject CN openssl s_client 输出 CN = expired.example.com
连接地址 s_client 使用 127.0.0.1 连接 主机名不匹配确有可能
verify 返回码 openssl verify 不带主机名校验 code 10 是证书有效期错误，非主机名错误（code 62）

❌ 排除理由：

  • openssl verify 返回的 code 10 明确针对证书有效期，而非主机名不匹配（后者返回 code 62）。
  • 主机名验证是应用层的独立检查，不影响 openssl verify 对证书有效期的判定。
  • 主机名不匹配是一个额外的问题，但不是导致 certificate has expired 的原因。

3.3 反事实验证（Counterfactual Verification）

通过"假设根因不存在，故障是否还会发生"的逻辑推演，验证根因的唯一性和充分性。

反事实场景 推理 结论
若 notAfter 被设置为 2027-05-29（一年后），其他条件不变 证书具有正有效期，openssl verify 不会返回 code 10 ✅ 故障消失 → 根因成立
若 notAfter 被设置为 2026-05-30（一天后），其他条件不变 证书有效期 > 0，验证通过 ✅ 故障消失 → 根因成立
若系统时间错误（假设快进 1 年），但证书有效期正常 故障可能发生，但此处系统时间正确，不适用 不支持时间错误假设
若补全了 TestCA 到受信任存储，但 notBefore==notAfter 不变 code 20/21 消失，但 code 10 仍然存在 验证仍失败 → 零有效期是唯一根因
若证书链增加中间 CA 和根 CA，但 notBefore==notAfter 不变 同上，code 10 仍在 链不完整是次要问题，零有效期是根因

反事实验证结论：只有修正 notAfter（使其 > notBefore），才能彻底消除 code 10 错误。零有效期是必要且充分的根因。

四、修复方案

4.1 应急处置（当前无应急方案）

由于证书从签发起就没有有效时间窗口，无法通过时间回拨、置零等方式"临时生效"。唯一的应急路径是立即签发新证书。

4.2 永久修复计划

步骤 操作 详细说明 执行人 预计时间
1 重新生成证书（使用正确的 -days 参数） 使用 openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes -subj "/CN=expired.example.com" 系统/人工 立即
2 将新证书部署到正确路径 复制到 /etc/ssl/certs/tls-test.crt 及对应私钥位置 系统/人工 5 分钟
3 补充中间 CA 证书到链中 若使用私有 CA（TestCA），将 TestCA 证书合并至链中或加入系统受信任存储 系统/人工 10 分钟
4 重启 TLS 服务 重新加载新证书：systemctl restart tls-test（或对应服务管理命令） 系统/人工 1 分钟
5 验证修复 执行 openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/tls-test.crt 人工 1 分钟
6 可选：配置容器内 NTP 安装 chrony 或 ntpd，确保 /etc/chrony/chrony.conf 配置正确的时间源 人工 15 分钟

4.3 预防措施

措施 说明 优先级
证书签发自动化脚本中加入有效期检查 签发后自动验证 notAfter > notBefore，且天数符合预期 高
CI/CD 中加入 TLS 证书健康检查 部署前自动执行 openssl verify，失败则阻断部署 高
证书过期监控告警 对生产证书设置 T-30d / T-7d / T-1d 三级过期告警 中
容器内 NTP 配置标准化 所有容器镜像模板预装并启用 chronyd 低

五、附加发现（次要问题）

5.1 证书文件位置异常

  • 执行 find /etc/ssl/certs/tls-test.crt 未找到该文件。
  • 证书通过 openssl s_client 从端口 4433 动态获取，但未落盘到标准路径。
  • 建议：将证书文件规范放置于 /etc/ssl/certs/ 路径下。

5.2 证书链不完整

  • 链深度为 1，Issuer 为 CN = TestCA，但未提供 TestCA 证书。
  • 依赖的客户端若未将 TestCA 加入受信任存储，则即使有效期修复后，仍会遇到 unable to get local issuer certificate（code 20/21）。
  • 建议：在证书链中附加中间 CA 证书，或确保客户端预先信任 TestCA。

5.3 容器内 NTP 未配置

  • timedatectl 不可用（容器限制）。
  • ntp.conf / chrony.conf 不存在。
  • 建议：在容器镜像构建阶段启用时间同步，或依赖宿主机时间同步。当前虽未引发问题，但属潜在风险点。
