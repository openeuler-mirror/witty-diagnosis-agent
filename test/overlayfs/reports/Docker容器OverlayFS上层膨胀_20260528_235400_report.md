## 三、排查过程

> 排查逻辑：**提出假设 → 收集证据 → 验证或排除 → 逐步收敛到根因**

### 3.1 初始现象

- **告警来源**：Docker 容器 `overlayfs-fault-H` 的 overlay upper 目录持续膨胀。
- **指标数据**：
  - upper 层大小：13 MB（250 个文件）
  - lower 层大小：1 MB（100 个文件）
  - 日志写入批次数：5 批
- **用户表现**：容器内应用日志写入正常，但宿主机 `/var/lib/docker/overlay2/` 对应的容器 upper 目录持续增长，若不干预将超出镜像大小持续膨胀。

### 3.2 假设驱动排查

#### 假设 A：文件描述符泄漏导致日志文件未被截断/轮转

> 🧪 假设：应用进程持有已删除日志文件的 fd，导致磁盘空间无法释放

| 检查项 | 操作 | 结论 |
|--------|------|------|
| upper 层文件列表 | 模拟环境检查 upper 目录下文件类型 | ✅ 日志文件为常规新建文件，非已删仍占 |

**❌ 排除**：无 fd 泄漏模式，文件均为正常新建/写入。

---

#### 假设 B：OverlayFS whiteout/opaque 异常导致多余文件

> 🧪 假设：whiteout 或 opaque 标记导致 upper 层出现异常隐藏文件

| 检查项 | 操作 | 结论 |
|--------|------|------|
| upper 层特殊文件检查 | 检查是否有 `.wh.` 前缀或 `trusted.overlay.opaque` 属性 | ✅ 无异常 whiteout，均为正常日志文件 |

**❌ 排除**：无 whiteout/opaque 异常。

---

#### 假设 C：OverlayFS copy-up 机制导致 upper 层膨胀 ✅ 确认根因

> 🧪 假设：日志写入触发 OverlayFS copy-up 语义，将 lower 层文件拷贝到 upper 层，且新建日志文件直接写入 upper，导致上层持续膨胀

**Step 1 — 分析 overlayfs 挂载结构**

```text
OverlayFS 挂载典型结构：
  lowerdir = 镜像层（只读，1MB / 100 文件）
  upperdir = 容器层（读写，13MB / 250 文件）
  workdir  = 临时工作目录

写入流程：
  修改 lower 层已有文件 → copy-up: lower → upper（完整拷贝）
  创建新文件           → 直接在 upper 创建
```

**Step 2 — 定量分析膨胀情况**

| 指标 | lower 层 | upper 层 | 增长倍数 |
|------|----------|----------|----------|
| 大小 | 1 MB | 13 MB | **13×** |
| 文件数 | 100 | 250 | **2.5×** |

**Step 3 — 归因判定**

- 5 批日志写入中，每次写入均可能触发：
  - 对 lower 层原有文件的写入 → copy-up 将文件从 lower 拷贝到 upper，原文件在 upper 层占据新空间
  - 新日志文件的创建 → 直接在 upper 层落盘
- 无 logrotate 或定时清理机制 ⇒ upper 层只增不减

**✅ 结论：应用日志写入不断触发 OverlayFS copy-up 语义，导致 upper 层从接近 0 持续膨胀至 13MB（250 文件）。若不引入清理策略，upper 层将继续增长，最终可能耗尽宿主机磁盘空间。**

---

### 3.3 排查结论

```text
容器 overlayfs-fault-H upper 层膨胀
├─► 假设 A：fd 泄漏导致空间不释放     → ✅ 排除（无 fd 泄漏证据）
├─► 假设 B：whiteout/opaque 异常     → ✅ 排除（无异常标记文件）
└─► 假设 C：OverlayFS copy-up 触发膨胀 → ✅ 确认根因
        └─► 5 批日志写入触发 copy-up
        └─► upper 层 13MB / 250 文件（增长 12MB / 150 文件）
        └─► 无清理/轮转策略 → 持续增长
                └─► 🎯 根因确认：日志写入 + 无清理 = OverlayFS upper 层膨胀
```

## 四、修复方案

### 4.1 应急处置

| 步骤 | 操作 | 执行人 | 时间 | 效果 |
|------|------|--------|------|------|
| 1 | 进入容器检查 upper 层占用详情：`du -sh /var/lib/docker/overlay2/<container-id>/diff/` | 运维 | 即时 | 确认当前 upper 膨胀规模 |
| 2 | 对容器内日志目录配置 logrotate，设置按大小轮转（如 1MB）并压缩归档 | 运维 | 立即 | 控制单文件大小，减少 copy-up 触发频率 |
| 3 | 如果磁盘紧急，可执行 `docker commit` 将当前 upper 层提交为新镜像，并用新镜像重建容器（压缩 upper 层） | 运维 | 按需 | 固化当前 upper 层为镜像层，新容器从 clean 状态开始 |
| 4 | 重建容器后，挂载外部 volume（如 `docker run -v /data/logs:/app/logs`）将日志写入宿主机目录，绕过 overlay copy-up | 运维 | 按需 | 日志不经过 overlay upper，彻底消除 copy-up 膨胀 |

### 4.2 永久修复计划

| 修复措施 | 负责人 | 完成时间 |
|---------|--------|---------|
| 1. 应用内日志改用**外部 volume 挂载**（推荐 `docker run -v` 或 `docker compose volumes`），日志不写入容器层 | 应用团队 / 运维 | 近期 |
| 2. 如必须写入容器层，在应用容器中配置 **logrotate**（按大小轮转 + 压缩 + 清理过期日志，如保留最近 3 份） | 应用团队 / 运维 | 近期 |
| 3. 在 Docker 或 K8s 层面配置 **容器磁盘配额**（`--storage-opt size=10G`），防止单个容器 upper 无限膨胀 | 运维 | 近期 |
| 4. 监控告警：对 `/var/lib/docker/overlay2/` 各容器 upper 目录配置磁盘使用量监控，超过阈值（如 500MB）告警 | 运维 | 近期 |
| 5. 最佳实践：在 Dockerfile 中将日志文件写入 **stdout/stderr**（而非文件），由 Docker 日志驱动统一采集（如 json-file、journald、fluentd），消除文件日志对 overlay 层的写放大 | 应用团队 | 中长期 |
