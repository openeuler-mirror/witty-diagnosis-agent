## 三、排查过程

> 排查逻辑：**提出假设 → 收集证据 → 验证或排除 → 逐步收敛到根因**

### 3.1 初始现象

- 用户报告：dig 查询任何域名均超时无响应
- /etc/resolv.conf 被写入了不可达的 nameserver 192.0.2.1

### 3.2 假设驱动排查

#### 假设 A：/etc/resolv.conf 配置错误导致 DNS 不可用

> 🧪 假设：resolv.conf 中错误的 nameserver 192.0.2.1 导致 DNS 无法解析

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 192.0.2.1 身份确认 | 查询 RFC 5737 + ping + TCP dig | ✅ 确认为 TEST-NET-1 文档保留地址，不可达 |
| UDP/53 连通性 | dig @192.0.2.1 baidu.com | ⚠️ 返回 4ms（Windows 主机透明劫持 UDP/53 导致假阳性） |
| TCP/53 连通性 | dig +tcp @192.0.2.1 baidu.com | ✅ 超时（不被劫持，真实结果） |
| 持久化配置 | cat /etc/resolvconf/resolv.conf.d/\* | ℹ️ 未配置（resolvconf 包未安装） |
| systemd-resolved | cat /etc/systemd/resolved.conf | ✅ 默认配置，运行正常 |

**🟡 部分确认**：192.0.2.1 确实不可达，但**仅凭此假设无法解释"所有域名查询均超时"**——因为当前 /etc/resolv.conf 已恢复为 10.255.255.254，且 Windows 透明劫持 UDP/53 会"覆盖"错误的 nameserver。

---

#### 假设 B：WSL2 实例状态异常导致网络不可用 ✅ 确认根因

> 🧪 假设：WSL 实例处于停止状态，导致网络接口不可用

| 检查项 | 操作 | 结论 |
|--------|------|------|
| WSL 实例状态 | `wsl --list -v` | ✅ **所有 WSL 实例均为 Stopped** |
| 网络连通性 | ping 目标 IP（172.29.89.45） | ✅ **100% 丢包** |
| SSH 可达性 | 尝试 SSH 连接 | ✅ **连接超时** |
| 实例启动后验证 | `wsl -d Ubuntu-22.04 -u root` 启动 | ✅ 启动后 resolv.conf 自动恢复为 10.255.255.254 |
| 启动后 DNS 测试 | dig @8.8.8.8 baidu.com | ✅ **4ms 正常响应** |

**✅ 根因确认：WSL2 Ubuntu-22.04 实例处于 Stopped 状态 → 网络接口不可用 → DNS 查询无法发出 → 超时无响应。**

---

#### 假设 C：Windows DNS 透明劫持干扰

> 🧪 假设：Windows 主机 UDP/53 拦截行为导致诊断结果误判

| 检查项 | 操作 | 结论 |
|--------|------|------|
| UDP/53 劫持验证 | dig @任意地址（含 192.0.2.1）baidu.com | ✅ 所有请求均 4ms 返回，证明劫持存在 |
| TCP/53 未被劫持 | dig +tcp @192.0.2.1 baidu.com | ✅ 超时（不受劫持，反映真实情况） |

**✅ 确认**：Windows 主机透明劫持 WSL2 出站 UDP/53 流量是 WSL2 架构默认行为，属于**已知特性而非故障原因**。此劫持在一定程度上掩盖了 /etc/resolv.conf 错误的表象，但非根因。

### 4.3 补充说明：WSL2 DNS 透明劫持机制

```text
应用 (getaddrinfo/dig/nslookup)
    │
    ▼
/etc/resolv.conf  →  nameserver 10.255.255.254
    │
    ▼
systemd-resolved (stub: 127.0.0.53:53, proxy: 10.255.255.254:53)
    │
    ▼
Windows Host DNS Interceptor
    → 拦截 WSL2 所有出站 UDP/53 流量
    → 重定向到 Windows DNS 配置
    │
    ▼
Internet DNS 服务器（如 114.114.114.114 或 Windows 配置的 DNS）
```

**关键结论**：由于 Windows 主机透明劫持 WSL2 出站 UDP/53，即使 /etc/resolv.conf 配置了错误的 nameserver，UDP 查询仍可能通过 Windows DNS 成功返回。**但这一特性仅在 WSL 实例处于 Running 状态时才生效**。当实例停止时，所有网络流量均无法发出，这才是导致"超时无响应"的真正根因。
