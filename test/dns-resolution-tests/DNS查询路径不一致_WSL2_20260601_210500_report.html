三、排查过程

3.1 初始现象

  • 现象描述：在 WSL2 Ubuntu 22.04 中，resolvectl query google.com 返回的 IP 地址与 dig @8.8.8.8 google.com 返回的结果不同
  • 用户初始猜测：怀疑 systemd-resolved 缓存被污染
  • 触发命令：
    bash 
    resolvectl query google.com    → 136.109.60.113
dig @8.8.8.8 google.com +short → 142.251.34.206
  • 不一致域名范围：google.com、youtube.com、facebook.com、twitter.com 等境外域名受影响；baidu.com、github.com、qq.com 等国内域名正常

3.2 假设驱动排查

假设 A：systemd-resolved 缓存被污染

🧪 假设：resolved 缓存中存入了错误记录，导致 resolvectl query 返回污染结果

检查项 操作 结论
缓存清除测试 resolvectl flush-caches 后重新查询 ❌ 清除前后 google.com 均返回 136.109.60.113
缓存统计 resolvectl statistics Cache Hits=7, Misses=22, Size=2 — 正常
Source 验证 查询结果显示 Data from: network（清除后首次） 来自上游，非缓存

❌ 排除：非缓存污染问题，结果直接来自上游 DNS。

证据来源：kuafu_T1_20260601_210025.md — 1.3 节、1.4 节

假设 B：DNS 劫持/投毒

🧪 假设：网络路径中存在中间人拦截 DNS 请求，返回伪造结果

检查项 操作 结论
对比多 DNS 路径 dig @10.255.255.254 vs dig @8.8.8.8 vs dig @10.1.20.30 三个路径返回三个不同 IP！
tcpdump 抓包 tcpdump -i any port 53 -c 15 -n 捕获两条独立 DNS 路径
伪造 IP 溯源 host 136.109.60.113 bc.googleusercontent.com ✅ 真实 GCP IP，非投毒
运营商 DNS 溯源 host 221.5.88.88 cache1-gd.cnc-gd.net ✅ 中国联通广东 DNS 缓存

🟡 部分确认：

  • ✅ WSL 代理路径（10.255.255.254 → Windows → 联通 DNS）确实返回了与直连 8.8.8.8 不同的结果
  • ✅ 联通 DNS 对境外域名进行选择性劫持（返回指向代理服务器的 IP）
  • ⚠️ 但"劫持"的 IP 本身也是合法 IP（GCP 实例），非恶意投毒，更像运营商层级的透明代理/缓存

证据来源：kuafu_T3_20260601_205422.md — 1.2 节、2.3 节、2.4 节

假设 C：systemd-resolved 配置异常

🧪 假设：resolved 的配置导致查询路径异常

检查项 操作 结论
resolvectl 状态 resolvectl status DNS Server: 10.255.255.254, mode: foreign
resolv.conf 检查 readlink -f /etc/resolv.conf → /mnt/wsl/resolv.conf（非 stub-resolv.conf）
/etc/wsl.conf cat /etc/wsl.conf 缺少 [network] 段，无 generateResolvConf = false
resolved.conf cat /etc/systemd/resolved.conf 全默认值，无自定义配置
历史配置 journalctl -u systemd-resolved 发现 eth0 曾被设为 127.0.0.54（不可达），已 revert

✅ 确认：配置存在多项异常：

  1. /etc/resolv.conf 指向 WSL 文件而非 stub-resolv.conf → 部分应用绕过 systemd-resolved
  2. resolv.conf mode: foreign → systemd-resolved 未管理本机 DNS 配置
  3. eth0 DefaultRoute = no → DNS 作用域异常
  4. 历史问题（127.0.0.54）已修复但体现了配置的脆弱性

证据来源：kuafu_T2_20260601_205947.md — 2.2 节、2.3 节、2.5 节、2.6 节、2.7 节

假设 D：时间同步导致缓存异常（加剧因素 ✅ 确认）

🧪 假设：systemd-timesyncd 频繁校正时钟导致 systemd-resolved 反复清空缓存

检查项 操作 结论
Clock change 计数 journalctl -u systemd-resolved | grep "Clock change detected" | wc -l 656 次
时间分布 查看日志时间戳 2026-05-25 ~ 2026-06-01 持续发生，间隔 30s~数分钟
NTP 状态 timedatectl timesync-status Offset +2.155s, Jitter 1.81s, Poll interval 32s
因果链验证 逻辑推演 timesyncd 校正时钟 → resolved 检测到变化 → 清空缓存

✅ 确认：WSL2 时间同步机制异常导致 DNS 缓存被高频清空（656次），是造成"间歇性不一致"感知的主要加剧因素。

证据来源：kuafu_T2_20260601_205947.md — 2.11 节、2.12 节

五、根因定位

主要根因：中国联通 DNS 运营商层级的 DNS 劫持/透明代理

维度 描述
根因类型 外部网络因素（运营商 DNS 劫持）
触发链路 WSL 应用 → resolvectl → systemd-resolved(127.0.0.53) → WSL DNS 代理(10.255.255.254) → Windows DNS → 中国联通 DNS(221.5.88.88)
劫持行为 联通 DNS 对 google.com、youtube.com、facebook.com、twitter.com 等境外域名，返回指向 GCP 代理实例（136.109.60.113 等）的伪造 IP
国内域名 baidu.com、github.com、qq.com 等正常返回真实 IP
证据力度 🟢 高置信 — tcpdump 直接捕获、多域名交叉验证、IP 溯源确认为 GCP 实例

加剧因素：WSL2 时间同步抖动导致 DNS 缓存高频清空

维度 描述
根因类型 系统配置缺陷
触发机制 systemd-timesyncd 每 32 秒轮询 → 检测到 Offset +2.155s → 校正时钟 → systemd-resolved 检测到 Clock change → 清空全部缓存
影响 累计 656 次清空，DNS 缓存间歇性失效，造成"不一致"的用户感知
证据力度 🟢 高置信 — journalctl 直接计数，时间链完全吻合

次要因素：systemd-resolved 配置缺陷

# 配置问题 影响
1 /etc/resolv.conf → /mnt/wsl/resolv.conf（非 stub-resolv.conf） 部分应用绕过 systemd-resolved，使用不同 DNS 路径
2 resolv.conf mode: foreign systemd-resolved 未管理系统 DNS 配置
3 /etc/wsl.conf 缺少 [network] 段 WSL 持续自动生成 resolv.conf，无法手动控制
4 eth0 DefaultRoute = no DNS 作用域异常
5 上游 DNS 10.255.255.254 不支持 EDNS0 功能降级（UDP 替代 UDP+EDNS0）

六、影响评估

维度 评估
业务影响 中低 — 返回的 IP 均为真实合法 IP（GCP 实例），不影响基本网络连通性；但可能导致境外服务的 CDN 调度异常、时延增加
间歇性表现 用户感知的"不一致"由两种机制共同导致：① 联通 DNS 劫持（主要）② 缓存高频清空导致的时序差异（加剧）
安全隐患 低 — 未发现恶意 DNS 投毒或 MITM 攻击证据；运营商 DNS 劫持/透明代理属于已知的网络运营行为
稳定性影响 高 — TCP DNS 查询通过 10.255.255.254 代理会导致 WSL 实例崩溃（应用/SSHD 断开），属于严重缺陷
受影响域名 google.com、youtube.com、facebook.com、twitter.com 等境外域名
未受影响域名 baidu.com、github.com、qq.com、weibo.com 等国内及部分境外域名

七、修复方案

7.1 应急处置

步骤 操作 执行人 预计时间 效果
1 在 WSL2 中手动指定 DNS 服务器：sudo resolvectl dns global 8.8.8.8 1.1.1.1 运维/用户 即时 ⚠️ 临时绕过 WSL DNS 代理，但重启 WSL 后失效
2 配置 /etc/wsl.conf 禁用 WSL DNS 自动生成，设置固定 DNS 运维/用户 5 分钟 🟢 持久生效

应急命令（立即执行）

bash 
# 方式 A：临时绕过（即时生效，重启失效）
sudo resolvectl dns global 8.8.8.8 1.1.1.1
sudo resolvectl domain global ~.
sudo resolvectl default-route eth0 true

# 验证
resolvectl query google.com  # 应返回与 dig @8.8.8.8 一致的结果

# 方式 B：在 WSL 中手动覆盖 resolv.conf
sudo tee /etc/wsl.conf << 'EOF'
[boot]
systemd=true

[network]
generateResolvConf = false

[user]
default=wyh
EOF

sudo rm -f /etc/resolv.conf
sudo tee /etc/resolv.conf << 'EOF'
nameserver 8.8.8.8
nameserver 1.1.1.1
EOF

⚠️ WSL TCP DNS 崩溃风险规避

由于 TCP DNS 查询通过 10.255.255.254 代理会导致 WSL 实例崩溃，在修复前 禁止使用 dig @10.255.255.254 +tcp 等方式进行 DNS 测试。

7.2 永久修复计划

修复措施 负责人 优先级 完成时间

B2. 考虑增大 PollIntervalMinSec / PollIntervalMaxSec 以减少 NTP 轮询频率 运维 P2 待定
