## 三、排查过程

### 3.1 初始现象

- **故障描述**：WSL2 Ubuntu 22.04 上自定义 DNS 服务器（127.0.0.1:5353）对带 EDNS0 OPT 记录的 UDP 查询返回 TC=1 截断响应，无任何应答记录。
- **用户侧表现**：
  - `dig @127.0.0.1 -p 5353 +bufsize=4096 +ignore +notcp cloudflare.com ANY` → `flags: qr tc ra; ANSWER: 0`
  - `resolvectl query cloudflare.com` → 正常返回（resolved 绕过问题路径）
  - 无 EDNS0 的 `dig +noedns` 查询 → 正常返回完整结果
  - TCP 方式 `dig +tcp +bufsize=4096` → 正常返回

### 3.2 假设驱动排查

#### 假设 A：iptables / 防火墙拦截 EDNS0 数据包

> 🧪 假设：本地防火墙规则过滤了携带 OPT 记录的 UDP 包，导致服务器无法正常处理

| 检查项 | 操作 | 结论 |
|--------|------|------|
| iptables 规则检查 | `iptables -L -n` 查看所有链 | ✅ 无任何规则，所有链默认 ACCEPT |

**❌ 排除**：iptables 未配置任何规则，不是防火墙导致的截断。

---

#### 假设 B：UDP 数据包过大导致网络层分片/丢弃

> 🧪 假设：EDNS0 扩展后的 UDP 包超过路径 MTU，被中间网络设备丢弃

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 回环接口 MTU | `ip link show lo`（默认 65536） | ✅ 回环接口 MTU 足够大，不会分片 |
| 服务器抓包确认 | 服务器日志显示明确收到了 EDNS0 请求 | ✅ 服务器成功接收并解析了请求 |

**❌ 排除**：回环接口无 UDP 分片问题，且服务器明确收到了请求包。

---

#### 假设 C：上游 DNS（8.8.8.8:53）不支持 EDNS0 或截断响应

> 🧪 假设：8.8.8.8 返回了截断响应，自定义服务器原样透传

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 服务器日志分析 | 日志显示服务器**未经上游查询**直接本地返回 `EDNS0 -> TC=1 (55b)` | ✅ 截断发生在本地，非上游返回 |

**❌ 排除**：服务器日志证实截断由自定义服务器自身产生，未向上游 8.8.8.8 转发查询。

---

#### 假设 D：自定义 DNS 服务器主动截断 EDNS0 ✅ 确认根因

> 🧪 假设：`/opt/dns-test/edns0_server.py` 在代码层面主动检测 EDNS0 OPT 并返回 TC=1

**Step 1 — 复现 EDNS0 UDP 故障**

```bash
dig @127.0.0.1 -p 5353 +bufsize=4096 +ignore +notcp cloudflare.com ANY
# → flags: qr tc ra; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 0
#   TC=1 确认截断，应答记录数为 0
```

**Step 2 — 对照组：无 EDNS0 UDP 查询正常**

```bash
dig @127.0.0.1 -p 5353 +noedns +short cloudflare.com ANY
# → HINFO "RFC8482" "" + RRSIG ✅
```

**Step 3 — 对照组：EDNS0 TCP 查询正常**

```bash
dig +tcp @127.0.0.1 -p 5353 +bufsize=4096 +short cloudflare.com ANY
# → HINFO + RRSIG ✅
```

**Step 4 — 服务器日志确认行为**

```
[EDNS0] UDP (...) No-EDNS0 -> OK (91b)   ← 无 EDNS0 → 正常转发
[EDNS0] UDP (...) EDNS0 -> TC=1 (55b)    ← 有 EDNS0 → 直接截断
[EDNS0] TCP (...) relay (163b)           ← TCP → 正常中继
[EDNS0] UDP (...) EDNS0 -> TC=1 (55b)    ← 有 EDNS0 → 直接截断（复现）
```

**✅ 结论：自定义 DNS 服务器源码 `/opt/dns-test/edns0_server.py` 在 UDP 处理分支中显式检测 EDNS0 OPT 伪记录（Type 41），命中后直接返回 TC=1 截断响应，未实现 EDNS0 协议的正向转发或协商支持。TCP 处理分支不受影响，因为 EDNS0 在 TCP 中是透传的中继转发。**

### 4.3 修复核心原理

EDNS0（RFC 6891）是 DNS 的扩展机制，允许在 UDP 查询中附加 OPT 伪记录以协商支持 DNSSEC、更大的 UDP 包（超过 512 字节）、DNS Cookie 等功能。正确实现应做到：

1. **识别 OPT 记录**：解析 UDP 查询中的附加区段，检测 Type 41（OPT）
2. **转发或处理**：将完整的查询（含 OPT 记录）转发给上游 DNS 服务器
3. **返回完整应答**：将上游返回的带 EDNS0 扩展的应答原样返回给客户端

当前服务器在步骤 1 后跳到了错误的逻辑分支（返回 TC=1），而非正常转发。
