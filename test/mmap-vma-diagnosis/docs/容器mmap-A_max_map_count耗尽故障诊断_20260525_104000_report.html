三、排查过程

排查逻辑：提出假设 → 收集证据 → 验证或排除 → 逐步收敛到根因

3.1 初始现象

  • 故障注入程序持续调用 mmap() 创建匿名映射，流程中断于 mmap 返回 ENOMEM
  • 容器内 mmap 相关操作失败，错误信息："Cannot allocate memory"
  • 进程 PID 7 处于 R（运行）状态但 mmap 调用持续失败

3.2 假设驱动排查

假设 A1：vm.max_map_count 耗尽 ✅ **确认根因**

🧪 假设：容器 vm.max_map_count 配置过低，进程创建大量匿名 mmap 后达到上限，后续 mmap 调用被内核拒绝。

检查项 操作（基于诊断结果） 结论
VMA 当前数量 /proc/7/maps | wc -l → 26 当前未被占满，但之前可能已耗尽
vm.max_map_count 5000（容器配置） 远低于默认 65530
VmPeak / VmSize 376 GB 证明进程曾分配了海量匿名映射
VmRSS 仅 1.4 MB overcommit 特性，无实际内存压力
非自愿上下文切换 55（远超自愿的 6） 系统调用频繁被抢占，与 mmap 失败重试行为一致

✅ 结论：vm.max_map_count=5000 耗尽是 mmap ENOMEM 的直接原因。进程持续创建匿名 mmap，VMA 数量曾达到上限 5000，后续 mmap() 调用被内核拒绝。

Counterfactual 验证：若将 max_map_count 设置为 262144，按进程行为模式（匿名 mmap），在达到 376 GB VmPeak 前不会撞到上限限制，mmap ENOMEM 不会发生。

假设 A2：物理内存不足/overcommit 限制 ❌ 排除

🧪 假设：系统物理内存不足或 overcommit 策略限制了 mmap 分配。

检查项 操作（基于诊断结果） 结论
VmRSS 仅 1.4 MB 实际物理内存占用极低
cgroup memory.max max（无限制） 无容器内存上限
容器内存使用 ~4.5 MB 物理内存充裕
进程状态 R（运行中） 未触发 OOM killer

❌ 排除：若为物理内存不足，376 GB 虚拟分配过程中应触发 OOM-killer 终止进程，但进程存活且 VmRSS 极低。overcommit 模式下内核允许超分配。确认排除。

假设 A3：文件描述符耗尽 ❌ 排除

🧪 假设：进程打开过多文件导致 mmap 因 ENFILE/EMFILE 失败。

检查项 操作（基于诊断结果） 结论
FD 数量 3 极低，远未达到 ulimit 上限
映射类型 匿名映射（MAP_ANONYMOUS） 匿名 mmap 不需要 fd 参数

❌ 排除：匿名 mmap 不依赖文件描述符，且 FD=3 说明 fd 资源充裕。确认排除。

假设 A4：mlock 超限 ❌ 排除

🧪 假设：进程尝试 mlock 超过 RLIMIT_MEMLOCK 限制导致 ENOMEM。

检查项 操作（基于诊断结果） 结论
VmLck 0 kB 未锁定任何内存页
映射性质 普通匿名映射 未使用 MAP_LOCKED 标志

❌ 排除：mlock 超限只影响 mlock()/mlockall() 系统调用，不影响普通 mmap。VmLck=0 直接证明未涉及 mlock。确认排除。

假设 A5：overcommit 严格模式（vm.overcommit_memory=2）❌ 排除

🧪 假设：vm.overcommit_memory=2 且 overcommit 额度已用完。

检查项 操作（基于诊断结果） 结论
VmPeak 376 GB 若 overcommit=2，在普通硬件上无法分配如此大量虚拟地址
进程存活 存活（状态=R） 如果 overcommit 严格，进程可能在申请过程中被 OOM-kill
当前 VMA 26 进程可以创建新的映射（正被 max_map_count 限制）

❌ 排除：376 GB 的 VmPeak 证明 overcommit 处于宽松模式。若为严格模式，通常在远低于此值时 mmap 就会因超过 commit limit 而失败。确认排除。
