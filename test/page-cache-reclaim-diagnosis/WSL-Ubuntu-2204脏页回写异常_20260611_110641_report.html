三、Dual-Track 分析模型详解

本次诊断采用 Page Writeback（脏页回写路径）+ Memory Reclaim（内存回收节流路径）双轨分析模型，对故障进行全链路溯源。

Track A: Page Writeback — 脏页生成与回写路径

层级 组件 故障时状态 当前状态 结论
L1 应用层 fio buffered write 脏页生成速率 > 回写速率 无 fio 进程运行 fio 写入速率超过系统排空能力
L2 页缓存层 Dirty pages 124 MB 232 KB 已排空
L2 页缓存层 Writeback pages 158 MB 0 KB 已排空
L3 回写调度层 pdflush/kworker 5s 间隔唤醒，回写 I/O 排队 空闲 回写机制正常，但吞吐不足
L4 文件系统层 ext4 (data=ordered) ordered 模式增加写延迟 同故障时 结构因素，非根因
L5 块设备层 sdd (VHDX) mq-deadline/none, nr_requests=1584 正常 队列无瓶颈
L6 虚拟化层 Hyper-V 虚拟磁盘 写操作经 ext4.vhdx → Windows NTFS 同故障时 关键瓶颈: VHDX 后端写吞吐受限
L7 物理层 Windows 主机磁盘 未知（不在诊断范围内） 未知 潜在外部因素

Track A 结论: 脏页生成端（fio）速率远超回写排空端（VHDX 虚拟磁盘）的稳态吞吐能力，页缓存层的 Writeback 队列持续堆积至 158MB。

Track B: Memory Reclaim/Throttling — 内存回收与节流路径

阶段 事件 阈值 实际值 触发？
B1 Background writeback 唤醒 dirty_background_ratio=1% (~160MB) Dirty=124MB ✅ 应已触发（Dirty 接近阈值）
B2 后台回写线程执行写 I/O — Writeback=158MB ✅ 已触发，但吞吐不足
B3 balance_dirty_pages 节流 dirty_ratio=2% (~320MB) Dirty+Writeback=282MB ✅ 已触发（逼近硬阈值）
B4 进程进入 D 状态 — fio D 状态 ✅ 已发生（用户报告）
B5 系统 hung task / 强制重启 — journal 损坏 ✅ 已发生（T1/T3 证据）

Track B 结论: 极低的 dirty_background_ratio=1% 导致回写过早启动，但 VHDX 虚拟磁盘无法消化 I/O 压力；脏页持续积累至 dirty_ratio=2% 硬阈值附近，触发 balance_dirty_pages 写节流，fio 进程被强制进入 D 状态等待。

四、排查过程

4.1 初始现象

  • 用户报告: fio 执行 buffered write 时 Dirty=124MB、Writeback=158MB 持续堆积不退
  • 进程状态: fio 处于 D 状态（不可中断睡眠，被回写节流阻塞）
  • 参数异常: dirty_ratio=2%（默认 20%）、dirty_background_ratio=1%（默认 10%）
  • 系统环境: WSL Ubuntu 22.04 on Windows，内核 6.18.33.1-microsoft-standard-WSL2

4.2 假设驱动排查

假设 A：脏页参数配置为持久化配置 → 根因因素之一 ✅ 部分确认

🧪 假设：dirty_ratio=2% 是系统有意配置的持久化设置

检查项 操作 结论
/etc/sysctl.conf grep dirty ✅ 未找到 dirty 配置
/etc/sysctl.d/* grep dirty ✅ 所有文件均无 dirty 配置
/etc/rc.local 存在性检查 ✅ 文件不存在
当前 sysctl 值 sysctl -a | grep dirty ✅ 已恢复默认 20%/10%

✅ 结论：dirty_ratio=2% 为临时 sysctl -w 设置，非持久化配置。系统重启后丢失。 但该参数在故障期间是导致节流过早触发的直接原因之一。

假设 B：回写吞吐瓶颈在 VHDX 虚拟磁盘 → 根因因素之二 ✅ 确认

🧪 假设：WSL2 VHDX 虚拟磁盘的稳态写吞吐低于 fio 脏页生成速率

检查项 操作 结论
块设备类型 lsblk ✅ sdd 为 VHDX 虚拟磁盘
IO 调度器 cat /sys/block/sdd/queue/scheduler ✅ none (blk-mq 默认)
队列深度 nr_requests ✅ 1584，充足
磁盘旋转标记 rotational ✅ 1（被标记为机械盘）
写缓存 write_cache ✅ write back（支持回写缓存）

BDI 限制 max_ratio/max_bytes ✅ 100% / ~3GB，无限制

✅ 结论：块层队列参数无配置瓶颈，但 VHDX 虚拟磁盘后端（ext4.vhdx 文件 → Windows NTFS）引入额外写延迟，稳态写吞吐较低。Idle 状态下写吞吐仅 ~313KB/s，远低于 fio 缓冲写生成速率。

假设 D：内存不足导致回收压力 → 已排除

五、关键证据链

证据 1：dirty 参数异常与恢复（T1 报告）

参数 故障时值 当前值 内核默认 解释
dirty_ratio 2% 20% 20% 被临时调低至默认值的 1/10

dirty_expire_centisecs — 3000 3000 默认未改
dirty_writeback_centisecs — 500 500 默认未改

结论: 故障期间 sysctl 参数为非持久化临时设置，重启后丢失。

证据 2：脏页堆积 vs 阈值推算

指标 故障时值 当前值
Dirty 124 MB (~31744 pages) 232 KB (79 pages)
Writeback 158 MB (~40448 pages) 0 KB
脏页总量 (Dirty+Writeback) 282 MB 232 KB
全局脏页阈值 @2% ~320 MB —
全局脏页阈值 @20% — ~3.0 GB

推算: 故障时(16GB 内存 × 2% = 320MB)，脏页总量 282MB 已达到阈值的 88%，balance_dirty_pages 节流已激活。若采用默认 20%（~3.0GB），282MB 仅占阈值的 9%，完全不会触发节流。

证据 3：VHDX 虚拟磁盘写性能瓶颈（T2 报告）

发现 详情 影响
写操作多层穿越 ext4 → 块层 → Hyper-V 虚拟磁盘 → Windows VHDX → NTFS 每层增加延迟
Idle 写吞吐 ~313 KB/s (iostat 采样) 极低，无法支撑大量 dirty 刷出
rotational=1 被标记为机械盘，影响 IO 合并策略 可能降低写吞吐
data=ordered ext4 ordered 模式需要数据先于元数据落盘 增加写延迟
无 SMART 监控 VHDX 虚拟设备不支持 smartctl 无法直接检测磁盘健康

结论: WSL2 虚拟磁盘架构是写吞吐的硬性天花板。

证据 4：系统非正常关闭（T1/T3 报告）

dmesg 日志:
- system-journal corrupted or uncleanly shut down
- user-1000.journal corrupted or uncleanly shut down

结论: 系统在故障期间经历了非正常关闭/强制重启，journal 文件损坏。这解释了为什么当前诊断时故障现场已丢失。

证据 5：节流计数器清零（T1 报告）

计数器 当前值 含义
