#### 假设 C：内核水位线参数配置不当 ✅ 确认根因

> 🧪 假设：`min_free_kbytes` 和 `watermark_scale_factor` 的非默认值组合导致水位线过低

**Step 1 — 确认当前参数与用户报告参数的差异**

**Step 2 — 计算水位线差异**

## 五、深度技术分析

### 5.1 水位线机制回顾

Linux 内存管理使用三个水位线（watermark）控制回收行为：

```
高水位 (high)  ──────  kswapd 停止扫描
  │
低水位 (low)   ──────  kswapd 被唤醒开始回收
  │  ← watermark_scale_factor 控制 low↔high 间距
最低水位 (min) ──────  触发直接回收（Direct Reclaim），分配线程同步等待
  │  ← min_free_kbytes 决定 min 水位
  ↓
  (OOM)         ──────  彻底无法分配 → OOM Killer
```

**正常情况下**（min_free_kbytes=45056, watermark_scale_factor=10）：
- low→min 间距 ≈ 4620 pages（~18 MB）→ kswapd 有充足时间回收
- 直接回收极少触发

**故障组合下**（min_free_kbytes=8192, watermark_scale_factor=1）：
- low→min 间距 ≈ 62 pages（~248 KB）→ 几乎无缓冲
- kswapd 刚被唤醒，水位就跌破了 min → 直接回收频繁触发

### 5.2 WSL 环境特殊性

- WSL2 使用 Hyper-V 虚拟机，内存分配策略与裸金属 Linux 存在差异
- 内核 6.18.33.1-microsoft-standard-WSL2 是微软定制内核，但水位线机制与主线一致
- WSL 重启会重置内核参数为默认值，这一行为在本案例中起到了恢复作用
