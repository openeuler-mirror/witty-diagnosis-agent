# 诊断报告 T1：Swap Thrashing 验证

## 故障概要
- **故障模式**: Swap Thrashing（容器 cgroup 级内存抖动）
- **置信度**: 高
- **分析轨道**: 现场指标（单轨，WSL2 环境无内核源码）
- **内核版本**: 6.6.87.2-microsoft-standard-WSL2 #1 SMP PREEMPT_DYNAMIC Thu Jun 5 18:30:46 UTC 2025 x86_64
- **任务 ID**: T1
- **诊断时间**: 2026-05-22 20:42 CST (2026-05-22T12:42:00Z)
- **执行路径**: localhost（WSL2 宿主机）

---

## 故障现象

用户报告 **容器 `swap-thrash-test` 卡死无响应，宿主机系统响应极慢**。

实际观察到：
1. 容器 `swap-thrash-test` 处于 `Up` 状态约 3 分钟，但进程处于活跃争抢状态
2. 宿主机 vmstat 显示 **r（runnable 进程）: 4~10**, **b（blocked 进程）: 1~3**
3. 系统 CPU iowait 高达 **13~14%**
4. Docker stats 显示容器 CPU 占用 **165%**，内存 **99.85%（255.6MiB/256MiB）**

---

## 触发原因（直接根因）

### 容器 cgroup 内存限制导致的 Thrashing

**容器配置：**
```
stress-ng --vm 4 --vm-bytes 384M --vm-method all --page-in --timeout 300s --vm-keep
```
- 4 个 VM stressor 各自试图分配 **384MB**（合计 1.5GB）
- `--page-in`：强制页错误，主动换入页面
- `--vm-keep`：保持页面常驻，不释放

**cgroup 限制：**
| 参数 | 值 |
|------|-----|
| memory.max (容器 RAM 上限) | 256MB (268,435,456 bytes) |
| memory.swap.max (容器 Swap 上限) | 256MB (268,435,456 bytes) |
| 合计内存+swap 上限 | 512MB |

**矛盾点：** workload 需要 1.5GB > 容器上限 512MB，强行压缩工作集。

**关键计数器：**
| 指标 | 值 | 含义 |
|------|-----|------|
| memory.events -> max | **119,059 次** | 容器命中内存上限的次数（极高） |
| memory.swap.events -> fail | **31 次** | swap 上限失败次数 |
| memory.swap.current | **180MB** | 容器 swap 使用量 |
| workingset_refault_anon | **5,854,905 次** | 匿名页被换出后又立即被换入（thrashing 标志） |

---

## 传播路径

```
[触发]        容器 stress-ng 尝试分配 1.5GB
    ↓
[cgroup 限流]  memory.max = 256MB → 内存分配失败
    ↓
[内核行为]     ① 水位线检查失败 → 唤醒 kswapd 进行 reclaim
               ② shrink_lruvec() 扫描匿名页 → swap_writepage() 换出至磁盘
               ③ 但 stress-ng --page-in 立即触发 do_swap_page() → swap_readpage() 换入
               ④ 循环：换出 → 立即换入 → 再换出 → 再换入 → ...
    ↓
[异常指标]     si ≈ 55K~87K pages/s, so ≈ 48K~86K pages/s（阈值 1000 pages/s）
               pgmajfault: 2,651,409（大量主缺页）
               pgscan_anon: 19,722,068（大量匿名页扫描）
               nr_vmscan_write: 6,301,143（数百万页面被写回 swap）
               workingset_refault_anon: 6,403,191（系统级 refault，严重 thrashing）
               pgrotated: 6,299,926（页面刚扫描到 LRU 末尾又立即被访问）
    ↓
[系统表现]     iowait ≈ 14%（swap 设备 IO 饱和）
               进程 D 状态（等待 IO 完成）
               CPU us+sy ≈ 30%（内核回收开销）
               系统响应极慢，吞吐几乎为零
```

## 内核语义轨道结论

（WSL2 环境，无内核源码，基于指标推理）

| 维度 | 发现 |
|------|------|
| 内核版本 | 6.6.87.2-microsoft-standard-WSL2 |
| swappiness | 60（默认值） |
| 关键配置 | CONFIG_MEMCG=y（cgroup v2 内存限制生效中） |
| 异常行为 | cgroup 存储控制器在 256MB 硬限制下不断回收匿名页，但 stress-ng 的 `--page-in` 立即触发 page fault 重新换入，形成无限 thrashing 循环 |
| 根因类型 | **cgroup 限制 + 应用工作集超限** |
| 触发条件 | 容器 cgroup memory.max 设为 256MB，但内部进程工作集需求远超此值 |
| 因果链 | [stress-ng 分配 1.5GB] → [cgroup memory.max=256MB 截断] → [内核 kswapd 持续回收匿名页] → [--page-in 立即触发缺页换入] → [换出换入无限循环] → [si/so 超 100K pages/s] → [iowait 14% + 进程 D 状态] |

| 假设 | 排除原因 |
|------|---------|
| 系统全局内存不足 | MemAvailable = 5.3GiB / 7.4GiB，系统级内存充足 |

## 完整因果链

```
[触发] Docker 容器 swap-thrash-test 运行 stress-ng --vm 4 --vm-bytes 384M --page-in --vm-keep
  → workload 内存需求 1.5GB >> 容器 cgroup memory.max = 256MB
  → 内核内存分配器进入直接回收路径
  → kswapd 和 direct reclaim 扫描匿名页 LRU 链表
  → swap_writepage() 将匿名页写入 swap 设备 (/dev/sdc)
  → stress-ng --page-in 立即触发 do_swap_page() → swap_readpage() 重新读入
    ↻ 循环：换出 → 立即换入 → 再换出（Thrashing 锁定）
  → si/so 速率达 50K~87K pages/s（阈值 60~80 倍）
  → pgmajfault 265 万次，workingset_refault 640 万次
  → swap 设备 IO 饱和，iowait 飙升至 14%
  → 进程大量陷入 D 状态等待 IO
  → 系统响应极慢，业务几乎停滞
```

## 修复建议

### 最小修复（立即可做）
```bash
# 停止问题容器（thrashing 立即消除）
docker stop swap-thrash-test

# 或调整容器内存限制（增大后重启）
# docker update --memory 2g --memory-swap 3g swap-thrash-test
```

### 根本修复（设计层面）
1. **增大容器 cgroup memory 限制**：将 `--memory` 从 256MB 提升至应用实际需求（建议至少 2GB）
2. **移除 `--vm-keep` 和 `--page-in` 参数**：这两个参数主动制造 thrashing，正常情况下不应使用
3. **设置合适的 swappiness**：如果宿主机以容器为主，可将 swappiness 调低至 10~20，减少匿名页换出倾向：
   ```bash
   sysctl -w vm.swappiness=10
   ```
4. **使用 zswap 缓解 swap IO 压力**：对 swap 设备启用压缩，减少物理 IO

---

## 验证建议

1. **操作前验证**：确认当前 si/so 速率 > 1000 pages/s
2. **操作后验证**：
   - `docker stop swap-thrash-test` 后观察 vmstat，si/so 应在 30 秒内降至接近 0
   - iowait 从 14% 回落至正常水平（< 2%）
   - 系统响应恢复
3. **长期监控**：使用 `check_thrashing.sh` 脚本定期检测 si/so 速率
