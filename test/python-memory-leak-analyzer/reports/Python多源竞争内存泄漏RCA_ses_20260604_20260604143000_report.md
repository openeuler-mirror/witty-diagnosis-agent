### 3.2 假设驱动排查

#### 假设 A：Python retained leak (LISTENERS 全局注册表) ✅ 确认主根因

> 🧪 假设：模块级全局变量 `LISTENERS` 以强引用持有 bound method，阻止 LargeTenant 实例被 GC 回收

| 检查项 | 操作 | 结论 |
|--------|------|------|
| **语义信号（semantic.json）** | LISTENERS 语义信号: `global_registry_retains_bound_methods`，len: 0→600，score=645 | **✅ 强烈信号** — 全局注册表以强引用持有 bound method |
| **保留链（retention.json）** | LargeTenant 实例 → `bound method LargeTenant.callback` → `builtins.list [LISTENERS]` | **✅ 保留链确认** — LISTENERS 是顶层保留者 |
| **静态可达性** | 清除前 600 个候选，清除后 600 个（reclaim_ratio=0%） | ⚠️ 静态分析无法确认回收，需反事实 |
| **反事实验证（G3）** | 清空全局 `LISTENERS` 列表后，600 个候选对象**全部回收**（reclaimed_ratio=1.0） | **✅ 强证据** — verdict=`counterfactual_confirmed`, confidence=`strong` |

**✅ 结论：LISTENERS 全局注册表是主导泄漏源** — `register_listener()` 将 bound method 追加到模块级列表，但没有任何机制在 LargeTenant 实例销毁时执行 `unregister`，导致 bound method 通过 `__self__` 强引用持有整个 LargeTenant 实例，形成完整的泄漏保留链。

---

#### 假设 B：Python retained leak (tenant_lookup 无界缓存) ⚠️ 确认次要泄漏源

> 🧪 假设：`@lru_cache(maxsize=None)` 装饰的函数因无大小上限，导致缓存条目不断累积

| 检查项 | 操作 | 结论 |
|--------|------|------|
| **语义信号（semantic.json）** | `unbounded_cache_growth`，currsize: 0→600，score=600 | **✅ 强烈信号** — 无界缓存语义 |
| **缓存增长（object_growth.json）** | `tenant_lookup` currsize_delta=600, maxsize=None, unbounded=true | **✅ 确认无界** |
| **分配热点（tracemalloc.json）** | `multi_source_mismatch.py:23` — cache 构建，+12,312,600 字节（11.74 MiB） | **✅ 最大分配点** — 占 tracemalloc 总增长的 52% |
| **保留链（retention.json）** | retention 链仅指向 LISTENERS，未指向 tenant_lookup | **⚠️ 无独立保留链证据** — 无法确认 cache 条目本身是否被强引用保留 |

- **tracemalloc 说明**: 分配点不等于保留点。`multi_source_mismatch.py:23`（cache 构建）的 11.74 MiB 是**分配量最大**的位置，但保留链只指向 LISTENERS。这意味着 cache 数据可能是 LargeTenant 初始化时生成的大字符串/数据，被 LargeTenant 实例持有，而 LargeTenant 实例又被 LISTENERS 通过 bound method 保留。

**⚠️ 结论：tenant_lookup 是次要泄漏源** — 语义信号明确指示无界缓存增长，但缺少独立保留链证据。当前最佳解释是：cache 数据作为 LargeTenant 实例的属性被创建，而 LargeTenant 实例被 LISTENERS 全局列表保留，因此 cache 消除需要等 LISTENERS 修复后才能完全确认独立贡献量。

### 5.2 最小修复（LISTENERS — 主导泄漏源）

为 `LargeTenant` 添加销毁时的 unregister 机制，或改用弱引用注册表：

```python
# 方案 A：在 LargeTenant 析构时主动执行

# LISTENERS.append(weakref.WeakMethod(self.callback))
# 注意：需要确保 callback 在被调用时 WeakMethod 仍然存活
```

### 5.3 根本修复（tenant_lookup — 竞争泄漏源）


| 修复措施 | 优先级 | 负责人 | 完成时间 |
|--------|--------|--------|--------|
| LISTENERS 增加 WeakMethod 或 unregister 机制 | P0 - 必须 | 待定 | 待定 |
| tenant_lookup 设置 maxsize 或引入淘汰策略 | P1 - 建议 | 待定 | 待定 |
| SMALL_GLOBAL 限制大小或移除 | P3 - 可忽略 | — | — |
| 修复后联合复测（G4 隔离复测） | 验证 | 待定 | 修复后立即执行 |

### 5.6 风险

- 使用 `WeakMethod` 后需确认回调在被调用时仍然可用（weakref 未回收）
- 设置 `maxsize` 后需评估业务缓存命中率影响，避免因缓存淘汰引入性能退化
- 两个泄漏源存在交互：cache 数据作为 LargeTenant 实例的属性，修复 LISTENERS 后有助于更准确量化 tenant_lookup 的独立贡献
