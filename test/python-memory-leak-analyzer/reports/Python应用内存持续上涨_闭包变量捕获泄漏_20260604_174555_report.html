三、排查过程

3.1 初始现象

  • 监控/证据发现：discovery.json 注册 rss_growth_observed，RSS 存在净增长，未呈现平台效应
  • 能力画像：环境缺少 psutil/objgraph/pympler/memray 等扩展库（stdlib-only 降级模式），但核心证据链完整
  • tracemalloc 总分配增长：3,702,040 bytes（3.531 MiB），Python 堆可完全解释 RSS 增长量级

3.2 假设驱动排查

假设 A：闭包变量捕获泄漏（T1 — 主假设）

🧪 假设：每次调用 make_handler() 创建闭包时捕获的 payload 字典因被全局 TASK_TABLE 持有而无法回收

检查项 操作（证据来源） 结论
RSS 持续增长 discovery.json rss_growth_observed ✅ 确认 RSS 净增长
分配热点 tracemalloc.json — 热点 Top 1: closure_capture_leak.py:10，3.100 MiB（占 87.8%） ✅ 指向 payload dict 创建行
对象增长 object_growth.json — dict +603, function +600, cell +600, tuple +600 ✅ 增长模式完全对应闭包创建
语义信号 semantic.json — global_table_retains_closures on TASK_TABLE, score=645 ✅ 唯一主导信号，无竞争
保留链 retention.json — 3/3 采样链指向 module_global:TASK_TABLE ✅ 保留路径完全收敛
可达性（反事实） reachability_counterfactual.json — clear TASK_TABLE 后 23.9% 对象回收 ✅ strong confidence

✅ 结论：闭包变量捕获泄漏确认为根因。 保留路径为：

module_global:TASK_TABLE → handler(function) → __closure__[0](cell) → payload(dict)

5.2 永久修复计划

修复措施 说明 优先级 负责人
方案 1：移除不必要的闭包捕获（推荐） 修改 make_handler()，避免闭包捕获 payload。若不需延迟执行，将 payload 处理逻辑移出闭包 ★★★ 最高 开发团队
方案 2：限制 TASK_TABLE 生命周期 任务完成后主动清理：TASK_TABLE.clear() 或 del TASK_TABLE[key] ★★★ 最高 开发团队
方案 3：有界缓存/淘汰策略 改为 OrderedDict + popitem(last=False)，限定最大条目（如 MAX_TASKS=100） ★★☆ 推荐 开发团队
方案 4：弱引用 使用 weakref.ref() 包装 handler，避免 TASK_TABLE 强引用保持 ★☆☆ 可选 开发团队
