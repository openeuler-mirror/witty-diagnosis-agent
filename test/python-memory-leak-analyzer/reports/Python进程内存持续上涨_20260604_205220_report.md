## 三、排查过程

> 排查逻辑：基于只读外部观测，提出假设 → 收集 /proc 证据 → 验证或排除 → 收敛到方向级结论。

### 3.1 初始现象

- **上游任务输入**："Python 进程内存持续上涨"
- **观测目标**：PID 406，live_pid_readonly 场景，仅允许外部只读观测（/proc 文件系统 + Python 标准库）
- **观测窗口**：2026-06-04 12:48:00 ~ 12:48:05（共 2.5 秒，6 个采样点）
- **核心指标**：RSS 从 10.5 MiB ➔ 11.75 MiB，净增长 1.25 MiB，速率 ~523 KiB/s
- **关键限制**：缺失 psutil / objgraph / pympler / memray / gdb / py-spy 等工具，无法 attach 进程或采集内存快照

### 3.2 假设驱动排查

#### 假设 A：Python 托管对象泄漏

> 🧪 假设：PID 406 的 Python 进程中存在全局容器、无界缓存或回调未注销导致对象持续积累。

| 检查项 | 操作 | 结论 |
|--------|------|------|
| object_growth 数据 | 读取 evidence_inputs.object_growth | ❌ null — 未采集（live_pid_readonly 限制） |
| tracemalloc 热力图 | 读取 evidence_inputs.tracemalloc | ❌ null — 未采集 |
| retention_chain | 读取 evidence_inputs.retention | ❌ null — 未采集 |
| semantic_probe | 读取 evidence_inputs.semantic | ❌ null — 未采集 |
| Python heap / Private_Dirty 比值 | 计算关联对账 | ❌ null — 无 Python heap 数据 |

**❌ 无法确认**：缺失所有进程内内省数据，无法将 RSS 增长归因为 Python 托管对象泄漏。按 skill 约束，禁止越级推断。

---

#### 假设 B：C 扩展 / native 分配增长

> 🧪 假设：RSS 增长可能来自 C 扩展（如 ctypes、numpy、Cython）或 malloc arena 高水位。

| 检查项 | 操作 | 结论 |
|--------|------|------|
| Private_Dirty 增长 | monitor_rss_pid.json | ✅ 增长 1.066 MiB，全部在 anonymous 区域 |
| memray / native stack | evidence_inputs.native_leak | ❌ null — 未采集 |
| smaps 详细分析 | 报告目录中缺失逐段 smaps 细节 | ❌ 无数据 |

**⚠️ 方向级疑似** — Private_Dirty 增长可能与 native 分配有关，但无 native 栈证据，无法核实。置信度极低。

---

#### 假设 C：mmap / file-backed / shmem 增长

> 🧪 假设：增长来自文件映射或共享内存。

| 检查项 | 操作 | 结论 |
|--------|------|------|
| RssFile 趋势 | monitor_rss_pid.json | ✅ 净增长 0 bytes — 无增长 |
| RssShmem 趋势 | monitor_rss_pid.json | ✅ 始终为 0 — 无增长 |

**❌ 已排除**：file-backed 和 shmem 无任何增长，可安全排除此路径。

---

#### 假设 D：allocator 高水位 / 平台期 / 预热

> 🧪 假设：增长仅为 allocator arena 复用或短期高水位，并非真正的保留泄漏。

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 观测窗口长度 | analysis_inference.json | ⚠️ 仅 2.5 秒（6 个采样点），判定为 insufficient_window |
| RSS 平台特征 | 增长趋势分析 | ⚠️ 未出现高位平台，也未观察到波动回落 |
| plateau/high-water 判断 | 竞争假设矩阵 | ⚠️ 窗口过短，无法判断是否为缓存预热或 allocator 高水位 |

**⚠️ 无法排除**：极短窗口内看到的线性增长可能是 allocator arena 复用、进程预热期或短期 high-water mark。需要更长观测窗口（分钟级）才能排除此假设。

---

#### 假设 E：短窗口观测偏差

> 🧪 假设：2.5 秒 6 个采样点不足以判断是否为持续泄漏趋势，可能为短期抖动。

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 采样点数 | monitor_rss_pid.json | ✅ 6 个点，窗口 2.5s |
| 趋势一致性 | 线性/阶梯增长 | ✅ 窗口内无回落，增长一致 |

**✅ 最稳妥的保守解释**：当前窗口内观察到的增长趋势一致，但窗口过短，无法断定是否为持续泄漏。这是当前证据条件下最可靠的判断。

---

#### 假设 F：范围失配（子进程 / cgroup 口径）

> 🧪 假设：RSS 增长来自其他子进程或 cgroup 口径不一致。

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 子进程 | discovery.json child_count | ✅ 0 — 无子进程 |
| cgroup 趋势 | monitor_rss_pid.json cgroup memory_current | ✅ 与 PID RSS 同步增长（+0.363 MiB） |

**❌ 已排除**：子进程和 cgroup 口径均可排除。

## 四、修复方案

### 4.1 应急处置（当前阶段）

由于根因尚未确认，应急处置应聚焦于**补充证据采集**，而非直接修复：

| 步骤 | 操作 | 预期效果 |
|------|------|---------|
| 1 | 延长 RSS 观测窗口至 5～10 分钟（使用 monitor_rss.py） | 判断增长是否为持续趋势，排除 allocator 预热假象 |
| 2 | 在可复现 workload 上运行 object_growth.py | 获取 Python 托管对象的类型级增长数据 |
| 3 | 运行 tracemalloc_probe.py | 定位分配热点，识别最大消耗者的调用栈 |
| 4 | 运行 semantic_probe.py | 识别全局容器、无界缓存、回调等语义模式 |
| 5 | 运行 retention_chain.py | 建立保留链，定位阻止 GC 回收的根对象 |
| 6 | 汇总全部证据后运行 correlate_evidence.py | 输出最终 verdict，从 readonly_insufficient 升级 |

### 4.2 永久修复计划（在确认 Python 根因后）

| 修复措施 | 负责人 | 优先级 |
|---------|--------|--------|
| 设置全局容器容量上限、TTL 或淘汰策略 | 应用开发团队 | 高 |
| 检查 `@lru_cache` 是否无界（`maxsize=None`） | 应用开发团队 | 高 |
| 确保请求/任务结束时清理线程局部存储（`threading.local`） | 应用开发团队 | 中 |
| 使用 `weakref` 替代强引用缓存 | 应用开发团队 | 中 |
| 添加 RSS 监控告警（阈值：增长速率 > 100 KiB/s 持续 5 分钟） | SRE 团队 | 高 |

> ⚠️ **风险提示**：在未确认 Python 保留泄漏前实施优化性修复可能投入方向错误。建议优先完成 4.1 节的证据补全流程。

### 4.3 复测方案

- **复现命令**：`bash ./run.sh run-stress live_pid_readonly`（在 `test/python-memory-leak-analyzer/` 下执行）
- **通过条件**：correlation.json 的 verdict 从 `readonly_insufficient` 转变为 `python_retained_leak_likely` 或 `native_or_allocator_suspect`，且 confidence_cap 提升至 weak 或 strong
