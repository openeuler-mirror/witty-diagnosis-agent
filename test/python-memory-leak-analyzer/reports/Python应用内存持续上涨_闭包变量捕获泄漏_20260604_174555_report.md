
## 三、排查过程

### 3.1 初始现象

- **监控/证据发现**：`discovery.json` 注册 `rss_growth_observed`，RSS 存在净增长，未呈现平台效应
- **能力画像**：环境缺少 psutil/objgraph/pympler/memray 等扩展库（stdlib-only 降级模式），但核心证据链完整
- **tracemalloc 总分配增长**：**3,702,040 bytes（3.531 MiB）**，Python 堆可完全解释 RSS 增长量级

---

### 3.2 假设驱动排查

#### 假设 A：闭包变量捕获泄漏（T1 — 主假设）

> 🧪 假设：每次调用 `make_handler()` 创建闭包时捕获的 payload 字典因被全局 TASK_TABLE 持有而无法回收

| 检查项 | 操作（证据来源） | 结论 |
|--------|-----------------|------|
| RSS 持续增长 | `discovery.json` rss_growth_observed | ✅ 确认 RSS 净增长 |
| 分配热点 | `tracemalloc.json` — 热点 Top 1: `closure_capture_leak.py:10`，3.100 MiB（占 87.8%） | ✅ 指向 payload dict 创建行 |
| 对象增长 | `object_growth.json` — dict +603, function +600, cell +600, tuple +600 | ✅ 增长模式完全对应闭包创建 |
| 语义信号 | `semantic.json` — `global_table_retains_closures` on TASK_TABLE, score=645 | ✅ 唯一主导信号，无竞争 |
| 保留链 | `retention.json` — 3/3 采样链指向 `module_global:TASK_TABLE` | ✅ 保留路径完全收敛 |
| 可达性（反事实） | `reachability_counterfactual.json` — clear TASK_TABLE 后 23.9% 对象回收 | ✅ **strong confidence** |

**✅ 结论：闭包变量捕获泄漏确认为根因。** 保留路径为：
```
module_global:TASK_TABLE → handler(function) → __closure__[0](cell) → payload(dict)
```

---

#### 假设 B：全局容器/缓存无界增长（T2 — 竞争假设）

> 🧪 假设：存在独立于闭包泄漏的全局容器或缓存无界增长

| 检查项 | 操作（证据来源） | 结论 |
|--------|-----------------|------|
| `cache_semantics` | `semantic.json` → cache_semantics: `[]` | ✅ 空，无缓存语义 |
| 竞争信号数 | `semantic.json` → competing_signal_count: **0** | ✅ 无竞争 |
| `cache_growth` | `object_growth.json` → cache_growth: `[]` | ✅ 空，无缓存增长 |
| 保留根 | `retention.json` → 唯一 root_kind: `module_global:TASK_TABLE` | ✅ 无独立缓存保留根 |
| 分配热点 | tracemalloc Top 1: 闭包 payload line 10（3.1 MiB），TASK_TABLE 插入仅 0.119 MiB | ✅ 容器自身增长极微 |

**❌ 排除**：TASK_TABLE 增长是闭包泄漏的**表现形式**（持有者），非独立泄漏来源。

---

#### 假设 C：对象引用循环（T3 — 竞争假设）

> 🧪 假设：存在对象间的引用循环导致 GC 无法回收

| 检查项 | 操作（证据来源） | 结论 |
|--------|-----------------|------|
| GC garbage 检查 | `semantic.json` → garbage_len: **0** | ✅ 无不可达循环对象 |
| `__del__` 相关类型 | garbage_type_counts: `{}` | ✅ 无 `__del__` 导致的循环 |
| 对象增长模式 | type_growth 为 function/cell/tuple 同步 +600，非自定义类 | ✅ 不符合循环泄漏特征 |
| 保留链 | retention.json — 无 `cycle` 条目 | ✅ 无循环结构 |
| 可达性 | reachability_static.json → verdict: `static_only` | ✅ 模块全局引用保持，非循环 |

**❌ 排除**：四重证据交叉确认对象引用循环不存在。

### 5.2 永久修复计划

| 修复措施 | 说明 | 优先级 | 负责人 |
|---------|------|--------|--------|
| **方案 1：移除不必要的闭包捕获（推荐）** | 修改 `make_handler()`，避免闭包捕获 payload。若不需延迟执行，将 payload 处理逻辑移出闭包 | ★★★ 最高 | 开发团队 |
| **方案 2：限制 TASK_TABLE 生命周期** | 任务完成后主动清理：`TASK_TABLE.clear()` 或 `del TASK_TABLE[key]` | ★★★ 最高 | 开发团队 |
| **方案 3：有界缓存/淘汰策略** | 改为 `OrderedDict` + `popitem(last=False)`，限定最大条目（如 MAX_TASKS=100） | ★★☆ 推荐 | 开发团队 |
| **方案 4：弱引用** | 使用 `weakref.ref()` 包装 handler，避免 TASK_TABLE 强引用保持 | ★☆☆ 可选 | 开发团队 |

### 5.3 复测验证方案

应用修复后，按以下步骤验证泄漏是否消除：

1. 重新运行压力测试：
   ```bash
   cd test/python-memory-leak-analyzer
   ./run.sh run-stress closure_capture
   ```
2. 检查 `object_growth.json` 中 type_growth 的 count_delta：
   - ✅ 预期：builtins.dict + function + cell 增量趋近于 0（或大幅降低）
   - ❌ 如果仍线性增长，说明根因未完全消除
3. 检查 `tracemalloc.json` 中 top_positive_size_diff_bytes：
   - ✅ 预期：显著低于 3.7 MiB
4. 检查 `semantic.json` 中 dominant_signals：
   - ✅ 预期：无 `global_table_retains_closures` 信号或 score 大幅降低
