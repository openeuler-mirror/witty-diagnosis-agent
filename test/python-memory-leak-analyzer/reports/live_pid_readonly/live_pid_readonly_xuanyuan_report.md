## 三、排查过程

> 排查逻辑：**提出假设 → 收集证据 → 验证或排除 → 逐步收敛到根因**

### 3.1 初始现象

- **RSS 时序监控**显示 PID 425 在 2.5 秒观测窗口内 RSS 从 **10.25 MiB** 持续增长至 **11.25 MiB**（净增长 **1.0 MiB**）
- **Private Dirty** 从 **4.13 MiB** 增长至 **5.19 MiB**（净增长 **1.066 MiB**）
- 增长形态为 **linear_or_step_growth**（线性/阶梯式），RSS 增长率约 **403,849 字节/秒**
- 进程映射结构稳定：6 个匿名映射、7 个文件映射、1 个堆映射、25 个共享库映射（所有采样点一致）

### 3.2 环境边界确认

通过 `capabilities.json` 和 `discovery.json` 确认运行环境：

| 检查项 | 值 | 结论 |
|--------|-----|------|
| 平台 | Linux 6.6.87.2-microsoft-standard-WSL2 (x86_64) | WSL2 环境 |
| Python 版本 | 3.12.3 | 较新版本 |
| ptrace_scope | 1（默认不允许 ptrace） | 限制附加调试 |
| smaps_rollup | 可用 | 支持内存详情 |
| cgroup v2 | memory.current 存在但不可读 | 只读观测 |
| 子进程 | child_count = 0 | 无子进程扩散 |
| 证据发现评分 | 83/100（7 个发现项） | 证据覆盖中等 |

### 3.3 假设驱动排查

#### 假设 A：Python 托管对象泄漏（方向级，未确认）

> 🧪 假设：进程内 Python 对象持续分配但未释放，导致堆内存增长

| 检查项 | 操作 | 结论 |
|--------|------|------|
| RSS 增长特征 | 源自匿名页（rss_anon），与 Python 堆分配行为一致 | ✅ 支持 |
| object_growth.json | **缺失** — 无法判断 Python 对象增长类型和速率 | ❌ 无证据 |
| tracemalloc.json | **缺失** — 无法定位分配热点 | ❌ 无证据 |
| semantic.json | **缺失** — 无法识别语义保留信号 | ❌ 无证据 |
| retention.json | **缺失** — 无法追踪保留链 | ❌ 无证据 |

**❌ 无法确认**：缺少 Python 堆内核心证据，方向合理但无法验证。

---

#### 假设 B：C 扩展 / Native 内存泄漏（方向级，未确认）

> 🧪 假设：C 扩展（如 ctypes、cffi、pybind11）或原生模块存在分配/释放不配对

| 检查项 | 操作 | 结论 |
|--------|------|------|
| Private Dirty 增长 | 无 Python heap 对应证据 | ⚠️ 间接支持 |
| native allocation stack | **缺失** — 无法确认 Native 层分配 | ❌ 无证据 |
| allocator stats | **缺失** — 无法判断分配器行为 | ❌ 无证据 |

**❌ 无法确认**：方向存在可能性，但无 Native 层证据支撑。

---

#### 假设 C：缓存/全局数据结构无界增长（方向级，未确认）

> 🧪 假设：全局缓存、注册表或回调列表持续增长，无淘汰策略

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 增长形态 | 线性增长，符合无界缓存特征 | ✅ 支持 |
| semantic probe | **缺失** — 无法识别全局容器/缓存语义 | ❌ 无证据 |
| retention chain | **缺失** — 无法追踪保留者 | ❌ 无证据 |

**❌ 无法确认**：形态符合，但缺少语义级验证。

---

#### 假设 D：分配器碎片 / 高水位假象（方向级，可能性较低）

> 🧪 假设：增长仅为内存碎片或分配器保留，非真实泄漏

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 增长形态 | 线性增长，非高位平台 | ❌ 不符合碎片特征 |
| RSS 谷值 | 逐采样点上移，无回落 | ❌ 不符合碎片模式 |

**❌ 已排除**：增长趋势明确且谷值上移，不符合碎片假象特征。

---

#### 假设 E：mmap / 文件映射 / 共享内存增长（已排除）

## 四、修复方案

### 4.1 应急处置（如有）

**当前阶段未执行任何修复操作**。由于处于只读观测边界，且未确认根本原因，建议先完成根因定位再进行修复。

### 4.2 永久修复计划

#### 后续验证方案（需单独授权）

| 步骤 | 操作 | 预期输出 | 优先级 |
|------|------|----------|--------|
| 1 | 提供可复现 workload，运行 `object_growth.py` | 确认 Python 对象增长类型和速率 | **P0** |
| 2 | 运行 `tracemalloc_probe.py` | 定位内存分配热点（调用栈） | **P0** |
| 3 | 运行 `semantic_probe.py` | 识别语义保留信号（全局容器、缓存等） | **P0** |
| 4 | 运行 `retention_chain.py` | 追踪保留链，定位根因保留者 | **P0** |
| 5 | 汇总分析，通过 `correlate_evidence.py` 对账 | 确认或排除各候选假设 | **P0** |

#### 根据确认后的根因分类修复

**如果确认 Python 托管对象泄漏：**

| 修复措施 | 说明 |
|----------|------|
| 检查全局容器/缓存上限 | 确认 `maxsize` 和淘汰策略是否配置 |
| 检查回调与事件监听器 | 确认是否存在未释放的引用（闭包、回调注册） |
| 使用弱引用管理 | 对长生命周期对象使用 `weakref`、显式清理机制 |

**如果确认 C 扩展 / Native 泄漏：**

| 修复措施 | 说明 |
|----------|------|
| 使用 valgrind/heaptrack/ASan | 定位 C 扩展中的内存泄漏 |
| 检查分配/释放配对 | 确认 ctypes/cffi/pybind11 扩展的分配/释放是否对称 |

**如果确认缓存无界增长：**

| 修复措施 | 说明 |
|----------|------|
| 设置 maxsize 和 TTL | 为缓存结构添加容量上限和过期策略 |
| 使用弱引用字典 | 替换为 `weakref.WeakValueDictionary` 或 `@lru_cache(maxsize=N)` |
| 监控与告警 | 定期监控缓存大小，设置告警阈值 |
