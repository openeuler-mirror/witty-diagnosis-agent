四、修复方案

4.1 应急处置（当前阶段）

由于根因尚未确认，应急处置应聚焦于补充证据采集，而非直接修复：

步骤 操作 预期效果
1 延长 RSS 观测窗口至 5～10 分钟（使用 monitor_rss.py） 判断增长是否为持续趋势，排除 allocator 预热假象
2 在可复现 workload 上运行 object_growth.py 获取 Python 托管对象的类型级增长数据
3 运行 tracemalloc_probe.py 定位分配热点，识别最大消耗者的调用栈
4 运行 semantic_probe.py 识别全局容器、无界缓存、回调等语义模式
5 运行 retention_chain.py 建立保留链，定位阻止 GC 回收的根对象
6 汇总全部证据后运行 correlate_evidence.py 输出最终 verdict，从 readonly_insufficient 升级

4.2 永久修复计划（在确认 Python 根因后）

修复措施 负责人 优先级
设置全局容器容量上限、TTL 或淘汰策略 应用开发团队 高
检查 @lru_cache 是否无界（maxsize=None） 应用开发团队 高

添加 RSS 监控告警（阈值：增长速率 > 100 KiB/s 持续 5 分钟） SRE 团队 高

⚠️ 风险提示：在未确认 Python 保留泄漏前实施优化性修复可能投入方向错误。建议优先完成 4.1 节的证据补全流程。
