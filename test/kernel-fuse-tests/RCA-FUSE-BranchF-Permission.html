3.1 初始现象

假设 C：文件系统权限变更 ✅ 确认根因

假设：/dev/fuse 文件权限从 0666 被限制为 0600，阻止非 root 进程访问

Step 1 — 检查设备文件当前权限

bash 
ls -la /dev/fuse
# 默认（正常）：crw-rw-rw- 1 root root 10, 229  → 0666
# 故障时：    crw------- 1 root root 10, 229  → 0600
对比项 默认（正常） 故障时
权限模式 crw-rw-rw- (0666) crw------- (0600)
other 权限 读写 无
文件属主 root:root root:root

Step 2 — 验证非 root 访问是否被权限层拒绝

bash 
# 以非 root 用户 (wyh) 执行
cat /dev/fuse
# 输出：cat: /dev/fuse: Permission denied

该错误码对应系统调用 open() 返回 EACCES（errno 13），由内核 VFS 层权限检查直接拒绝，非应用层逻辑。

Step 3 — 验证 FUSE 守护进程是否因 open() 失败而退出

非 root 守护进程 fuse_d3 启动流程：

fuse_d3 (non-root)
  └─► open("/dev/fuse", O_RDWR)
        └─► 内核 VFS 权限检查 → 0600 拒绝非 root
              └─► 返回 -EACCES, errno=13
                    └─► fuse_d3 收到 "Permission denied" → 进程立即退出
                          └─► 无 FUSE 会话 → 无挂载点 → 完全不可用

Step 4 — 恢复验证

将权限恢复为 0666 后，非 root 用户可正常打开 /dev/fuse，FUSE 挂载立即恢复正常。

✅ 结论：/dev/fuse 权限从 0666 变更为 0600，是导致非 root FUSE 操作全部失败的唯一根因。

五、补充分析

5.1 故障本质

本故障属于前置资源访问控制型故障，区别于其他 FUSE 注入分支（守护进程内部逻辑异常、内存损坏等），其特点是：

  • 故障点在 open() 系统调用层：内核 VFS 权限检查是第一道关卡，任何非 root 进程在尝试打开 /dev/fuse 时即被拒绝。
  • 零启动延迟：权限变更后，下一个非 root open() 调用立即失败，无中间状态、无渐近恶化过程。
  • 全面阻断：不是"功能降级"或"部分挂载失败"——所有非 root FUSE 操作被 100% 阻断。

5.2 内核权限检查路径（参考）

open("/dev/fuse", O_RDWR)
  └─► path_openat()
        └─► inode_permission()
              └─► generic_permission()
                    └─► acl_permission_check()
                          └─► inode->i_mode 检查
                                ├─► 0600: 仅 owner(root) 有 rw-
                                └─► 0666: owner/group/other 均有 rw-
  └─► 权限不足 → 返回 -EACCES

5.3 安全考虑

将 /dev/fuse 设为 0600 本身是一种有效的安全加固手段，可用于限制非受信用户创建 FUSE 文件系统（防止潜在的利用 FUSE 绕过安全策略的攻击向量）。如果系统明确需要支持非 root FUSE 操作，则必须保持 0666 或使用 setuid 包装器。

场景 推荐权限 说明
多用户环境需要 FUSE 0666 标准配置，允许所有用户使用 FUSE
仅 root 需要 FUSE 0600 安全加固，阻断非 root 滥用
仅特定用户需要 FUSE 0660 + 专用用户组 精细权限控制，推荐方案
