### 2.2 配置项逐项评估

| 配置项 | 当前值 | 评估 | 风险等级 | 说明 |
|--------|--------|------|----------|------|
| `CONFIG_FUSE_FS` | `=y` (built-in) | ⚠️ 不可卸载 | 🟡 中 | 内核内置，无法通过 `modprobe -r` 或 `blacklist` 移除；若发现 FUSE 内核漏洞，需完整内核升级才能修复 |
| `CONFIG_FUSE_DAX` | `=y` (enabled) | ⚠️ 攻击面扩大 | 🟡 中 | DAX 支持增加直接内存访问路径，若未使用 PMEM，建议关闭以减小内核攻击面 |
| `allow_sys_admin_access` | `N` | ✅ 安全默认 | 🟢 低 | 非 root 用户无法通过 `allow_other` 挂载绕过访问控制，符合最小权限原则 |
| `max_user_bgreq` | `5158` | ⚠️ 阈值偏高 | 🟡 中 | 单用户可累积 5158 个后台请求，异常场景下可能导致请求积压和内存压力 |
| `max_user_congthresh` | `5158` | ⚠️ 阈值偏高 | 🟡 中 | 与 bgreq 相同，拥塞控制阈值偏高，在突发 I/O 场景可能延迟拥塞响应 |
| `max_background` (per-conn) | `12` | ✅ 内核默认 | 🟢 低 | 默认每连接 12 后台请求，与主线内核一致，行为可预期 |
| `/dev/fuse` 权限 | `0666` | ❌ 全用户可访问 | 🔴 高 | 任何本地用户均可打开 `/dev/fuse` 创建 FUSE 实例，是主要安全暴露面 |
| `max_read` | 未暴露（内核默认） | ✅ 默认行为 | 🟢 低 | 使用内核内部默认限制，通信行为符合预期 |
| API 版本 | v7.39 | ✅ 稳定版本 | 🟢 低 | 主线内核稳定支持，功能完备（writeback cache, readdirplus 等） |

## 三、风险分析

### 3.1 风险矩阵

| 风险分类 | 风险项 | 可能性 | 影响面 | 风险等级 |
|----------|--------|--------|--------|----------|
| 安全暴露 | `/dev/fuse` 0666 全局可读写 | 中 | 高（任意用户构造 FUSE 文件系统） | 🔴 **P2** |
| 安全暴露 | FUSE 模块内置不可卸载 | 低 | 高（漏洞无法通过模块卸载规避） | 🟡 **P3** |
| 资源风险 | `max_user_bgreq=5158` 偏高 | 低 | 中（异常累积导致 OOM 或卡顿） | 🟡 **P3** |
| 资源风险 | `max_user_congthresh=5158` 偏高 | 低 | 中（拥塞响应延迟） | 🟡 **P3** |
| 攻击面 | DAX 直通支持已启用 | 低 | 中（PMEM 直接访问路径暴露） | 🟡 **P3** |
| 运维风险 | 模块参数无法运行时调整 | 中 | 低（需重启或 sysfs 调整） | 🟢 **P4** |

### 3.2 风险详情

#### 风险 A：`/dev/fuse` 全局可读写（🔴 P2）

| 检查项 | 细节 |
|--------|------|
| 现象 | `/dev/fuse` 权限为 `crw-rw-rw-` (0666)，所有用户（包括非特权用户）均可读写 |
| 影响 | 任何本地用户均可通过 `/dev/fuse` 创建 FUSE 文件系统实例，可被用于：隐藏恶意文件、绕过文件系统权限检查、执行用户态文件系统提权攻击 |
| 缓解 | WSL2 环境默认所有进程以 root 运行，但若存在非 root 进程或容器，该风险会暴露 |
| 建议 | 若业务不需要任意用户访问 FUSE，应将权限收紧为 `0660`（仅 root+root 组）或 `0600` |

#### 风险 B：FUSE 内置 + DAX 支持（🟡 P3）

| 检查项 | 细节 |
|--------|------|
| 现象 | `CONFIG_FUSE_FS=y` 和 `CONFIG_FUSE_DAX=y` 均在静态内核中启用 |
| 影响 | FUSE 代码和 DAX 路径始终存在于内核内存中，即使未挂载任何 FUSE 文件系统也占据内核代码段；若出现 CVE 漏洞，无法通过模块黑名单规避 |
| 缓解 | WSL2 内核由 Microsoft 以更新方式推送，漏洞修复依赖上游 |
| 建议 | 对于生产场景，建议跟踪 CVE 公告；若无需 FUSE DAX，向内核编译环境反馈禁用该选项 |

#### 风险 C：后台请求/拥塞阈值偏高（🟡 P3）

| 检查项 | 细节 |
|--------|------|
| 现象 | `max_user_bgreq=5158`，`max_user_congthresh=5158`，远高于常规默认值（通常 12-256） |
| 影响 | 单用户可累积大量 FUSE 后台请求，在 FUSE daemon 处理能力不足时导致请求积压、内存占用上升，甚至触发 OOM |
| 推测原因 | 该值根据系统 `fs.file-max` 按比例计算（`/sys/fs/fuse/connections/...` 相关算法），当前系统文件句柄上限较高 |
| 建议 | 评估实际工作负载，确认是否确实需要此并发能力；若无特殊需求，考虑在系统层面调整 `fs.file-max` 间接控制 |

## 五、架构约束与影响分析

### 5.1 模块不可拆卸的影响

由于 FUSE 是静态编译（`y` 而非 `m`），存在以下约束：

```text
┌─ WSL2 内核 FUSE 约束 ──────────────────────────────────┐
│                                                          │
│  1. ❌ 无法通过 modprobe -r 卸载 FUSE                    │
│  2. ❌ 无法通过 /etc/modprobe.d/blacklist.conf 屏蔽      │
│  3. ❌ 无法使用 module 参数在 insmod/modprobe 时传递      │
│  4. ✅ 可在 /sys/module/fuse/parameters/ 查看运行参数     │
│  5. ✅ 可通过 sysfs 调整部分参数（>/sys/...）             │
│  6. ⚠️ 内核升级是唯一更新 FUSE 代码的方式                 │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 5.2 DAX 支持影响

`CONFIG_FUSE_DAX=y` 启用后：

- 允许 FUSE daemon 通过 DAX 直接访问持久内存（PMEM / NVDIMM）
- 当 DAX 映射激活时，I/O 路径可能绕过 VFS 页缓存，需 FUSE daemon 自行管理缓存一致性
- WSL2 环境通常不部署 PMEM，DAX 功能在此场景下处于空载状态，但代码路径仍会编译进内核
- 若未来 WSL2 支持虚拟 PMEM，该功能将变为可用

### 5.3 `max_user_bgreq / congthresh` 数值推导分析

当前值 5158 是系统自动计算的，依据是：

- 内核源码（`fs/fuse/inode.c`）中 `max_user_bgreq` 和 `max_user_congthresh` 默认为 `max(12, totalram_pages * ...)` 或关联 `file-max` 的 0.4%
- 5158 的值表明当前系统的 `fs.file-max` 或 `totalram_pages` 较高（WSL2 可访问宿主机大量内存）
- 示例：若 `file-max = 515800`，则 0.4% ≈ 2063，而此处 bgreq=5158 约等于 1% 的 515800，说明系统 `file-max` 可能在 515800 左右

```text
WSL2 典型 file-max 计算:
  fs.file-max ≈ 0.4% * (s物理内存页数)
  若 WSL2 分配 16GB 内存:
    totalram_pages ≈ 4,194,304 页 (4KB)
    file-max ≈ 16,777
    5158 > 12, 且明显高于 16,777*0.4%=67
  → 说明 WSL2 可访问宿主机大量物理内存，导致 file-max 偏高
```

## 六、改进建议

### 6.1 高优先级

| 序号 | 建议 | 严重程度 | 预期效果 |
|------|------|----------|----------|
| 1 | 收紧 `/dev/fuse` 权限为 `0660` 或 `0600`：`chmod 0660 /dev/fuse` | 🔴 高 | 阻止非授权用户创建 FUSE 实例，减少攻击面 |
| 2 | 评估并限制 `max_user_bgreq`：通过 sysfs 写入 `/sys/module/fuse/parameters/max_user_bgreq` | 🟡 中 | 降低单用户后台请求过载风险 |

### 6.2 中优先级

| 序号 | 建议 | 严重程度 | 预期效果 |
|------|------|----------|----------|
| 3 | 关注 FUSE 和 FUSE DAX 相关 CVE 公告，评估是否需要重新编译内核 | 🟡 中 | 确保及时修复潜在安全漏洞 |
| 4 | 确认 WSL2 环境是否确实需要 FUSE DAX 支持，不需要则在编译时关闭 | 🟡 中 | 减少内核攻击面和代码体积 |
| 5 | 对实际工作负载进行 FUSE 后台请求压力测试，确认 5158 阈值是否合理 | 🟡 中 | 防止异常场景下的资源耗尽 |

### 6.3 低优先级（信息性）

| 序号 | 建议 | 严重程度 | 预期效果 |
|------|------|----------|----------|
| 6 | 审查 `/sys/fs/fuse/connections/` 下所有活跃连接的挂载点和参数 | 🟢 低 | 建立 FUSE 使用基线 |
| 7 | 在 WSL2 WSLg 等组件中确认是否有 FUSE 使用白名单机制 | 🟢 低 | 提升整体安全可见性 |

### 7.2 假设驱动排查

#### 假设 A：FUSE 存在安全暴露面

> 🧪 假设：FUSE 设备节点或模块参数配置可能导致非授权用户创建 FUSE 实例

| 检查项 | 操作 | 结论 |
|--------|------|------|
| `/dev/fuse` 权限 | 查看 `ls -la /dev/fuse` | ❌ 0666，所有用户可读写 |
| `allow_sys_admin_access` | 读取 `/sys/module/fuse/parameters/allow_sys_admin_access` | ✅ `N`，非 root 不可绕过访问控制 |
| 其他 FUSE 子功能 | 检查 `CONFIG_CUSE`, `CONFIG_FUSE_NOTIFY` | ✅ 未启用，无额外攻击面 |

**✅ 结论：`/dev/fuse` 0666 是主要安全暴露点。** 尽管 `allow_sys_admin_access=N` 限制了 `allow_other` 挂载选项的滥用，但任意用户仍可打开设备节点创建 FUSE daemon 实例。

#### 假设 B：模块参数阈值可能导致资源风险

> 🧪 假设：`max_user_bgreq=5158` 偏高，可能导致异常场景下的资源耗尽

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 当前值 | 读取 `/sys/module/fuse/parameters/max_user_bgreq` | ⚠️ `5158` |
| 对比基线 | 与主线内核默认值对比 | 📊 通常默认值为 12-256，5158 显著偏高 |
| 系统 file-max 推导 | 根据内核计算公式反推 | 🔍 推测系统 `file-max` 较高，与 WSL2 大内存配置一致 |

**✅ 结论：阈值偏高是系统性特征，受 WSL2 大内存影响，非人为配置问题，但仍需关注异常场景风险。**

#### 假设 C：FUSE DAX 带来不必要的攻击面

> 🧪 假设：DAX 支持已启用但在 WSL2 环境中无实际用途

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 内核配置 | 检查 `.config` 中的 `CONFIG_FUSE_DAX` | ✅ `=y`，已启用 |
| WSL2 DAX 能力 | 评估 WSL2 是否支持 PMEM/NVDIMM | ❌ WSL2 标准环境不支持物理 PMEM |
| 攻击面影响 | DAX 代码路径是否可用于攻击 | ⚠️ 代码路径在内核中，但无实际设备映射时被利用的可能性极低 |

**✅ 结论：DAX 支持在 WSL2 标准环境中属于被动风险，无实际攻击面，但建议在定制编译时按需关闭。**
