## 三、排查过程

> 排查逻辑：**根据前置 Kuafu 诊断结果 → 证据链关联 → 理论建模 → 根因确认**

### 3.1 初始现象

- **诊断前置结论**：futex(FUTEX_WAIT) 调用耗时显著 > 50ms
- **容器信息**：`strace-fi-loop-b-futex-1779969082`，进程 `branch_b_slow --loop futex`
- **线程拓扑**：1 主线程 + 4 个工作线程，全部竞争同一把 pthread mutex
- **临界区特征**：持有锁后忙等 ~50ms，释放后 usleep(10ms)，循环重复

---

### 3.2 假设驱动排查

#### 假设 A：线程数量过多导致锁竞争加剧

> 🧪 假设：4 个线程竞争同一把锁，线程数过高导致上下文切换开销过大

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 线程竞争模型 | 分析 n=4 线程竞争单一资源的锁获取概率 | ✅ 理论：单把锁任意时刻仅 1 线程可持有，n≥2 即产生竞争 |
| 临界区占比 | 计算临界区时间 / 总周期时间 | ✅ 50ms / (50ms + 10ms) = 83.3% 锁处于被持有状态 |
| 竞争程度 | 4 线程竞争 1 资源，等待时间与临界区长度成正比 | ✅ 等待时间 = 临界区长度 × (n-1)/2 ≈ 75ms 理论均值 |

**结论**：线程数 n=4 确实加剧竞争，但即使 n=2 也会产生显著竞争。**核心问题不在于线程数，而是锁粒度本身。**

---

#### 假设 B：临界区过长是锁竞争的直接原因 ✅ 确认根因

> 🧪 假设：~50ms 的临界区忙等时间过长，导致线程长时间占用锁，其他线程被迫长时间阻塞

**Step 1 — 锁竞争周期计算**
```
总周期 = 临界区(50ms) + 释放后休眠(10ms) = 60ms
锁持有时间占比 = 50ms / 60ms ≈ 83.3%
平均等待线程数 = 4 - 1 = 3（不考虑主线程）
单线程平均获取锁等待时间 ≈ (n-1) × 临界区 / n × (1 + 休眠/临界区) ...
```

简化模型：在 4 线程公平竞争场景下，每个线程每轮循环的等待时间约为：
- 假设锁分配相对公平，每 60ms 周期内有 1 个线程持有锁（50ms）+ 休眠（10ms）
- 3 个等待线程的阻塞时间约在 **50ms ~ 150ms** 之间（取决于竞争时序）

确认报告结论 **futex(FUTEX_WAIT) 耗时 > 50ms** 与理论计算一致。

**Step 2 — /proc/1/task/ 状态佐证**
- 仅 2 个活跃任务（主线程 + 1 个工作线程），其余 3 个工作线程均阻塞在 `futex(FUTEX_WAIT)`
- 阻塞线程处于 `S` 状态（interruptible sleep），不会在 `/proc/1/task/` 的活跃统计中计数
- 内核栈显示 `hrtimer_nanosleep` — futex 底层通过 hrtimer 实现超时等待

**✅ 结论：临界区过长（~50ms）是锁竞争的直接原因，导致 3/4 的线程长期阻塞在 futex，等待时间 > 50ms。**

---

#### 假设 C：usleep(10ms) 设计不合理

> 🧪 假设：usleep(10ms) 导致锁释放后有空窗期，降低整体吞吐

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 休眠必要性 | 检查临界区外是否必须释放 CPU | ✅ 忙等后释放 CPU 有利，但 10ms 过长 |
| 吞吐影响 | 计算无休眠的纯锁竞争吞吐 | 无休眠时锁几乎总被持有，吞吐反而可能更高但公平性更差 |
| 优化方向 | 建议使用 mutex + condition variable 代替 usleep | 🔍 设计级建议 |

**结论**：usleep(10ms) 虽不是根因，但它延长了线程的空闲周期，变相降低了整体吞吐量。更好的设计应采用条件变量或读写锁。

## 五、技术深度分析

### 5.1 futex 内核机制回顾

futex (Fast Userspace Mutex) 是 Linux 下高效的用户态锁实现：

1. **无竞争时**：锁操作完全在用户态完成（原子 cmpxchg），不进入内核，开销极低（~10ns）
2. **有竞争时**：
   - 请求锁但发现已被持有 → `futex(FUTEX_WAIT, val)` 系统调用 → 线程挂起进入 `hrtimer_nanosleep`
   - 持有锁的线程释放锁 → `futex(FUTEX_WAKE, n)` 唤醒至多 n 个等待线程
   - 被唤醒的线程返回用户态，重新尝试原子操作获取锁

**本场景的核心问题**：由于 4 线程全部阻塞等待，每次 `FUTEX_WAKE` 会产生**惊群效应（thundering herd）** — 3 个等待线程全部被唤醒，但只有 1 个能成功获取锁，其余 2 个立即重入 `FUTEX_WAIT`，造成额外的上下文切换和内核态/用户态切换开销。

### 5.2 锁竞争与多核可扩展性

本场景在任意多核 CPU 上都会表现出一致的瓶颈，因为：

```
Amdahl's Law: S = 1 / (1 - P + P/n)
其中 P = 可并行比例，n = 核心数

本场景中临界区占比 = 50ms / 60ms ≈ 83.3%
可并行比例 = 1 - 0.833 = 16.7%
最大加速比 = 1 / 0.833 = 1.2x

即使使用 128 核，加速比也仅为 1.2 — 即性能约等于单线程的 1.2 倍。
```

### 5.3 内核栈 `hrtimer_nanosleep` 解读

- `hrtimer_nanosleep` 是 Linux 高精度定时器（HRT）驱动的睡眠机制
- futex 的 `FUTEX_WAIT` 内部使用 `hrtimer` 实现超时等待
- 线程在 `FUTEX_WAIT` 中阻塞时内核态栈底表现为 `hrtimer_nanosleep`
- 这验证了线程确实在 futex 等待中进入了长时睡眠，而非处于用户态自旋
