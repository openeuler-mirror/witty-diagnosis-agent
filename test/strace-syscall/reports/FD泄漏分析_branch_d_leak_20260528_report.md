## 三、排查过程

### 3.1 初始现象

- **进程**：`branch_d_leak --loop fd_leak`，PID: 11172
- **FD 数量**：当前 135，且持续快速增长中
- **泄漏模式**：每轮循环稳定泄漏 3 个 FD
  - `open(临时文件)` → 不执行 `close()`
  - `open(/dev/null)` → 不执行 `close()`
  - `dup(1)`（复制 stdout） → 不执行 `close()`
- **特质**：泄漏速率稳定、可预测，每轮循环严格增加 3 个 FD，无随机波动

### 3.2 假设驱动排查

#### 假设 A：内核级 FD 泄漏（如内核 bug）

> 🧪 假设：Linux 内核存在 FD 表管理 bug，导致进程 FD 异常增长

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 泄漏模式分析 | 每轮精确泄漏 3 个 FD，无随机性 | ❌ 非内核 bug（内核泄漏通常无此精确模式） |
| 可复现性 | 进程启动后每轮循环稳定泄漏 | ❌ 非偶发，不符合内核 bug 特征 |

**❌ 排除**：泄漏模式高度规律，是典型应用层未释放 FD 的行为，非内核级问题。

---

#### 假设 B：第三方库或框架层的 FD 泄漏

> 🧪 假设：进程调用的第三方库在内部打开 FD 后未释放

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 泄漏接口分析 | 泄漏源直接来自 `open()` / `dup()` 系统调用 | ✅ 确认为应用层主动调用 |
| 泄漏接口明了 | 三个操作均为常见的基础系统调用 | ❌ 属于应用逻辑直接行为，非库的隐含开销 |

**❌ 排除**：泄漏由应用代码中的显式 `open()` 和 `dup()` 直接导致，非第三方库行为。

---

#### 假设 C：应用逻辑缺陷 — FD 未释放  ✅ 确认根因

> 🧪 假设：进程 `branch_d_leak` 在循环体中遗漏了 `close()` 调用

**证据列表：**

| 序号 | 证据项 | 来源 |
|------|--------|------|
| 1 | 每轮循环精确泄漏 3 个 FD | 诊断报告描述 |
| 2 | 泄漏源明确：`open(临时文件)`、`open(/dev/null)`、`dup(1)` 皆未 close | 诊断报告描述 |
| 3 | FD 数量线性增长（已达 135），无收敛或波动 | 诊断报告描述 |
| 4 | 进程以 `--loop fd_leak` 模式运行，明确为 FD 泄漏场景 | 诊断报告 |
| 5 | 增长速率与循环次数成正比 | 逻辑推导 |

**✅ 结论：进程 `branch_d_leak` 在 `fd_leak` 模式下的循环体中，每次迭代依次执行 `open()` 和 `dup()` 操作获取新的文件描述符，但对应路径上完全没有 `close()` 调用，导致 FD 只增不减，持续泄漏。**

### 5.2 知识点补充：Linux FD 泄漏的典型危害

当进程文件描述符耗尽时，以下系统调用将返回 `EMFILE`（进程级）或 `ENFILE`（系统级）错误：

- `open()` / `openat()` — 无法打开文件
- `socket()` / `accept()` — 无法建立网络连接
- `pipe()` — 无法创建管道
- `dup()` / `dup2()` — 无法复制 FD
- `epoll_create()` / `eventfd()` / `signalfd()` — 无法创建事件机制

在 Web 服务器等网络服务中，FD 耗尽通常表现为**全部新请求拒绝服务**，是典型的"慢速杀手"型故障。
