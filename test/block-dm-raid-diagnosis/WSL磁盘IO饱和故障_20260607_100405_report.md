## 三、排查过程

### 3.1 初始现象

- **用户报告**：WSL Ubuntu 22.04 系统中 iowait 达到 68%，16 个 fio 进程处于 Ds 状态
- **关键指标**：sdd 设备 %util=100%，系统 load 从 0.1 飙升到 1.56
- **假设方向**：怀疑块设备层 IO 饱和异常
- **当前状态**：WSL 实例已重启，故障状态不可复现（采集的数据为恢复后的残余余波）

### 3.2 假设驱动排查

#### 假设 A：物理磁盘硬件故障（如磁盘坏道、SATA/SAS 链路错误）

> 🧪 假设：sdd 设备对应的底层磁盘存在物理坏道或硬件故障，导致 IO 卡顿

| 检查项 | 操作 | 结论 |
|--------|------|------|
| dmesg 内核错误日志 | `dmesg \| grep -iE "sdd\|i/o error\|buffer"` | ✅ 无任何 I/O error、Buffer I/O 或设备异常错误 |
| 设备只读状态 | `cat /sys/block/sdd/ro` | ✅ ro=0，可读写，未被切换为只读 |
| 设备状态 | `cat /sys/block/sdd/device/state` | ✅ `running`，正常运行 |
| SMART 健康信息 | `smartctl -a /dev/sdd` | ⚠️ WSL 环境不支持 smartctl，无法获取 SMART 数据 |

**❌ 排除**：dmesg 无任何 IO 错误，设备状态 running，无物理磁盘故障证据。即使无法获取 SMART，零 IO 错误日志已足够排除硬件级故障。

---

#### 假设 B：IO 调度器异常导致 IO 排队

> 🧪 假设：IO 调度器配置不当或调度器异常导致 IO 请求被不合理地排队延迟

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 当前调度器 | `cat /sys/block/sdd/queue/scheduler` | ✅ `none`（multi-queue 模式无调度器） |
| 队列深度 | `cat /sys/block/sdd/queue/nr_requests` | ✅ 1584，深度充裕 |
| inflight 状态 | `cat /sys/block/sdd/inflight` | ✅ 故障恢复后 inflight=[0,0] |
| 队列状态 | 查看 queue/state | ✅ 正常，未被冻结 |

**❌ 排除**：none 调度器表示 IO 请求直通块层，无调度器介入排队。队列深度 1584 充足，非调度器导致。

---

#### 假设 C：LVM / DM / md RAID / Multipath 映射层故障

> 🧪 假设：Device-Mapper 映射错误、软 RAID 降级、LVM 配置异常或 multipath 路径失效

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 软 RAID 状态 | `cat /proc/mdstat` | ✅ 空，无 md 设备 |
| DM 设备表 | `dmsetup table` | ✅ 空，无 DM 映射设备 |
| LVM 状态 | `pvs` / `vgs` / `lvs` | ✅ 无 LVM 配置 |
| multipath 状态 | `multipath -ll` | ✅ 未配置 multipath |

**❌ 排除**：L2 映射栈完全为空，sdd 是直通设备，无任何中间映射层。

---

#### 假设 D：块设备 IO 饱和（WSL 虚拟化层排队瓶颈） ✅ 确认根因

> 🧪 假设：sdd 设备 %util=100% 并非因为磁盘硬件响应慢，而是 IO 请求在 WSL 虚拟化层排队等待 Windows 宿主机后端处理

**Step 1 — 分析 IO 性能指标的关键矛盾**

采集到的 iostat 数据显示：

| 指标 | 故障时数值 | 含义 |
|------|-----------|------|
| r/s | 2089.47 | 读 IOPS 较高 |
| r_await | **0.23 ms** | 读平均延迟**极低** |
| w_await | **0.56 ms** | 写平均延迟**极低** |
| aqu-sz | 0.49 | 平均队列长度 |
| %util | **100% → 28.83% → 0.80%** | 快速回落 |

> **关键洞察**：机械硬盘（ROTA=1）的正常 await 应在 5~15ms 范围。这里 await 仅 0.17~0.56ms，是 SSD 级别的延迟。如果磁盘硬件是瓶颈，await 会随 %util 升高而同步升高。但这里 **%util=100% 而 await<1ms**，说明 IO 请求在**设备更上层的虚拟化层排队**，而非磁盘硬件本身慢。

**Step 2 — 分析 discard 操作的极端延迟**

从 `/sys/block/sdd/stat` 读取的数据中有一个突出异常：

| 统计项 | 值 | 分析 |
|--------|-----|------|
| discard I/Os | 32 | 仅有 32 次 discard 操作 |
| discard ticks | **59568 ms** | 总耗时 **59.5 秒** |
| 平均每次 discrad 耗时 | **1861 ms** | 单次 discard 约 1.86 秒 |

> 这是 WSL 虚拟磁盘（ext4.vhdx）处理 TRIM 命令时的**已知性能特征**：Windows 宿主机在处理 VHDX 的 discard/TRIM 时，需要与宿主文件系统交互，开销极大。这直接印证了 WSL 后端 IO 路径的延迟特性。

**Step 3 — 确认设备属性**

| 属性 | 值 | 含义 |
|------|-----|------|
| 设备型号 | Virtual Disk | WSL 虚拟磁盘 |
| 厂商 | Msft (Microsoft) | 微软虚拟化层 |
| ROTA | 1 | 报告为旋转设备（模拟 HDD） |
| 容量 | 1.00 TiB | 映射到 Windows 的 ext4.vhdx |
| 挂载点 | /mnt/wslg/distro | WSL 系统盘 |
| 文件系统 | ext4 | WSL 内核模拟的 ext4 |

> `/dev/sdd` 并非物理磁盘，而是映射到 Windows 宿主机 `%LOCALAPPDATA%\Packages\*\LocalState\ext4.vhdx` 文件的虚拟磁盘。所有 IO 请求必须经过 WSL 虚拟化层转发到 Windows 文件系统处理。

**✅ 结论：WSL 虚拟磁盘后端 IO 排队瓶颈。** WSL 虚拟化层的 IO 处理路径（无论是 9P 协议还是 VHDX 后端）存在队列深度限制或单线程处理模型，当 16 个 fio 进程产生高并发 IO 时，请求在虚拟化层排队等待 Windows 后端处理，表现为 %util=100% 但 await 极低、iowait 飙升、进程 D 状态堆积。

## 四、修复方案

### 4.1 应急处置（本次已执行）

| 步骤 | 操作 | 执行人 | 时间 | 效果 |
|------|------|--------|------|------|
| 1 | WSL 实例重启（用户操作） | 用户 | 2026-06-07 ~10:04:00 | ✅ %util 从 100% 回落至 0.80%，load 归零，系统恢复 |
| 2 | 终止 16 个 fio 并发进程 | — | 重启后自动终止 | ✅ 进程不再阻塞，系统恢复正常 |

> **注意**：WSL 重启是本次故障恢复的直接原因，重启清空了虚拟化层的 IO 队列，释放了所有阻塞的进程。

### 4.2 永久修复计划

| 修复措施 | 风险等级 | 说明 |
|---------|---------|------|
| **1. 限制并发 IO 深度** | 🟢 低 | 在 WSL 中进行 IO 密集型操作时，控制并发进程数（建议不超过 4~6 个），避免同时启动过多 fio 类进程压测 WSL 虚拟磁盘后端 |
| **2. 调整 WSL 挂载参数禁用 discard** | 🟢 低 | 编辑 `/etc/wsl.conf`，添加 `[automount]` 下的 `options="noatime,nodiscard"` 配置，避免 TRIM 命令带来的极端延迟。配置后需重启 WSL 生效 |
| **3. 优化 Windows 安全软件扫描排除** | 🟢 低 | 在 Windows Defender 或第三方杀毒软件中，排除 WSL 虚拟磁盘文件路径：`%USERPROFILE%\AppData\Local\Packages\*Ubuntu*\LocalState\`，减少实时扫描对 IO 路径的干扰 |
| **4. 将 WSL 工作负载迁移到 ext4 分区** | 🟡 中 | 在 Windows 中单独创建一个 ext4 分区（使用 ext2fsd 或 WSL2 的挂载功能），或者在 WSL 中挂载 Windows 的 NTFS 路径（`/mnt/c/`）进行 IO 密集操作，绕过 VHDX 虚拟化层瓶颈（注意 NTFS 挂载也有性能开销，但并发模型不同） |
| **5. 关注 WSL 版本更新** | 🟢 低 | 持续关注 WSL 官方的磁盘性能改进。WSL2 内核 6.6.114.1 已较新，但 VHDX 后端 IO 路径是 WSL 持续优化的领域 |

### 4.3 验证方法

- **验证条件**：在相似负载下（启动多个 fio 进程并发读压测），同时监控以下指标：
  - `iostat -x 1`：观察 `%util` 与 `await` 的关系。若 `await < 2ms` 但 `%util` 持续 90%+，即可确认虚拟化层排队
  - `/sys/block/sdd/inflight`：查看飞行中 IO 计数是否堆积
  - `watch -n 1 'cat /proc/loadavg'`：监控系统负载变化
- **修复效果验证**：应用禁用 discard 并重启 WSL 后，再次运行同等并发 fio 压测，确认 `%util` 不再饱和或 `await` 不异常升高
