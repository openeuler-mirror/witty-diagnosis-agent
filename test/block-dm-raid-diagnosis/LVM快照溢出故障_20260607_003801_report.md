## 四、根因定位

**根因描述**：

LVM 传统快照 `lv_snap` 的 COW（写时复制）存储空间大小仅为 **52MiB**，远小于源卷 `lv_orig` 的 **300MiB**。当源卷在快照创建后持续写入，产生的差异数据总量超过 52MiB 时，内核 Device Mapper 快照目标无法分配新的例外块（exception），按照 LVM 快照的设计规范，自动将快照标记为 **INVALID（无效）**。

**决定性证据**（内核日志）：
```
[    3.742780] device-mapper: snapshots: Invalidating snapshot: Unable to allocate exception.
```

**置信度**：**🟢 高置信**
- 内核日志直接报告了 `Unable to allocate exception`（正向决定性证据）
- `dmsetup status` 明确显示 `snapshot Invalid`（正向决定性证据）
- LVM 属性 `lv_attr=swi-I-s---` 含 `I`（invalid）标志（正向决定性证据）
- Data%=100.00, Snap%=100.00（正向决定性证据）
- PV/VG 正常、loop 设备正常，排除其他可能（反事实验证通过）

## 五、排查过程

### 5.1 初始现象

- LVM 快照 `lv_snap` 无法使用
- `lvs -a -o lv_name,data_percent,snap_percent,lv_attr` 显示：
  - `Data%=100.00`
  - `Snap%=100.00`
  - `lv_attr=swi-I-s---`（I = invalid）
- 源卷 `lv_orig` 可正常读写

### 5.2 假设驱动排查

#### 假设 A：PV/VG 底层故障

| 检查项 | 操作 | 结论 |
|--------|------|------|
| PV 状态 | `sudo pvs` — PV `/dev/loop0` 正常，124 PE，36 PE 空闲 | ✅ 正常 |
| VG 状态 | `sudo vgs` — VG `vg_d` 正常，496MiB 大小，144MiB 空闲 | ✅ 正常 |

**❌ 排除**：PV/VG 均健康且有富余空间，非底层故障。

#### 假设 B：内核模块或 DM 驱动 Bug

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 内核版本 | 6.6.114.1-microsoft-standard-WSL2（标准 WSL2 内核） | ✅ 主流版本 |
| dmesg 快照日志 | `Invalidating snapshot: Unable to allocate exception` | ✅ 明确指明了原因 |
| 其他 DM 设备 | `dmsetup table` 中 `lv_orig` / `lv_orig-real` / `lv_snap-cow` 均正常 | ✅ 正常 |

**❌ 排除**：内核日志明确指出 COW 空间耗尽为原因，无 Bug 迹象。

#### 假设 C：硬件故障 / 底层磁盘问题

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 底层设备类型 | loop 设备（基于 WSL 宿主机文件系统） | ✅ 无物理磁盘 |
| 物理链路 | WSL2 虚拟化环境 | ✅ 无物理链路 |

**❌ 排除**：WSL 虚拟化环境，无物理硬件故障可能性。

#### 假设 D：COW 空间配置不足 ✅ 确认根因

| 检查项 | 操作 | 结论 |
|--------|------|------|
| COW 空间大小 | `lvdisplay -am` → COW-table size = **52.00 MiB** | ❌ 严重不足 |
| 源卷大小 | `lvs` → lv_orig = **300 MiB** | 源卷大小是 COW 的 5.77 倍 |
| COW 使用率 | `Data%=100.00`，`Snap%=100.00` | ❌ 已完全耗尽 |
| DM 状态确认 | `dmsetup status` → `snapshot Invalid` | ❌ 已失效 |
| 内核原因确认 | `dmesg` → `Unable to allocate exception` | ❌ 内核确认 |

**✅ 确认根因**：COW 空间仅 52MiB，不足以容纳源卷 300MiB 的差异数据，导致快照溢出失效。

### 5.3 排查结论

```text
快照 lv_snap 不可用
├─► PV/VG 底层故障            → ✅ 正常，排除
├─► 内核 DM 模块 Bug          → ✅ 正常，排除
├─► 硬件/物理磁盘故障          → ✅ 正常，排除
└─► COW 空间配置不足           → ❌ 52MiB << 300MiB（源卷）
        └─► Data%=100.00      → ❌ COW 空间完全耗尽
                └─► dmesg     → ❌ "Unable to allocate exception"
                        └─► 🎯 根因确认：COW 空间溢出
```

## 六、修复方案

### 6.1 临时措施

| 步骤 | 操作 | 风险等级 | 说明 |
|------|------|---------|------|
| 1 | `sudo lvremove vg_d/lv_snap` — 移除已失效的快照 | **中** | 操作不可逆，快照数据永久丢失。**需确认不再需要快照数据后再执行** |
| 2 | `sudo lvcreate -s -n lv_snap_new -L 300M vg_d/lv_orig` — 创建新快照（COW 空间设为 300MiB） | **低** | 新快照的 COW 空间与源卷大小一致，确保有足够空间容纳差异数据 |

### 6.2 永久措施

| 修复措施 | 风险等级 | 说明 |
|--------|---------|------|
| 合理规划快照 COW 容量，建议至少为源卷的 30%~100% | **低** | 对于 300MiB 源卷，建议 COW ≥ 100MiB（30%）；若写入量大则建议与源卷等大 |
| 实施快照使用率监控告警：`lvs -o+snap_percent`，在 COW 使用率 > 80% 时预警 | **低** | 避免再次出现 COW 耗尽导致的快照失效 |
| 评估使用 Thin Provisioning 替代传统快照（thin pool + thin LV + thin snapshots） | **低** | Thin 快照空间管理更灵活，支持更多快照，但需确认内核和 LVM 版本支持 |
| 定期巡检 LVM 快照状态，纳入自动化运维体系 | **低** | 纳入健康巡检流程 |

### 6.3 验证方法

- **验证旧快照已移除**：`sudo lvs -a` 确认 `lv_snap` 不再列出
- **验证新快照状态**：`sudo lvs -a -o lv_name,data_percent,snap_percent,lv_attr` 确认新快照属性不含 `I` 标志
- **写入测试**：在源卷 `lv_orig` 上写入数据后，持续观察 `Snap%` 增长是否正常
- **验证快照可用性**：通过 `dmsetup status` 确认状态非 `Invalid`

## 七、经验教训与后续建议

| 类别 | 建议 |
|------|------|
| 容量规划 | 快照 COW 空间不能仅凭经验随意设定，需基于源卷实际写入量评估。建议 COW 空间不低于源卷的 30%，写入密集型场景建议与源卷等大 |
| 监控建设 | 在 LVM 层面部署快照使用率告警，建议阈值：`Snap% > 80%` 触发警告，`> 95%` 触发紧急告警 |
| 技术选型 | 对于有频繁快照需求的场景，评估是否迁移至 LVM Thin Provisioning，其空间利用率和可管理性更优 |
| 自动化运维 | 将 LVM 快照巡检纳入自动化工具体系，通过 `lvs -o+snap_percent` 定期采集并上报 |
