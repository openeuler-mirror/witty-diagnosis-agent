三、排查过程

排查逻辑：三份 Kuafu 独立诊断报告交叉验证 → 逐层收敛到根因

3.1 初始现象

  • 诊断对象：基于 perf 采样文件 /tmp/example-perf-stacks.txt（perf record -F 99 -a -g -- sleep 10）的系统性能分析
  • 主机信息：lgud-bgregg | Intel Core i5-2400 @ 3.10GHz (4核) | 内存 4005800 kB
  • 总样本数：1315 | 唯一栈数：710 | 平均栈深度：~29 层
  • 全局现象：CPU 高度占用（仅 5.5% 空闲），Java 进程占 75.7% CPU，92.93% 样本根帧在 libpthread
  • 应用栈：wrk（压测客户端）→ Vert.x HTTP Server → Netty NioEventLoop → Mozilla Rhino JS 引擎

3.2 假设驱动排查

假设 A：JVM 未启用 JIT 编译导致解释执行成为瓶颈 ✅ 确认

🧪 假设：基于 Interpreter_[j] 帧出现 2868 次（218.1% 帧占比），推测 JVM 以纯解释模式运行

检查项 操作（基于 T1 报告数据） 结论
解释器帧占比 Interpreter_[j] 占 218.1% 帧出现率，为 Top 1 热点 ✅ 极高
热点函数路径 ScriptRuntime.setObjectProp → ScriptableObject.createSlot → putImpl ✅ 全在解释模式下执行
锁同步根帧 [libpthread-2.19.so] 占 92.93% ✅ 吻合（解释模式 + 锁竞争）
调用链完整性 wrk → Netty → Vert.x → Rhino → ScriptableObject，每一步可追踪 ✅ 完整

✅ 确认：JVM 以解释模式运行（可能因 -Xint 参数或 JIT 未生效），Rhino 引擎所有 JS 相关操作均未编译为机器码。可通过 -XX:+PrintCompilation 验证。

假设 B：Mozilla Rhino ScriptableObject 锁竞争导致线程同步瓶颈 ✅ 确认

🧪 假设：基于 92.93% 样本根帧为 libpthread，以及热点路径集中在 ScriptableObject 操作，推测锁竞争是性能瓶颈的主因

检查项 操作（基于 T2 报告数据） 结论
libpthread 占比 1222/1315 (92.93%) 样本的根帧为 [libpthread-2.19.so] ✅ 几乎所有活跃线程都因锁操作消耗 CPU
锁竞争根因调用链 ScriptRuntime.setObjectProp → IdScriptableObject.put → ScriptableObject.putImpl → createSlot（热点叶节点） ✅ 明确且完整
排他性验证 Netty EventLoop 本身非瓶颈（事件循环操作正常），GC 占比 <1% ✅ 排除其他假设
辅助因素 内核 lock_sock_nested + _raw_spin_lock_bh 出现在 TCP 路径（23 样本含内核锁） ✅ 次要因素
双剧本吻合度 锁竞争剧本 + CPU 热点剧本结论完全吻合 ✅

✅ 确认：Mozilla Rhino 引擎的 ScriptableObject 属性操作（createSlot/putImpl/has）内部使用锁保证线程安全。高并发下多线程激烈争抢同一把锁，导致 92.93% 的 CPU 样本消耗在 libpthread 的同步原语上。

假设 C：Rhino ScriptableObject 频繁内存分配触发 GC 压力 ✅ 确认

🧪 假设：基于 createSlot 占 7.2% CPU，getSlot 12.0%，putImpl 10.3%，推测频繁的内存分配是 GC 压力的主因

检查项 操作（基于 T3 报告数据） 结论
ScriptableObject 合计占比 307 样本，23.3% CPU ✅ 主导内存分配
GC 活动占比 CardTableExtension::scavenge_contents_parallel 20 样本（1.5%），合计 GC 28 样本（2.1%） ✅ Young GC 被频繁触发
createSlot 性质 每次调用创建新属性槽 → 新内存分配 ✅ 内存分配热点源头
NativeCall.<init> 157 样本（11.9%）JS 构造函数调用 ✅ 每个请求产生新对象

✅ 确认：Rhino ScriptableObject 的 createSlot 操作为每次 HTTP 请求分配新的属性槽内存，getSlot/putImpl 频繁访问/修改属性数组。大量短期对象触发 JVM Young GC，额外消耗 2.1% CPU。

四、修复方案

4.1 应急处置

步骤 操作 执行人 时间 效果
1 检查 JVM 启动参数：ps aux | grep java 确认是否存在 -Xint 或 -Djava.compiler=NONE 系统管理员 立即 确认/排除 JIT 被禁用的情况
2 使用 -XX:+PrintCompilation 启动 JVM，观察 Rhino 相关方法是否被 JIT 编译 系统管理员 立即 确认 JIT 对 Rhino 方法的编译覆盖情况
3 在 Rhino 中启用优化级别：Context.setOptimizationLevel(9) 开发人员 短期 开启 Rhino 内部优化（即使是解释模式也有一定优化空间）
4 评估是否可以临时将 Rhino 脚本替换为 Java 原生 Handler 开发人员 短期 直接消除 JS 引擎瓶颈

4.2 永久修复计划

修复措施 负责人 完成时间
① JIT 编译确认与修复：检查 JVM 是否启用 JIT（java -version 确认非 -Xint 或 interpreted 模式），确保 Rhino 相关热点方法被 JIT 编译为机器码 系统管理员 / SRE 近期
② Rhino 线程隔离：将 JavaScript 运行时改为线程隔离模式（ThreadLocal Scope），避免多线程共享 ScriptableObject 导致的锁竞争。每个 worker 线程使用独立的 Rhino Context 和 Scope 开发团队 中期
③ 用 Java 原生重写 JS 热路径：将高频执行的 Rhino JS Handler（尤其是 __vertx_http_js__）用 Java 原生代码实现，完全消除 JS 引擎开销 开发团队 中期
④ 替换 JS 引擎：评估将 Mozilla Rhino 替换为更现代的 JS 引擎： 架构团队 长期
→ GraalVM JavaScript（高性能，支持 JIT，部分兼容 Rhino API）
→ Oracle Nashorn（JDK 内置，Java 8+，支持 invokedynamic 优化）
⑤ GC 参数调优：若保留 Rhino，调整 JVM GC 参数以适配高分配速率负载： 系统管理员 近期
→ -XX:+UseG1GC 或 -XX:+UseZGC（低延迟 GC）
→ 增大年轻代：-Xmn 调整
→ -XX:ParallelGCThreads 调整 GC 并发线程数
⑥ 减少 JS 脚本中动态对象创建：优化 Rhino 脚本，使用对象池或缓存复用 ScriptableObject 实例，减少 createSlot 调用频率 开发团队 中期
⑦ 补充监控：部署 JVM GC 日志收集、内存分配速率监控和 CPU Profiler（持续采样），在负载高峰期间多次采样验证优化效果 监控团队 近期

4.3 预期优化效果

优化措施 预期效果 说明
① JIT 启用/确认 Java 执行效率提升 5~10 倍 解释模式 → 机器码编译
② Rhino 线程隔离 消除 ~70%+ 锁竞争开销 92.93% libpthread 大幅下降
③ Java 原生重写 完全消除 Rhino 开销 直接移除最重瓶颈

⑤ GC 参数调优 GC 开销从 2.1% 降至 <1% 减少 GC 停顿时间
