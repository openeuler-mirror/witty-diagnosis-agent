## 三、排查过程

### 3.1 初始现象

- **用户反馈**：连接 `/tmp/uds_backlog.sock` 报 `Connection refused`（ECONNREFUSED）
- **故障摘要**：Unix socket backlog 满，backlog=2，已有 3 个 client 连接占满队列
- **目标进程**：PID 494（uds_backlog）

---

### 3.2 假设驱动排查

#### 假设 A：Socket 路径不存在 / 权限问题

> 🧪 假设：目标 Unix socket 文件未创建或权限配置错误导致拒绝连接

| 检查项 | 操作 | 结论 |
|--------|------|------|
| Socket 文件存在 | `ss -xlp \| grep uds_backlog` | ✅ socket 存在，处于 LISTEN 状态 |
| 进程存活 | `ps -p 494` | ✅ 进程存活 |

**❌ 排除**：Socket 正常创建且处于 LISTEN 状态，非路径/权限问题。

---

#### 假设 B：Backlog 队列饱和 ✅ 确认中间链路

> 🧪 假设：listen backlog 设置过小，accept 队列已满，内核拒绝新连接

| 检查项 | 操作 | 结论 |
|--------|------|------|
| 确认 Recv-Q / Send-Q | `ss -xlp \| grep uds_backlog` | ✅ Recv-Q=3, Send-Q=2（backlog 上限） |
| 计算饱和度 | `3/2 = 150%` | ✅ 饱和度超过 100%，队列溢出 |
| 已建立连接 | `ss -xa` 确认 3 个 ESTAB 连接 | ✅ 3 个已完成连接填满队列 |

**🟡 确认中间链路**：backlog 饱和是新连接被拒绝的直接原因，**但饱和本身是表象，需要继续追查**为什么 Server 不调用 `accept()`。

---

#### 假设 C：Server 进程阻塞 / 无法执行 accept() ✅ 确认根因

> 🧪 假设：Server 进程自身被阻塞在某个操作，无法及时调用 `accept()` 消费队列

**Step 1 — 检查进程状态**

```bash
ps -p 494 -o pid,ppid,stat,comm,wchan
```

| 字段 | 值 | 含义 |
|------|------|------|
| STAT | S+ | 可中断睡眠，前台进程组 |
| WCHAN | unix_wait_for_peer | 等待 Unix socket peer 接受连接 |

**Step 2 — 检查进程线程数**

```bash
cat /proc/494/status | grep Threads
# Threads: 1
```

**关键发现**：单线程进程，`WCHAN=unix_wait_for_peer`，意味着进程卡在 `connect()` 路径上等待 accept 队列空出。

**Step 3 — 分析 FD 分布**

```bash
lsof 或 ss -xa
```

| FD | Socket 号 | 状态 | 说明 |
|----|-----------|------|------|
| fd 3 | socket:[13446] | LISTEN | `/tmp/uds_backlog.sock` listen socket |
| fd 4 | socket:[13447] | ESTABLISHED | 第 1 个自连接成功 |
| fd 5 | socket:[13448] | ESTABLISHED | 第 2 个自连接成功 |
| fd 6 | socket:[13449] | ESTABLISHED | 第 3 个自连接成功 |
| fd 7 | socket:[13450] | UNCONN | 第 4 次 connect 的 socket，尚未建立 |

**Step 4 — 源码确认**

```c
int backlog  = 2;
int nclients = 10;

listen(srv_fd, backlog);

for (int i = 0; i < nclients; i++) {
    cfd = socket(AF_UNIX, SOCK_STREAM, 0);
    connect(cfd, &addr, sizeof(addr));  // 第4次阻塞在此行
}
// accept() 在 for 循环之后——永不可达
while (running) pause();
```

**✅ 结论：单线程自连接(self-connect)导致死锁。**

## 四、修复方案

### 4.1 应急处置

| 步骤 | 操作 | 执行人 | 时间 | 效果 |
|------|------|--------|------|------|
| 1 | 终止阻塞进程: `kill -9 494` | 人工 | 即时 | 释放 PID 和 socket 文件 |
| 2 | 清理残留 socket 文件: `rm -f /tmp/uds_backlog.sock` | 人工 | 即时 | 确保下次启动时无冲突 |
| 3 | 修改程序逻辑后重新启动进程 | 人工/开发 | 修复后 | 恢复正常服务 |

### 4.2 永久修复计划

| 修复措施 | 优先级 | 详细说明 |
|--------|--------|--------|
| **方案一（推荐）**：先 accept 再处理数据 | P0 | 修改程序结构，在 for 循环之前启动 accept 循环，或先 accept 连接再创建后续 client 连接，避免自连接阻塞 |
| **方案二**：多线程/多进程架构 | P1 | 使用独立线程/进程处理 accept，与业务逻辑解耦。主线程负责 accept，工作线程处理业务 |
| **方案三**：非阻塞 + I/O 多路复用 | P1 | 使用 `select()`/`poll()`/`epoll()` 事件驱动模型，无阻塞风险 |
| **方案四**：避免自连接模式 | P0 | Server 进程不应在同一进程中连接自身 listen 地址。如需要测试，应使用独立进程 |
| **方案五**：增大 backlog（仅缓解） | P2 | 将 `backlog=2` 提升至 128 或 4096，但这仅能延缓死锁发生，不能根治设计缺陷 |
| **增加监控**：监控 backlog 饱和度 | P2 | 部署对 UDS listen socket Recv-Q 的监控，当饱和度 >80% 时告警，早期发现阻塞风险 |

### 4.3 修复代码示例

```c
// ✅ 正确做法：先 accept，再处理其他逻辑
int srv_fd = socket(AF_UNIX, SOCK_STREAM, 0);
listen(srv_fd, 128);  // 适当增大 backlog

// 启动 accept 循环（可放在独立线程）
while (running) {
    int cfd = accept(srv_fd, NULL, NULL);
    if (cfd > 0) {
        // 处理客户端连接
    }
}

// 或使用多线程
pthread_t tid;
pthread_create(&tid, NULL, accept_loop, &srv_fd);
// 主线程继续执行其他业务...
```
