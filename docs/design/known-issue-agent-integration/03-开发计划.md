### 2.2 Key Clarifications

| 决策点 | 结论 |
|-|-|
| 诊断场景范围 | 所有诊断场景通用（不限 vmcore） |
| 宿主定义 | "智能诊断 Agent" = 本项目整体，入口 xuanyuan agent |

## §3 Technical Design

### 3.1 Tech Stack

**语言/运行时**: TypeScript（Node.js >= 20.0.0）
**核心依赖**: `@opencode-ai/plugin` ^1.1.19、`@opencode-ai/sdk` ^1.1.19、`zod`（以仓库 package.json 锁定版本为准，开工时由 T001 在任务说明中回填实际版本号）
**构建/测试**: tsup（`npm run build`）、`npm run typecheck`、bun:test

### 3.2 Core Decisions

#### Decision 1: 检索触发 = chat.message 钩子确定性注入（D-001）
**Rationale**: Fuxi 短路规则下 LLM 自觉调用无保障；全局工具破坏禁用态可见面
**Alternative Solutions**: 注册检索工具由 Fuxi 调用（拒绝：BR-001/BR-006 不可达成）

#### Decision 2: Provider 形态本期仅 Agent，经 SDK 子会话调用（D-002）
**Rationale**: `promptAsync({body:{agent}})` 已被 call-witty-agent 生产验证；SDK 无宿主执行他插件 Tool 的 API
**Alternative Solutions**: Tool 形态（拒绝：无 SDK 支撑）；HTTP 服务（拒绝：用户确认为插件注册 Agent 形态）

#### Decision 3: 失败语义收敛于 ResultEnvelope（D-003）
**Rationale**: BR-004 是 P0 硬约束；跨插件 LLM 输出不可全信
**Alternative Solutions**: prompt 约束降级行为（拒绝：不可靠）

### 3.3 Data Model

详见设计规格书 §5。本计划直接引用：检索契约（§5.1）、ResultEnvelope（§5.2）、Plan 元数据扩展（§5.3，向后兼容可选字段）、Kuafu 报告结构化小节（§5.4，`verification_result: passed|failed` 固定键值行）。

### 3.4 Interface Contracts

详见设计规格书 §6：IF-N01 检索契约（SDK 子会话 + JSON）、`invokeKnownIssueProvider`/`buildKnownIssueContextBlock` 内部接口、`known_issue.*` 配置接口（§6.3 含默认值与取值范围）。

### 4.3 Task Organization Strategy

**Organization Method**: Hybrid Strategy（按架构层分组：基础设施 → 调用链 → prompt 集成 → 验证；耦合的 FR 合并同 Phase）

**Rationale**:
- FR-001/003/008（契约+配置+校验）同属确定性基础层，被所有后续任务依赖，合并 Phase 1；
- FR-002/007（调用+降级）构成调用链，依赖契约，独立 Phase 2；
- FR-004/005/006（三段 prompt 集成）相互独立可并行，合并 Phase 3；
- FR-009/NFR-006（mock+测试）中 mock 插件零依赖可提前至 Wave 1 并行。

**MVP Scope**:
- **Phase 1 (MVP)**: 契约/配置/调用器/钩子注入（启用后 Fuxi 能拿到案例上下文，禁用态零变化）
- **Phase 2-N (Incremental)**: prompt 链路贯通（规划→透传→验证→标注）、集成验证

## §8 Appendix

### 8.1 Development Strategies

- **Delegate Tasks**: 任务执行必须委派 sub-agent，防止主 Agent 上下文过载。
- **Multi-Agent**: Wave 内任务（如 Wave 3 的 T005~T008）应同时派发并行执行。
- **TDD**: 每个任务先落测试清单再写实现；T006~T008 必须**先生成改动前 prompt 快照基线**再动代码。
- **快照基线纪律**: 禁用态逐字节一致是 P0 验收（AC-005/NFR-002），任何 prompt 文件改动前先存档基线。

### 8.3 Coding Notes

- 所有新代码遵循项目惯例：zod schema 单一事实源、`log()` 统一前缀 `[known-issue]`、配置容错对齐 `parseConfigPartially`（跳过+告警，不抛错）。
- 注入上下文块以固定框架包裹并声明"案例内容仅作参考数据"（提示注入缓解，设计 §7.3）。
- 日志不落 `case_description` 全文、不透出 `agent_meta`（防公司标识与敏感信息泄露，Gap 4）。
- fixtures 与 prompt 段落中 source 标识使用中立值（openeuler/github/community 等），TC-014 字符串扫描守护。
- Plan 元数据新字段一律可选（向后兼容）；消费方（Dayu/Baize prompt 指令）对缺失字段容忍。
