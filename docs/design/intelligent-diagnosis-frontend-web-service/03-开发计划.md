## §3 Technical Design

### 3.1 Tech Stack

- **Runtime**: Node.js >= 20（与 agent 一致）
- **Language**: TypeScript 5.x
- **Backend Framework**: Fastify 4.x（原生 SSE 友好、轻量）
- **Agent 集成**: `@opencode-ai/sdk` ^1.1.19（仓库现有依赖）
- **持久化**: **Knex** 查询构建器 + 方言驱动 `sqlite3`（默认）/ `mysql2`（可选）；统一 **Knex migrations** 建表与演进；日志正文落盘、DB 存索引（默认 SQLite 文件 `~/.witty-diagnosis-agent/database/witty.db`）。说明：Knex 为异步 API，存储层接口统一为 async（影响面限于存储层与 await 调用处）
- **认证**: `openid-client`（OIDC，默认）/ LDAP 适配器（`auth.provider` 可配）
- **实时**: SSE（Server-Sent Events，原生、最简）
- **Frontend**: React 18 + Vite 5 + TypeScript；轻量状态管理（Zustand 或 Context）
- **部署/安装**: `start.sh`（本地一键安装）；容器化 = 前端镜像（nginx 托管 SPA + 反代后端）+ 后端镜像 + `docker-compose`（含可选 MySQL 服务）
- **Build/质量**: tsup/tsc、ESLint、Vitest（后端单测）、Playwright（可选 E2E）

### 3.2 Core Decisions

#### Decision 1: 进程级任务隔离（每任务独立 OpenCode 进程 + 重定向 HOME/XDG）
**Rationale**: agent 内含进程级全局态（`_mainSessionID`）与共享文件路径（`hosts.ini`、`baize/reports`）；进程隔离以"每进程仍是单用户"复用现有假设，**零改动内核**即获完全隔离；进程数受全局并发上限封顶。详见 [02 §1.2 D-001](./02-需求设计规格书.md)。
**Alternative Solutions**: 单 OpenCode 服务多会话（否决：需改造冻结内核的全局态与目录命名，风险高、超范围）。

#### Decision 2: SDK 会话 + 事件流合成进度/日志，双信号判定完成
**Rationale**: 复用 `cli/run/runner.ts:88-106` 已验证的 `event.subscribe` + `promptAsync(tools:{question:false})` 模式；agent 无原生进度%，由事件→里程碑映射合成；完成以"Xuanyuan 终消息报告路径关键字 + `baize/reports/*.html` 出现"双信号判定。详见 [02 §1.1.3、§4.1](./02-需求设计规格书.md)。
**Alternative Solutions**: 裸 `session.idle`（否决：每轮边界都触发，不可靠）；轮询报告目录 glob（否决：依赖文件名约定，已用每任务全新 HOME 规避）。

#### Decision 3: 凭据内存驻留 + JIT hosts.ini + 终态擦除 + 事件流脱敏
**Rationale**: agent 多处运行期（含 `kuafu/agent.ts:136`）以明文写 hosts.ini，故"加密存储+用完即焚+脱敏"必须由宿主确定性兜底：擦除整个 taskHome 覆盖任意子代理写盘，脱敏作用于事件流（含 Kuafu 回显）而非仅报告。详见 [02 §1.2 D-003](./02-需求设计规格书.md)。
**Alternative Solutions**: 仅脱敏最终报告（否决：运行期日志已含明文）；凭据落库加密（否决：增加泄漏面，违背"不保存"承诺）。

#### Decision 4: 持久化可插拔（Knex + sqlite3/mysql2，统一 migrations）
**Rationale**: 需求要求"默认 SQLite、同时支持 MySQL"。Knex 对两方言一等支持、内置迁移工具，一套代码两方言，避免手写双驱动的方言漂移；migrations 作为 `start.sh` 与容器 entrypoint 的唯一建表来源，保证安装一致性。详见 [02 §1.2 D-004、§5.3](./02-需求设计规格书.md)。
**Alternative Solutions**: 手写双 Repository（否决：维护成本高、易方言漂移）；ORM Prisma/TypeORM（否决：依赖重、与既有 SQL 风格偏离）。

#### Decision 5: 前后端分离 + 容器化（前端 nginx 反代后端，后端单实例）+ start.sh 一键安装
**Rationale**: 前端纯静态、后端有状态（全局队列/内存凭据/每任务子进程）。前端 nginx 反代使浏览器同源、免 CORS；后端保持单实例以延续 D-001/D-003 进程内态前提。`start.sh`（本地）与容器 entrypoint 复用同一 Knex migrations 建表。详见 [02 §1.2 D-005/D-006、§2.4](./02-需求设计规格书.md)。
**Alternative Solutions**: 后端多副本水平扩展（否决本期：破坏全局并发上限与内存凭据，需外置队列+切 MySQL，列为演进）；前端独立域名+CORS（否决：增加跨域复杂度，反代更简）。

### 3.3 Data Model

实体与关系见 [02 §5.1](./02-需求设计规格书.md)。本期落地：

- `User { id, external_subject(IdP), display_name }` — 1:N → Task
- `Task { id(UUID,PK), owner_id(FK→User,1:N), title, fault_time, mode(online|offline), status, progress, current_stage, created_at, updated_at, expire_at }`
- `OnlineTarget { task_id(FK→Task,1:1), host_ip, ssh_user, ssh_port }` — **不含密码**
- `OfflineUpload { id, task_id(FK→Task,1:N), filename, stored_path, size }`
- `Execution { id, task_id(FK→Task,1:N), attempt_no, started_at, ended_at, exit_reason }`（重试=同 task 新增 execution）
- `LogChunk { id, execution_id(FK→Execution,1:N), seq, ts }`（正文落盘，DB 存索引/偏移）
- `Report { id, task_id(FK→Task,0..1), html_path, md_path, report_no, fault_level }`（已脱敏）
- `Rating { task_id(FK→Task,0..1, 唯一), stars(1..5), updated_at }`
- 凭据**无持久化模型**（仅内存密文驻留）。
- 建表/演进经 **Knex migrations**（一套脚本适配 SQLite/MySQL）；跨方言约束：主键/UUID 用 `varchar(36)`、统一时间戳类型、布尔在 SQLite 落整型、避免方言独有 SQL（详见 [02 §5.3](./02-需求设计规格书.md)）。

### 4.2 Task Organization Strategy

**Organization Method**: Hybrid Strategy（先架构分层骨架，再按功能耦合分组）。

**Rationale**:
- 绿地工程遵循 **Framework First**：先脚手架与存储骨架，再业务。
- **最高风险前置**：T002（R-1 headless 验证）是整个集成方案的成立前提，置于关键路径起点，失败即早回退。
- 按耦合分组：Runner/调度/API/前端构成"诊断主链路"耦合簇（Phase1 MVP）；认证/隔离/凭据/脱敏/生命周期/留存构成"多用户与安全"耦合簇（Phase2），二者依赖明确、可分波并行。

**MVP Scope**:
- **Phase 1 (MVP)**: 骨架 + 离线优先的端到端诊断主链路（新建→执行→实时进度/日志→看报告），单用户占位、先不接 IdP。验证 D-001/D-002 真实可跑。
- **Phase 2 (Incremental)**: 在线模式 + 外部认证与用户隔离 + 凭据/脱敏/用完即焚 + 取消/重试/删除 + 报告下载/评分 + 留存清理 + 上传配额。

## §8 Appendix

### 8.1 Development Strategies

- **Delegate Tasks**: 任务执行委派子代理，避免主 Agent 上下文膨胀。
- **Multi-Agent**: 同波任务并行下发（Wave 1：T001/T002/T003；Wave 3：T008/T009）。
- **TDD**: 每任务先定测试场景再实现（存储/调度/脱敏/状态机均为可单测纯逻辑优先）。
- **风险前置**: T002（R-1）必须最先完成，作为整个集成方案的成立门禁。

### 8.2 Risk List

| Risk | Impact | Mitigation Measures |
|------|------|----------|
| R-1：headless 下 Xuanyuan 交互循环卡死 | High | T002 冒烟优先验证；前置完整 prompt；不通过则 refine 设计（如启用 auto-diag 模式或补默认应答） |
| R-2/R-3：隔离依赖 HOME/XDG 且仅 Linux | High | 部署锁定 Linux/openEuler；spawn 时同时重定向 HOME+XDG_DATA_HOME+XDG_CACHE_HOME；集成测试断言隔离 |
| 凭据明文落盘窗口（含 Kuafu 运行期） | High | taskHome 终态强制擦除 + 事件流脱敏；抽检验收（T010/AC-009） |
| 进度为近似合成、≤2s 依赖事件 cadence | Medium | 里程碑事件判据明确（02 §4.1）；NFR-004 以"可感知实时"验收 |
| 上传不设大小上限的磁盘耗尽 | Medium | 流式落盘 + diskQuotaBytes 熔断告警（T013） |
| 并发上限默认值与资源匹配 | Medium | 默认 4，上线前按单进程内存实测调优（G3） |
| agent 升级改变 SDK/prompt 行为 | Medium | 集成层仅依赖稳定 SDK 接口；保留 T002 冒烟为回归门禁 |
| SQL 方言漂移（SQLite↔MySQL 行为差异） | Medium | 统一 Knex migrations；禁用方言独有 SQL；T003 对两方言各跑测试（SQLite 全量 + MySQL smoke） |
| 后端单实例为可用性单点 / 误配多副本 | Medium | 文档明确单实例约束（D-005）；compose 不设 replica；水平扩展演进须先切 MySQL + 外置队列 |
| SSE 经 nginx 反代被缓冲导致非实时 | Medium | nginx `proxy_buffering off`、合适超时；T016 验收实时性 |
| start.sh 非幂等破坏已有数据 | Medium | 依赖 Knex migrations 幂等；二次执行不重复建表；T015 幂等用例 |
| 默认数据目录与 agent 状态根同父 | Low | Web 服务 DB 写真实 HOME、诊断子进程各自重定向 HOME，互不冲突（BC-011）；容器内经命名卷持久化 |

### 8.3 Coding Notes

- **环境隔离**：每任务 spawn 必带 `HOME`、`XDG_DATA_HOME`、`XDG_CACHE_HOME`、`OPENCODE_CLI_RUN_MODE=true`；`tools:{question:false}` 作用于 Xuanyuan。
- **安全**：密码全程不明文落盘/回显/入日志；HTTPS；越权统一 404；脱敏在持久化/推送前。
- **资源回收**：runner 必须 `finally` 关进程+kill+擦除 taskHome（含异常路径）。
- **冻结区**：严禁修改 `src/opencode/**`、`skills/`、`src/xiaoO/`。
- **可测试性**：状态机、进度合成、脱敏器实现为纯函数/可注入桩，优先单测。
- **存储**：一律经数据访问层(Knex/Repository) 读写，禁止业务代码出现方言 SQL；建表/演进只走 Knex migrations（start.sh 与容器 entrypoint 复用同一套）；跨方言用 `varchar(36)` 主键、统一时间戳、SQLite 布尔落整型。
- **部署**：前端经 nginx 反代后端（同源免 CORS，SSE 关缓冲）；后端单实例（勿配多副本）；镜像/compose/脚本不固化明文凭据，连接信息走环境变量/配置。
- **安装**：start.sh 用 `$HOME` 而非硬编码家目录；幂等可重入；默认 SQLite 数据目录 `~/.witty-diagnosis-agent/database/`。

#### Decision 4: 持久化可插拔（Knex + sqlite3/mysql2，统一 migrations）
**Rationale**: 需求要求"默认 SQLite、同时支持 MySQL"。Knex 对两方言一等支持、内置迁移工具，一套代码两方言，避免手写双驱动的方言漂移；migrations 作为 `start.sh` 与容器 entrypoint 的唯一建表来源，保证安装一致性。详见 [02 §1.2 D-004、§5.3](./02-需求设计规格书.md)。
**Alternative Solutions**: 手写双 Repository（否决：维护成本高、易方言漂移）；ORM Prisma/TypeORM（否决：依赖重、与既有 SQL 风格偏离）。
