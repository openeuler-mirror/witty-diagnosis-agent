# Witty 智能诊断 Agent 技术方案概述

## 一、问题背景

在操作系统运维领域，故障诊断一直是保障业务稳定运行的关键环节。然而，随着系统规模不断扩大、业务形态向超节点演进，传统依赖人工经验的诊断方式已难以满足高效、规模化的运维需求。

### 主要技术挑战

#### 诊断周期长，高度依赖专家经验

OS 故障覆盖内核、硬件、系统服务、应用、网络等多层面，排查链路呈网状复杂结构。普通运维人员因缺乏深度经验积累，难以快速定位问题根源，必须依赖资深专家介入分析。从故障发生到完成根因定位，传统故障诊断方法通常需数小时甚至数天，严重影响业务恢复效率。

#### 缺乏标准化诊断流程与工具

传统运维中，不同运维人员、团队缺乏统一的诊断规范与工具体系，各自采用差异化的排查思路和操作手段，导致诊断过程缺乏统一性与规范性。这一问题直接导致：一是运维知识难以跨团队共享、沉淀与传承，专家经验无法形成标准化资产；二是新型故障、跨领域故障的排查缺乏统一指引，响应效率低下；三是新运维人员上手周期长，一旦核心专家离岗，易出现故障诊断能力断层，进一步加剧运维风险。

#### 跨领域协同成本高，难以适应规模化需求

随着算力形态从单节点向超节点演进，系统规模呈指数级扩展，超节点场景下可观测数据量爆发式增长。复杂故障的分析已不再局限于单一领域，而是需要内核、网络、存储、AI 框架、应用开发等多领域专家协同协作。传统人工分析方式依赖专家点对点沟通，协同成本高、效率低，无法支撑大规模集群的批量运维需求，难以适配规模化部署场景。

在此背景下，Witty 智能诊断gent 应运而生，通过融合 AI 技术与内核可观测能力，为 openEuler生态提供全流程自动化故障诊断与可控修复方案，推动 OS 故障诊断迈入智能化时代。

## 二、落地效果

### 案例一：系统Crash故障诊断

以ixgbe驱动BUG导致系统Crash问题诊断为例，运维人员输入故障现象，例如：“我有个系统发生了 crash， vmcore 相关文件和内核源码归档在76.53.137.175的/home/crash/目录下，请分析原因。”，智能诊断 Agent即可自动基于系统日志、vmcore文件、内核源码等相关信息，快速定位到异常模块、问题函数和代码行，自动生成结构化诊断报告，清晰呈现故障根因、关键证据链、影响范围与优化建议，将传统数小时的诊断流程压缩至分钟级，大幅提升故障处理效率。
!\[image]\(assets/vmcore\_diag.png null)

### 案例二：磁盘故障诊断

以硬盘坏道问题诊断为例，运维人员只需输入故障描述，例如：“请诊断 2026-03-05 14:31 前最近一次硬盘故障，日志路径：/tmp/diskfault/logs”。智能诊断 Agent 将自动关联用户提供的多维遥测数据，包括硬盘 SMART 参数、运行日志、系统状态快照等，精准定位物理坏道等底层根因，自动构建清晰的故障传播链路，完整呈现从异常现象到根本诱因的全链路诊断逻辑。
!\[image]\(assets/disk\_diag.png null)

### 案例三：系网络故障诊断

以黑洞路由问题诊断为例，运维人员仅需输入故障现象，例如：“我的服务器 76.53.183.189 无法访问网段 10.0.0.0/8，请进行诊断”。智能诊断 Agent 将基于内置的标准化脚本与工具集，自动完成服务器网络及系统状态的全量信息采集，通过分层递进式排查方式逐层定位问题，最终精准锁定根因，并自动生成包含故障时间窗口、根因分析、故障路径回溯等内容的标准化诊断报告。

## 三、构筑思路

Witty 智能诊断 Agent 基于「假设-验证」（Hypothetico-Deductive）故障排查范式与 Multi-Agent 协同架构，实现了全链路的自动化故障诊断能力。

系统由六个核心 Agent 组成，采用流水线式协作模式，实现了从故障现象到根因分析、修复方案的完整闭环：

```

│                 │    │                 │    │                 │
│   Fuxi          │    │   Dayu          │    │   Kuafu         │

│   Xuanyuan      │◀───│   Baize         │◀───│   证据数据       │
│  (全链路总控)    │    │  (根因分析)      │    │                 │
│                 │    │                 │    └─────────────────┘
│ • 流程协调       │    │ • 证据链构建     │
```

1. **诊断启动**：用户描述故障现象，系统开始诊断流程
2. **规划阶段**：Fuxi Agent 基于故障现象生成诊断排查方案
3. **编排阶段**：Dayu Agent 将诊断方案转化为具体任务集并进行调度
4. **执行阶段**：Kuafu Agent 执行诊断任务，收集证据
5. **分析阶段**：Baize Agent 基于收集的证据进行根因分析
6. **修复阶段**：Nuwa Agent 生成修复方案和预防建议
7. **报告生成**：汇总诊断过程和结果，输出完整报告

## 四、 关键挑战与应对措施

### 挑战一：单Agent架构的局限性

**挑战描述**：故障诊断涉及复杂的全链路流程，单个Agent难以承担所有职责。单Agent架构存在以下问题：首先是职责过载，需要同时负责规划、执行、分析、报告等多个阶段，违反单一职责原则；其次是token限制问题，复杂诊断场景容易触发大模型token限制，即使采用压缩策略也可能导致关键信息丢失；最后是诊断准确率下降，频繁的上下文切换和信息压缩会降低诊断的准确性和深度。这些问题严重影响了诊断系统的可靠性和效率。

**应对措施**：Witty智能诊断Agent采用流水线式多Agent协作架构，通过职责专业化划分解决单Agent架构的局限性。系统将复杂的诊断流程分解为规划、执行、分析等独立阶段，每个Agent专注于特定的核心职责：Fuxi负责诊断规划和方案生成，Dayu承担任务编排和调度，Kuafu专注于证据收集和工具执行，Baize负责根因分析和故障链路构建，Nuwa生成修复方案，Xuanyuan协调全链路协作。这种架构设计避免了单Agent的职责过载问题，有效解决了token限制和上下文切换带来的信息丢失风险，显著提升了诊断的可靠性和效率。

### 挑战二：大模型缺乏系统性诊断方法论导致的随机探索困境

**挑战描述**：大模型在排查问题时缺乏系统性方法论指导，呈现出边查边分析的随机性特征，没有明确的排查路径，往往基于直觉进行尝试。这种随机探索方式导致验证效率低下，诊断过程冗长，难以应对复杂的系统故障。

**应对措施**：资深专家在排查系统Hang死等疑难杂症时，往往采用先提出根因假设再排查验证的结构化分析方式。Google SRE团队提出的"假设-验证（Hypothesis-verification）"方法论，遵循"观察现象→提出多个假设→多路验证→排除或确认"的严谨流程。Witty智能诊断Agent将这一方法论深度融入多Agent协同工作流程，通过系统化的假设生成、并行验证和证据整合机制，将传统的串行排查模式转变为并行验证模式。Fuxi负责系统性地提出多个根因假设，Dayu将这些假设转化为并行的诊断任务集，Kuafu同步执行多个诊断任务以高效验证或排除假设，Baize基于验证结果构建完整的证据链并确认最终根因。这种方法论的引入显著提升了诊断效率，实现了分钟级的精准故障定位。

### 挑战三：大模型缺乏具体故障模式的专业诊断流程

**挑战描述**：不同故障模式的诊断流程存在显著差异，大模型基于通用预训练知识难以理解这种差异性，缺乏针对特定故障模式的专业诊断流程指导。对于简单故障，模型可能基于预训练知识给出大致方向，但面对复杂故障时，由于缺乏针对不同故障模式的专业根因分析流程和规范指导，模型只能基于原子化的系统命令进行顺序尝试，需要不断试错，耗时长且诊断准确率低。此外，对于预训练时未知的知识和故障，单靠模型基本上无法给出准确的根因。例如，对于支持节点内存借用的超节点架构，当节点B的内存条物理损坏导致节点A读写失败时，模型由于不了解这种特殊架构特性和节点拓扑关系，即使获取了完整日志也只能定位到表面现象，无法找到真正的根因。

**应对措施**：Witty智能诊断Agent基于OS全栈（硬件层→内核层→系统服务层）的故障模式库梳理和构建故障模式诊断Skill集。通过深入分析各类故障模式的特征、诊断逻辑和处置流程，将专家的领域知识和诊断经验结构化地转化为标准化的Skill。每个Skill都包含完整的诊断流程定义、工具链配置、证据收集规范和根因判定规则，形成了覆盖全栈故障场景的诊断能力体系。这种系统化的Skill构建机制确保了模型能够遵循专业的诊断流程进行精准排查，有效处理复杂故障场景，建立完整的故障传播链路。

### 挑战四：模型基于局部信息过早下结论的认知偏差

**挑战描述**：大模型倾向于使用简单工具（如head命令）读取日志片段，并在发现表面关联后立即下结论，无法处理复杂的"一因多果"和"多因多果"故障场景。这种倾向导致模型在分析过程中存在信息不完整、因果关系误判、级联故障分析能力不足等问题。例如，一个底层硬件故障可能引发多个上层服务异常，或者在同一时间段内多个独立根因共同作用导致多个故障现象，模型往往只能定位到最明显的表面症状，而无法建立完整的故障传播链路或区分不同根因的影响范围。

**应对措施**：Witty智能诊断Agent通过建立标准化的证据收集流程确保信息完整性，采用"先宏观后微观"的分析原则，避免过早陷入细节。系统要求构建完整的时间线和证据链，基于全面的信息进行综合分析，而不是基于局部信息做出判断。Kuafu在执行诊断任务时，会收集全面的系统信息，包括日志、性能指标、配置信息等，确保Baize在分析时有足够的证据支持，能够构建完整的故障链路，准确识别根本原因和表面症状。

### 挑战五：大模型亚健康问题诊断能力不足导致的早期预警缺失

**挑战描述**：大模型善于识别带有Error、Failure等明确错误关键字的故障，但对于没有明显错误标识的亚健康问题（如性能下降、资源异常等）诊断能力不足。亚健康问题通常没有明显的错误日志，问题表现为性能缓慢、资源利用率异常等非致命症状，缺乏统一的判断标准和阈值，传统的基于关键字匹配的方法难以有效识别。

**应对措施**：Witty智能诊断Agent通过建立性能基线和异常检测机制，开发专门的亚健康诊断Skill（如预失效检测、性能异常分析），引入长期监控数据进行趋势分析，基于统计方法识别异常模式。系统能够通过对比历史数据和基线值，识别出性能指标的异常变化，即使没有明确的错误日志也能发现潜在的亚健康问题。这种能力使系统能够在问题恶化前提前发现并预警，实现了从被动响应到主动预防的转变。

### 挑战六：诊断结果缺乏可解释性的信任危机

**挑战描述**：大模型的推理过程缺乏透明度，导致诊断结果的可解释性差。用户难以理解诊断结论的依据和推理过程，降低了对诊断结果的信任度。同时，诊断经验难以有效沉淀和复用，无法形成可传承的知识库。这种"黑盒"特性使得诊断过程缺乏可信度验证，知识传递困难。

**应对措施**：Witty智能诊断Agent建立了结构化的证据展示机制，清晰呈现诊断依据和推理过程。系统提供详细的诊断过程记录和决策路径，包括执行的命令、收集的证据、分析的逻辑等。通过标准化的报告格式，将分散的证据串联为完整的故障链路，使用户能够清晰理解诊断结论的由来。同时，系统支持诊断知识的结构化存储和检索，将成功的诊断案例沉淀为可复用的知识，形成持续演进的诊断知识库。

## 五、下一步计划

基于当前能力和 OS 全栈故障诊断的需求，Witty 智能诊断 Agent 需要在以下几个方面进行能力补充：

### 1. 扩展故障模式覆盖

- **硬件层面**：增强对 CPU、内存、存储、网络等硬件故障的诊断能力
- **内核层面**：深入支持文件系统、内存管理、进程调度等内核子系统的故障分析
- **应用层面**：扩展对数据库、中间件、Web 服务等应用层故障的诊断支持

### 2. 增强诊断深度和准确性

- **根因定位精度**：从当前的模块级定位提升到代码行级定位
- **预测性诊断**：基于历史数据和趋势分析，实现故障的预测性诊断
- **因果关系挖掘**：增强对复杂故障因果关系的挖掘能力

### 3. 优化用户体验

- **交互式诊断**：支持用户参与的交互式诊断流程
- **可视化展示**：提供更直观的故障链路和诊断过程可视化
- **知识沉淀**：建立诊断知识库，支持经验的积累和复用

通过持续的能力扩展和技术演进，Witty 智能诊断 Agent 将逐步实现对 OS 全栈故障的全面覆盖，为企业提供更加智能、高效、可靠的故障诊断解决方案。
