项目 内容
故障标题 内核 PID 预留机制缺陷导致 Kernel Panic — set_pid_unused BUG_ON 触发

3.2 假设驱动排查

假设 A：硬件内存故障（MCE/ECC）导致代码执行异常

🧪 假设：内存硬件错误导致 set_pid_unused 函数执行异常或数据损坏

检查项 操作 结论
内核日志 MCE 记录 检查 vmcore dmesg 中 MCE/ECC 错误 ✅ 无相关硬件错误记录
reserved_data 指针 crash> px reserved_data ✅ 结果为 NULL（预期行为，非内存损坏）
反汇编代码完整性 crash> dis set_pid_unused ✅ 指令流正常，非内存 bitflip 导致

❌ 排除：无硬件错误证据，代码执行路径正常，reserved_data==NULL 是预期状态而非损坏。

假设 B：`reserved_data` 全局变量被意外篡改

🧪 假设：reserved_data 指针本应有值，但被其他内核路径错误清零

检查项 操作 结论
reserved_data 值 crash> px reserved_data ✅ 值为 NULL
reserve_idr 值 crash> px reserve_idr ✅ 值为 NULL
检查其他进程预留状态 无法遍历（PARTIAL DUMP 限制） ⚠️ 有限信息

❌ 排除：CompositorTileW 进程本身未参与 PID 预留机制，reserved_data==NULL 是其正常状态。问题出在 __change_pid 错误地调用了与该进程无关的 set_pid_unused。

假设 C：内核 PID 预留机制存在逻辑缺陷 ✅ 确认根因

🧪 假设：__change_pid 函数在 CONFIG_PID_RESERVE 路径中错误使用 current 而非 task

Step 2 — 定位缺陷源码位置

源码位置：kernel/pid.c:446（__change_pid 函数内）

c 
static void __change_pid(struct task_struct *task, enum pid_type type,
                        struct pid *new)
{
    ...
    free_pid(pid);
#ifdef CONFIG_PID_RESERVE
    if (task_pid_reserved(current))                          // ← BUG: 使用 current
        set_pid_unused(current->group_leader->pid, current->pid);  // ← BUG: 使用 current

Step 3 — Identity 检查（关键证据）

对象 task_struct 地址 对应进程
current (TASK) ffff94fdb131c080 PID 3665228 CompositorTileW
__exit_signal 形参 tsk (RBP) ffff94fca4f3c080 被回收的子 task（另一个进程）

结论：两个地址不一致。current 是正在执行退出逻辑的 CompositorTileW 进程，而 __exit_signal 的参数 tsk 是正在被回收的另一个子 task。

Step 4 — 反汇编验证

__exit_signal 入口处：

asm 
0xffffffff93ee86fe <__exit_signal+14>:  mov    %rdi,%rbp    # RBP = tsk (形参)

RBP = ffff94fca4f3c080（tsk）≠ TASK = ffff94fdb131c080（current），确认 Identity 不一致。

set_pid_unused 入口处：

Step 5 — 全局变量确认

5.2 关联事件（非直接相关）

系统日志中记录了 2 次 cgroup 级别 OOM kill 事件，但与本次内核崩溃无直接因果关系：

5.3 风险提示

  • 该缺陷存在于启用了 CONFIG_PID_RESERVE 内核编译选项的系统中
  • 触发条件：release_task(p) 回收非 current 自身的 task（子进程/线程退出场景），且被回收的 task 在 __change_pid 中进入 PID 预留归还路径
  • 任何运行相同内核版本的节点均存在触发此缺陷的潜在风险
  • 建议尽快排查集群中所有运行该内核版本的节点，制定升级计划
