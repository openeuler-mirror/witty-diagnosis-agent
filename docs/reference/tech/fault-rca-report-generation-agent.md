# 智能故障诊断 Agent 的根因分析引擎：从证据拼图到决策报告

## 概述

在 witty-diagnosis-agent 的 Multi-Agent 体系中，各个前置诊断 Skill（如 VMCore 分析、磁盘健康诊断、Docker 故障分析等）负责从不同维度采集"证据碎片"——日志片段、指标异常、系统状态快照。然而，**收集证据不等于诊断完成**。真正的诊断发生在将这些碎片拼合成完整叙事、追溯因果链条、并最终输出可操作的决策报告的那一刻。

`fault-rca-report-generation` Skill 就是负责这一关键环节的 **Meta-Skill（元技能）**。它不直接采集任何底层数据，而是定义了一套完整的**推理协议（Reasoning Protocol）**，指导诊断 Agent 如何：

- 将多源异构证据归一化为统一的推理实体
- 重建故障的时间线与逻辑因果链
- 对根因候选进行置信度评估
- 输出标准化的、面向人类运维人员的故障诊断报告

> 如果将 witty-diagnosis-agent 比作一个医疗诊断团队，各检测科室（检验科、影像科）负责出检查报告，那么这个 Skill 就是主治医师的临床推理方法论——如何结合所有检查结果，做出诊断，并撰写病历。

## 背景

### 为什么需要这个 Skill？

现代分布式系统的故障诊断面临一个核心矛盾：**数据丰富，但信息贫乏**。

一个典型的故障场景会产下列诊断数据：

| 数据来源 | 典型产出 | 信息量级 |
|---------|---------|---------|
| VMCore 分析 | 内核崩溃栈 + 内存转储分析 | 数百行结构化分析 |
| 磁盘诊断 | SMART 数据 + I/O 错误日志 | 数十个指标 + 时间戳 |
| 网络诊断 | 连通性测试 + 抓包分析 | 数百条连接记录 |
| OOM 分析 | 系统/进程/CGroup 内存状态 | 多维度内存快照 |
| Docker 分析 | 容器状态 + 资源限制 | 数十个配置项 |

这些数据各自独立看时，意义有限。它们之间的关系——时序上的先后、逻辑上的因果——才是真正有价值的信息。传统做法依赖高级工程师凭借经验在脑海中完成这些关联，但这种方式存在几个根本性问题：

1. **认知负荷过高**：人在短时间内处理多维度异构数据（内核日志、SQL 慢查询、网络抓包、应用报错）并建立因果关联，极易遗漏关键线索
2. **知识难以沉淀**：经验丰富的 SRE 的推理过程无法被有效复用和传承
3. **报告质量参差不齐**：不同工程师输出的诊断报告格式各异，关键信息（根因、影响范围、置信度）可能缺失或表述不一致
4. **排查效率低**：无结构化方法的排查容易陷入"试错循环"——逐个猜测、逐个验证，缺乏系统性

### 设计目标

> 让 Agent 像一个经验丰富的 SRE 那样思考和推理。

具体而言，这个 Skill 的设计目标有四个：

1. **结构化推理**：为 Agent 提供明确的推理框架，而非自由联想。通过"现象驱动"的因果链构建和"假说-演绎"的验证方法，确保根因推断过程可追溯、可复现
2. **证据为依据**：所有结论必须有对应的证据支撑，严禁"无中生有"。每一次推理跳跃都需要正向证据（支持）和反向证据（反对）的平衡
3. **标准化输出**：确保无论是什么类型的故障，最终的诊断报告都遵循统一的格式，让读者能快速定位关键信息
4. **自我评估**：引入置信度机制，让 Agent 能表达对自身结论的确信程度——这是 AI 辅助诊断中最关键但又最容易被忽视的能力

> **注意**：本节内容基于 SKILL.md 中定义的推理步骤和报告规范，结合通用知识（General World Knowledge） 对设计意图进行推断。SKILL.md 明确定义了"做什么"和"怎么做"，但未显式说明"为什么这样设计"。以下分析基于代码结构、项目 README 中描述的 Hypothetico-Deductive 范式以及其他技能定义推导得出。

## 设计哲学：Agent 的"临床推理"方法论

### 假说-演绎推理

witty-diagnosis-agent 整体的核心方法论是 **Hypothetico-Deductive（假说-演绎）** 推理范式。这个 Skill 将这一哲学具体化为可操作的推理步骤：

```text
现象观察（Observation）
    ↓
建立假说（Hypothesis Formation）："可能的原因是 X"
    ↓
演绎验证（Deductive Testing）："如果 X 是根因，那么应该观察到 Y"
    ↓
证据收集（Evidence Collection）：检查 Y 是否存在
    ↓
假说评估（Hypothesis Evaluation）：支持证据 vs 反对证据
    ↓
收敛或迭代（Converge or Iterate）
```

这与传统"专家系统"的规则匹配有着本质区别。专家系统试图穷举所有故障模式（"如果 A 且 B，则结论是 C"），而 Agent 的方法更接近人类的认知过程——**先提出假说，再针对性收集证据来验证**。这意味着它不依赖预定义的故障模板，能处理未见过的故障模式。

### "现象驱动" vs "数据驱动"

这是一个微妙但重要的设计决策。**"数据驱动"意味着让数据决定分析方向**——先收集所有数据，再从数据中寻找模式。这在实践中往往导致"捡了芝麻丢了西瓜"，因为数据量太大，信号淹没在噪声中。

**"现象驱动"则是从故障表象出发，反向追踪根因**：

```text
现象：支付接口 500（这是故障的外在表现）
  ↓
问：为什么支付接口会 500？
  ↓
中间链路：DB 连接池耗尽 → 新请求超时
  ↓
问：为什么连接池会耗尽？
  ↓
根因候选：某 SQL 全表扫描 → 连接长期不释放
```

这种自顶向下的推理方式更高效，因为它始终紧扣"解释现象"这个目标，不会在无关数据上浪费计算资源。每个分析步骤都有一个明确的"为什么"驱动。

### Agent 的"元认知"：置信度

> **注意**：下列关于置信度体系与"元认知"的内在关联分析，以及"对抗确认偏误"的设计意图，是基于推理得出的判断。SKILL.md 中明确定义了四级置信度的语义标准，但未显式说明其认知科学层面的设计动机。

这个 Skill 最有趣的设计之一是**置信度评估体系**。它本质上是 Agent 的"元认知"——对自己认知状态的反思：

| 置信度 | 标识 | Agent 的自我评估 | 对应人类状态 |
|-------|------|-----------------|------------|
| 高置信 | 🟢 | "证据链完整，单一原因可解释所有现象" | 确诊 |
| 中置信 | 🟡 | "主因基本确认，但有 1-2 个无法完全解释的次要现象" | 有保留的诊断 |
| 低置信 | 🟠 | "有多个可疑原因，尚未排除竞争性假说" | 鉴别诊断中 |
| 未知 | 🔴 | "现象无法解释，需要进一步调查" | 原因不明 |

这一设计的精妙之处在于：它不仅告诉读者"Agent 认为答案是什么"，还告诉读者"Agent 对答案的把握有多大"。在运维场景中，这一信息有时比结论本身更重要——一个 🟠 低置信度的根因判断意味着需要人工介入验证，而 🟢 高置信度的结论则可以直接触发自动修复。

## 核心流程：Agent 的三阶段推理

### Phase 1：证据收集与关联（从数据到证据）

这个阶段发生在 Agent 的"感知层"。它的输入是前序多个诊断 Skill 的输出——这些输出可能是文本分析、结构化 JSON 或命令行执行结果。Agent 需要做三件事：

#### 1a. 数据归一化

多源异构数据被归一化为统一的**内部证据实体（Evidence Entity）**。每个证据实体至少包含：

- **时间戳**：事件发生的精确时间（强制统一为绝对时间 `YYYY-MM-DD HH:MM:SS`，避免相对时间的歧义）
- **来源**：证据的来源 Skill 和数据源路径
- **类型**：日志片段 / 指标异常 / 系统状态 / 命令输出
- **内容摘要**：关键信息的结构化描述

这一步骤的关键在于**降噪**。原始诊断数据中有大量冗余信息（正常状态的确认、重复的日志等），Agent 需要提取真正有价值的信号。

#### 1b. 时间线重建

Agent 将所有证据按时间排序，构建一条事件时间线。这个过程不仅仅是排序——Agent 需要识别出几个关键的时间节点：

```text
首次异常发生 ──→ 告警触发 ──→ 故障蔓延 ──→ 尝试恢复 ──→ 当前状态
```

时间线是后续因果推理的基础。Agent 在时间线上标注每个事件的**性质**：

- 📈 外部触发（如流量突增）
- ⚠️ 隐患激活（如慢查询开始）
- 🟡 压力积累（如连接池使用率上升）
- 🔴 故障爆发（如服务中断）

#### 1c. 关联分析

在时间线的基础上，Agent 开始寻找事件之间的**时序关联**和**逻辑关联**。时序关联是"什么先发生"，逻辑关联是"什么导致了什么"。这是整个 Skill 中最需要推理能力的环节，也是纯规则系统最难实现的部分。

### Phase 2：根因推断与影响评估（从推理到判断）

#### 2a. 构建故障传导链路

Agent 采用"现象驱动"的方法，从最外部的故障表象出发，逐层深入构建因果树：

```text
故障表象（最外层，用户/监控可见）
    ↓ "为什么会这样？"
中间链路 1（第一层原因）
    ↓ "再进一步，为什么会这样？"
中间链路 2（更深层原因）
    ↓ ...
根因候选（最底层，技术根因）
```

这个因果树的构建不是一个一次性过程，而是一个**迭代推理循环**：

1. Agent 观察当前层级的现象
2. 提出一个或多个可能的解释（假说）
3. 在已有证据中寻找支持或反驳该假说的信息
4. 如果找到足够的证据，继续深入下一层
5. 如果在某层找不到证据支持，回到上层，尝试其他假说
6. 当某个原因无法再被分解（"这就是最根本的"），标记为根因候选

这正是"假说-演绎"方法的具体实践。

#### 2b. 假设验证与置信度评估

一旦 Agent 提取出根因候选，它需要做一件非常重要的事情：**自我审查**。对于每个候选，Agent 会列出：

- **正向证据（支持）**：哪些现象可以用这个根因解释
- **反向证据（反对）**：哪些现象这个根因无法解释

然后基于以下规则评估置信度：

- **决定性证据 + 能解释所有现象 → 🟢 高置信**
    - "找到了唯一能解释一切的证据，且该根因可以被验证"
- **间接证据 + 无明显反证 → 🟡 中置信**
    - "证据指向这个方向，但缺少关键性证据或存在次要未解现象"
- **相互矛盾的证据 + 多个竞争性假说 → 🟠 低置信**
    - "目前还不能排除其他可能性"

> **设计意图**：这个评估机制强制 Agent 对抗"确认偏误"——这是人类推理中最常见的认知偏差之一。人类容易高估支持自己假说的证据权重，低估反对证据。通过显式要求 Agent 同时列出正向和反向证据，Skill 的设计者在 Agent 的认知过程中嵌入了一个"反思"环节。

#### 2c. 业务影响评估

根因分析最终要回答的不是"技术上出了什么问题"，而是"这对业务意味着什么"。Agent 需要评估：

- **影响范围**：哪些服务、节点、用户受到了影响
- **故障时段**：从首次异常发生到当前的时间窗口
- **严重程度**：基于影响面进行定级（P1/P2/P3 或 Critical/Major/Minor）

### Phase 3：输出标准化故障诊断报告（从判断到沟通）

诊断的最终产出是一份结构化的故障诊断报告。这份报告的设计遵循一个重要原则：**它是 Agent 与人类之间的通信协议**。

报告分为以下主要部分：

#### 故障概览（速查区）

一张表格让读者在 10 秒内了解概况：故障标题、影响范围、故障时段、根因摘要、恢复状态、置信度。

这部分的设计体现了"信息检索的 10 秒原则"——当 SRE 被线上故障打得焦头烂额时，他们没有时间通读长文。故障概览就是他们的"急诊分诊台"。

#### 事故时间线与故障传导链路（叙事区）

这是报告的核心叙事部分，也是 Agent 推理过程的"可视化呈现"：

```text
时间                   事件                                          性质         溯源路径
─────────────────────────────────────────────────────────────────────────────────────────────────────
2024-01-01 09:05:00   用户请求量突增（大促活动开始）                    📈 外部触发   [nginx/access.log]
  │
  ▼
2024-01-01 09:08:00   orders 表慢查询开始堆积（status 字段全表扫描）     ⚠️ 隐患激活   [mysql/slow.log]
```

这个时间线 + 因果链的联合视图是报告中最有价值的部分。它让读者一眼看清故障的"故事线"——不是数据罗列，而是有因果关系的叙事。

> **关键设计决策**：Agent 不只是在输出数据，它是在讲述故事。这是一个重要的认知转变。故障诊断报告的读者（人类 SRE）需要的不是数据堆砌，而是一个有开头、发展、高潮、结局的故事。

#### 排查过程（推理区）

Agent 展示它经历了哪些推理路径，排除了哪些假说，最终如何收敛到根因：

```text
支付接口 500
├─► 网络层                → ✅ 正常，排除（基于 ping/nslookup）
├─► 应用服务              → ✅ 进程存活，排除崩溃（基于 ps/日志）
│       └─► 日志发现连接池超时 → 🔍 深入 DB 层
└─► 数据库层              → ❌ 连接池 100/100 已满
        └─► 慢查询堆积      → ❌ 80+ 线程卡住
                └─► 定位 SQL → ❌ orders.status 全表扫描
                        └─► 🎯 根因确认：缺少索引
```

这个排查树的设计目的是**建立信任**。当人类 SRE 看到 Agent 系统地考虑并排除了各种可能性，他们对最终结论的信任度会显著提高。相反，如果 Agent 直接跳出一个结论而没有展示推理过程，人类很难信任这个结论。

#### 修复方案（行动区）

报告的最终落脚点是"接下来怎么办"。Agent 输出两个时间维度的方案：

- **应急处置**：立即可以执行的操作（如 Kill 慢查询、重启服务）
- **永久修复计划**：解决问题的根本措施（如补充索引、优化 SQL、增加连接池）

> **注意**：本节的技术权衡分析基于对 SKILL.md 中设计选择的推理和对比分析，以及 witty-diagnosis-agent 项目文档中对运维场景的描述。SKILL.md 本身是一个规范性文档，未包含权衡讨论。

## 技术权衡

### 结构化模板 vs 自由形式

**选择**：强结构化模板。

**理由**：在运维场景中，一致性比创造性更重要。当一套系统每天产生数十份诊断报告时，报告的格式一致性决定了阅读效率。强结构化模板确保了无论是什么类型的故障，读者都知道去哪里找关键信息。

**代价**：某些非常规故障可能需要更灵活的表述方式，模板的固定结构可能限制了表达。

### 置信度细化 vs 简化

**选择**：四级置信度（高/中/低/未知），带详细语义定义。

**理由**：置信度不是一个可有可无的附属信息，它是 Agent 自我认知的核心表达。四级分级在粒度（足够区分不同确信程度）和易用性（人容易理解和记忆）之间取得了平衡。

**代价**：即使有详细的语义定义，不同场景下 Agent 的置信度标定可能不够稳定。

### "现象驱动" vs "全面覆盖"

**选择**：现象驱动，自顶向下追溯。

**理由**：全面覆盖（检查一切可能）在理论上更完备，但在实践中不可行——系统故障的搜索空间是指数级的。现象驱动通过"以解释为目标"的推理，大幅缩小了搜索空间。

**代价**：如果 Agent 对初始现象的观察不完整或偏差，可能沿着错误的方向进行推理，遗漏真实根因。这就是为什么置信度机制和"反思"环节如此重要——它们为这种风险提供了安全保障。

### 标准化报告 vs 差异化输出

**选择**：统一使用标准报告模板，但允许在模板框架内的灵活填充。

**理由**：标准化的好处已在前文讨论。但 Agent 仍然需要在模板中做出判断——哪些排查路径需要详细展示、哪些可以略过、因果链的详细程度等。采用"框架统一，内容灵活"的策略。

## 使用视角：用户如何与 Agent 协作

### 触发时机

这个 Skill 不是用户直接调用的。它在 witty-diagnosis-agent 的多 Agent 工作流中被自动触发——当前置诊断 Skill 完成数据采集后，Agent 会进入根因分析与报告生成阶段。用户的使用体验是：

```text
用户输入："/diagnose" 或自然语言描述故障
     ↓
Agent 自动触发相关诊断 Skill（VMCore / 磁盘 / 网络 / OOM ...）
     ↓
诊断结果自动进入 fault-rca-report-generation Skill
     ↓
Agent 输出一份完整的故障诊断报告
```

### 用户的关键行为

虽然 Agent 自动完成大部分工作，但有几个关键交互节点：

1. **提供初始故障描述**：用户描述得越精确（"支付接口 500 报错" vs "系统有问题"），Agent 的现象驱动推理就越高效
2. **确认或修正推理方向**：在 Agent 生成排查树后，用户可以补充 Agent 未掌握的信息，或纠正 Agent 的理解偏差
3. **审阅报告并执行修复**：报告中的置信度标识帮助用户判断哪些结论可以信任、哪些需要人工验证

### 典型使用场景

```text
用户：帮我看看为什么支付服务最近半小时一直报 500 错误。

Agent：（自动触发数据收集 → 调用多个诊断 Skill → 执行 RCA 推理）
↓
输出故障诊断报告，包含：
  - 根因：users 表缺少联合索引导致的连接池耗尽
  - 置信度：🟢 高置信
  - 应急处置：Kill 当前慢查询以释放连接池
  - 永久修复：为 users 表补充 (status, created_at) 联合索引
```

### 与命令行工具的集成

在 witty-diagnosis-agent 的命令体系中，诊断命令 `diagnose` 和 `collect-data` 的输出会自动成为这个 Skill 的输入。用户无需记住特殊命令——整个流程是端到端的。

## 总结

`fault-rca-report-generation` Skill 是 witty-diagnosis-agent 推理能力的集中体现。它不仅是一份"文档"，更是一套定义 Agent 如何思考、如何推理、如何与人类沟通的**认知协议**。

它的核心设计可以概括为：

| 维度 | 设计选择 | 为什么 |
|------|---------|--------|
| 推理范式 | 假说-演绎 | 可处理未知故障模式，不依赖预定义规则库 |
| 驱动方式 | 现象驱动 | 缩小搜索空间，保持推理目标清晰 |
| 证据要求 | 正向+反向同时评估 | 强制 Agent 自我反思，对抗确认偏误 |
| 输出格式 | 强结构化模板 | 保证一致性和人类阅读效率 |
| 认知表达 | 四级置信度体系 | 不仅告诉"是什么"，还告诉"多确信" |

> 当 AI Agent 在做故障诊断时，它不是在"运行程序"，而是在进行一种拟人的认知活动——观察、假设、验证、推理、沟通。这个 Skill 的精髓不在于它写了什么代码，而在于它如何定义了一种**科学的、可追溯的、可信赖的**认知范式，并将其交付给 Agent 执行。这才是"AI 辅助运维"从工具走向伙伴的关键一步。
